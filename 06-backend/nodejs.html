Node.js

The JavaScript runtime that runs outside the browser — modules, npm, the file system, environment variables, and the server building blocks behind the MERN backend.

JavaScript needs a runtime

JavaScript is a programming language. A language by itself cannot do anything — it needs a runtime environment to execute and to provide the APIs it can interact with. The two common environments are the browser and Node.js.

Browser                          Node.js
   |                                 |
Browser APIs                     Node.js APIs
   |                                 |
DOM / Web/DOM/UI              OS / Files / Network

The same JavaScript runs in both, but the environment decides what the code is allowed to touch:

ConcernBrowserNode.js
RunsWeb pageTerminal / server
InputMouse, keyboard, page, networkTerminal, files, network, OS
OutputWeb page, DevTools consoleTerminal, files, network, OS
APIsdocument, window, DOM, Web APIsfs, path, http, process

For example, the same line behaves differently in each runtime:

console.log("Hello");

// Browser  -> prints to DevTools console
// Node.js  -> run "node app.js", prints to the Terminal
Key point

JavaScript is the language; Browser and Node.js are the runtimes. In MERN, React runs JavaScript in the browser and Node.js runs JavaScript on the server.

Running Node.js

The node executable runs a JavaScript file outside the browser. This is how your Express server starts on a machine or in production; -v flags verify what versions are installed before you debug anything else.

# create server.js, then run it
node server.js      # executes the file once; process exits when done

# check the installed Node version
node -v             # useful before reporting bugs or picking ES features

# check the npm version
npm -v

npm — Node Package Manager

npm is the default package manager bundled with Node. It downloads third-party libraries (the whole Express/Mongoose ecosystem), records them in package.json, and pins exact versions in package-lock.json so every machine installs the same tree.

# create package.json (interactive)
npm init

# create package.json with defaults
npm init -y          # skips the questions; good for quick projects

# install a runtime dependency
npm install express  # added to "dependencies"

# install a development-only dependency
npm install -D nodemon  # added to "devDependencies" (not shipped to prod)

# remove a dependency
npm uninstall express

Run the scripts you define in package.json:

npm start      # runs the "start" script
npm run dev    # runs the "dev" script (any custom name needs "run")

package.json

The manifest describes your project: its name, version, scripts, and dependencies.

{
    "name": "notes-app",
    "version": "1.0.0",

    "scripts": {
        "start": "node server.js",
        "dev": "nodemon server.js"
    },

    "dependencies": {
        "express": "..."
    },

    "devDependencies": {
        "nodemon": "..."
    }
}
  • dependencies — packages the app needs in production.
  • devDependencies — packages only needed while developing (added with -D).
  • scripts — named commands run with npm run <name>.

Modules — CommonJS

Modules split code into files and expose only what you export, so each file has its own scope. CommonJS is Node's original system: require() loads a module synchronously, and module.exports defines what leaves the file. You will still see it in older Express tutorials and many npm packages.

// import (CommonJS) — path without extension, resolved from node_modules or ./ 
const express = require("express");
const { add } = require("./math");  // destructure a named export

// export (CommonJS) — assigning replaces the whole module.exports object
module.exports = something;

Modules — ES Modules

The standard import / export syntax, shared with the browser and modern React. Set "type": "module" in package.json (or use the .mjs extension) to enable it. Prefer ESM in new projects so client and server code look the same.

// default export — one main value per module
export default something;

// named export — many values, imported by exact name
export { something };

// import a default export
import express from "express";

// import a named export — include the .js extension in Node ESM
import { something } from "./file.js";

ESM example

A complete two-file example: one file exports a function using a named export, the other imports it by that exact name. Note that Node ESM requires the file extension in the import path.

// math.js
export const add = (a, b) => {   // exported at definition
    return a + b;
};

// server.js
import { add } from "./math.js"; // named import must match the export name

console.log(add(5, 3)); // 8

Globals and the process object

Node exposes process as a global object describing the running program — always available without an import.

console.log(process);   // the full object (type, platform, version, ...)

process.env;      // environment variables
process.argv;     // command-line arguments
process.cwd();    // current working directory

// current environment
console.log(process.env.NODE_ENV);  // "development" | "production" | undefined

// exit the program with a non-zero code (failure)
process.exit(1);  // 0 = success; any non-zero = failure for CI/deploy scripts
  • process.argv — array of command-line arguments; argv[2] is the first user argument.
  • process.cwd() — the directory the process was started from.
  • process.env — the merged environment variables (see below).
  • process.exit(code) — stop the process; 0 means success.

Environment variables and .env

Secrets and per-environment settings (ports, database URLs, API keys) belong in environment variables — never hard-coded in source. The dotenv package loads a .env file into process.env at startup.

npm install dotenv
import dotenv from "dotenv";

dotenv.config();  // reads .env and copies each key into process.env

const port = process.env.PORT || 5000;  // fall back to 5000 if unset
console.log(process.env.PORT);
# .env
PORT=5000
MONGO_URI=mongodb://...
JWT_SECRET=mysecret
Warning

Never put secrets directly in your code: const password = "123456"; is wrong. Use process.env.PASSWORD and add .env to .gitignore. Commit a .env.example with placeholder keys instead.

The path module

path builds and inspects file paths safely across operating systems.

import path from "path";

const filePath = path.join("uploads", "images", "photo.jpg"); // joins with the OS separator

console.log(filePath);          // uploads\images\photo.jpg (Windows) or uploads/images/photo.jpg (Linux)
console.log(path.basename(filePath)); // photo.jpg   ← filename only
console.log(path.extname(filePath));  // .jpg        ← extension
console.log(path.dirname(filePath));  // uploads\images  ← folder part

File system — synchronous (fs)

The fs module reads and writes files. The *Sync methods block the event loop until they finish, so use them mainly for startup or scripts.

import fs from "fs";

// read a file — returns a string because we passed the "utf8" encoding
const data = fs.readFileSync("file.txt", "utf8");

// write a file — overwrites the whole file if it already exists
fs.writeFileSync("file.txt", "Hello");

File system — asynchronous (fs/promises)

In server code, prefer the promise-based API so you never block the event loop. While a read is in flight, Node keeps serving other requests.

import fs from "fs/promises";

// read — awaits without freezing the server
const data = await fs.readFile("file.txt", "utf8");

// write — returns a promise, so remember to await it
await fs.writeFile("file.txt", "Hello");

The crypto module

crypto provides cryptographic primitives. A common use is generating secure random values (for example, file keys or tokens).

import crypto from "crypto";

// 16 random bytes -> 32-char hex string; safe for filenames or tokens
const randomValue = crypto.randomBytes(16).toString("hex");

HTTP server without Express

Node's built-in http module can create a server on its own. Express wraps this and makes routing far simpler — but seeing the raw version shows what Express hides. Here every request hits the same callback; you would have to parse the URL and method yourself.

import http from "http";

const server = http.createServer((req, res) => {
    res.writeHead(200, { "Content-Type": "text/plain" }); // status + headers manually
    res.end("Hello Node");                                // send body and finish
});

server.listen(5000, () => {   // bind to a port
    console.log("Server running");
});

Continue to Express for the same server with clean routing and middleware.

Async / await and Promises

A Promise represents a value that will exist later. async / await lets you write asynchronous code that reads like synchronous code, avoiding deeply nested callbacks ("callback hell").

const promise = new Promise((resolve, reject) => {
    const success = true;
    if (success) {
        resolve("Success");   // fulfils the promise with a value
    } else {
        reject("Failed");     // rejects with an error/reason
    }
});

promise
    .then((result) => {
        console.log(result);
    })
    .catch((error) => {   // always handle rejection
        console.log(error);
    });
const getData = async () => {   // async always returns a promise
    const result = await someFunction();  // pauses here until it resolves
    console.log(result);
};

Note

Older Node code passes a callback function that runs when the work finishes. Prefer promises and async / await in new code.

try / catch error handling

Wrap awaited calls in try / catch so a rejected promise becomes a handled error instead of an unhandled rejection.

async function getUsers() {
    try {
        const users = await User.find();
        return users;
    } catch (error) {
        console.error(error);
        throw error;   // re-throw so the caller (route) can respond
    }
}
try {
    const result = await getData();
} catch (error) {
    console.error(error);   // handle the rejection here instead of crashing
}

The event loop

Node.js is single-threaded and event-driven: it does not wait for timers or I/O, it keeps processing other work and runs callbacks when those operations complete.

console.log("1");

setTimeout(() => {
    console.log("2");
}, 0);

console.log("3");

// Output: 1, 3, 2

Events and Streams

Two core Node ideas that power servers and large files: events (a source emits signals you listen for) and streams (data flows in chunks instead of loading everything at once).

EventEmitter

An EventEmitter lets an object publish named events that other code subscribes to. You register a listener with on() and fire the event with emit(), which keeps the code that triggers an event separate from the code that reacts to it.

import { EventEmitter } from "events";

const emitter = new EventEmitter();

emitter.on("userCreated", (user) => {   // register a listener
    console.log("New user:", user.name);
});

emitter.emit("userCreated", { name: "Alice" }); // fire the event with a payload

Many Node objects are event emitters — an HTTP server emits "request", a stream emits "data", "end", and "error".

Readable and writable streams

Streams move data in small chunks instead of loading a whole file into memory, which keeps large files and network traffic efficient. A readable stream emits "data" chunks and an "end" event; a writable stream consumes chunks.

import fs from "fs";

// readable stream: read a big file in chunks
const readStream = fs.createReadStream("big.txt", "utf8");

readStream.on("data", (chunk) => {   // fires repeatedly, one chunk at a time
    console.log("chunk length:", chunk.length);
});

readStream.on("end", () => {   // all chunks consumed
    console.log("done");
});

// writable stream
const writeStream = fs.createWriteStream("copy.txt");
Watch out

A stream that errors with no "error" listener will crash the process. Always attach stream.on("error", handler).

Piping

pipe() connects a readable stream to a writable one, flowing data without buffering the whole file in memory.

const readStream = fs.createReadStream("big.txt");
const writeStream = fs.createWriteStream("copy.txt");

readStream.pipe(writeStream);   // chunks flow automatically to the destination

// in an HTTP server, stream a file straight to the response:
// readStream.pipe(res);

Node + Express

Express is the framework that runs on top of Node. This is the smallest Express server.

import express from "express";

const app = express();

app.use(express.json());   // parse JSON bodies before routes run

app.get("/", (req, res) => {
    res.json({ message: "Hello Node" });   // send JSON, not plain text
});

app.listen(5000, () => {
    console.log("Server running on port 5000");
});

Full routing, middleware, and controllers live on the Express page.

Node + Mongoose connection

Connect to MongoDB once at startup. The connection string comes from an environment variable (see the env vars section).

import mongoose from "mongoose";

mongoose.connect(process.env.MONGO_URI)  // URI from .env, never hard-coded
    .then(() => {
        console.log("MongoDB connected");
    })
    .catch((error) => {   // bad URI or DB down -> fail loudly at startup
        console.error(error);
    });

Schemas, models, and queries are covered on MongoDB Basics.
