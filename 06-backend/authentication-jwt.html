Registration flow

Registration creates the account: the client sends credentials, the server validates them and hashes the password, and only then persists the user. Hashing always happens on the server, never in the browser.

Warning

Never save a plain password. password: "123456" is wrong; store password: hashedPassword.

bcrypt

bcrypt is a one-way password-hashing library. You hash a password once at registration and never decrypt it; at login you compare the submitted password against the stored hash. Hashing means a database leak does not expose real passwords.

npm install bcrypt
import bcrypt from "bcrypt";

// hash a password before saving
const hashedPassword = await bcrypt.hash(password, 10);

// compare a plain password against the stored hash
const isMatch = await bcrypt.compare(password, user.password);
// true or false
Key point

The number 10 is the salt rounds (cost factor). Hashing is intentionally slow to resist brute force.

User model

Email is unique, the password is always stored hashed, and role drives authorization.

const userSchema = new mongoose.Schema({
    name: {

        required: true,

Login flow

The login endpoint receives credentials and returns a signed token. It reuses bcrypt.compare to check the password, then mints a JWT the client can present on later requests.

JWT — JSON Web Token

A JWT is a signed, tamper-evident string that carries a payload of information about the user.

{
    "id": "123",
    "role": "admin"
}

The token is signed using a secret key. The server can verify the signature later without storing session state.

Watch out

A JWT is only signed, not encrypted. Anyone can decode the payload, so never put secrets or sensitive data inside it.

jsonwebtoken

jsonwebtoken is the library that creates (sign) and checks (verify) JWTs. Sign the payload with your secret at login so the client can present it later; the secret is what makes the token unforgeable.

npm install jsonwebtoken
import jwt from "jsonwebtoken";

const token = jwt.sign(
    {
        id: user._id,   // public claim: identify the user, no secrets
        role: user.role // authorization data read later by adminOnly
    },
    process.env.JWT_SECRET, // signing key: must stay server-side
    {
        expiresIn: "30d"    // token is rejected automatically after this
    }
);

JWT secret

The secret is the private key that signs and verifies every token. Anyone who knows it can mint valid tokens, so it must be long, random, and kept out of source control.

# .env
JWT_SECRET=very-long-random-secret # server-only; loaded via process.env
Common mistake

Never commit JWT_SECRET to GitHub. Keep it in .env and add .env to .gitignore. See Node.js · Environment variables.

Send the token to the client

After signing, the token is returned to the client in the response body (or a cookie). The client stores it and attaches it to later requests so the server can identify the user without a session store.

res.json({
    user,
    token
});
{
    "user": {
        "_id": "123",
        "name": "Alice"
    },
    "token": "eyJhbGciOiJIUzI1Ni..."
}

Client sends the token

For every protected request the client sends the token in the Authorization header using the Bearer scheme. This keeps the credential out of the URL and body.

GET /api/users/profile

Header:
Authorization: Bearer eyJhbGciOi...

Get the token from the header

The server extracts the raw token by splitting the header on the space after Bearer. Optional chaining guards against a missing header so the code does not throw.

const authHeader = req.headers.authorization;
// "Bearer eyJhbGciOi..."

const token = authHeader?.split(" ")[1]; // part after "Bearer"

The protect middleware

This page owns the protect middleware. It verifies the JWT, decodes it, attaches the user to req.user, and otherwise responds 401.

const protect = async (req, res, next) => {
    try {
        const authHeader = req.headers.authorization;

        if (!authHeader || !authHeader.startsWith("Bearer")) { // no/invalid scheme
            return res.status(401).json({ message: "Not authorized" });
        }

        const token = authHeader.split(" ")[1];

        const decoded = jwt.verify(token, process.env.JWT_SECRET); // throws if tampered or expired

        req.user = decoded; // controllers read the identity from here

        next();
    } catch (error) {
        return res.status(401).json({ message: "Invalid token" });
    }
};

Protected route

Attaching protect to a route gates it: the middleware runs before the controller, so only requests carrying a valid token reach the handler.

router.get("/profile", protect, getProfile); // runs protect first

// req.user = { id: "...", role: "admin" }

Role middleware: adminOnly

Authorization happens after authentication: the token is valid, and now we check the role.

const adminOnly = (req, res, next) => {
    if (req.user.role !== "admin") { // protect already ran, so req.user exists
        return res.status(403).json({ message: "Admin access required" }); // 403 = known but forbidden
    }

    next();
};

router.delete("/products/:id", protect, adminOnly, deleteProduct);

Login controller

The controller ties the login flow together: find the user, compare the password, sign a token, and return it. On any failure it responds 401 without revealing which field was wrong.

const login = async (req, res, next) => {
    try {
        const { email, password } = req.body;

        const user = await User.findOne({ email });

        if (!user) {
            return res.status(401).json({ message: "Invalid credentials" }); // same message as a bad password
        }

        const isMatch = await bcrypt.compare(password, user.password); // never compare plain text

        if (!isMatch) {
            return res.status(401).json({ message: "Invalid credentials" });
        }

        const token = jwt.sign(
            { id: user._id, role: user.role },
            process.env.JWT_SECRET,
            { expiresIn: "30d" }
        );

        res.json({ user, token });
    } catch (error) {
        next(error);
    }
};

Register controller

The register controller validates uniqueness, hashes the password, and creates the user. It returns 409 if the email already exists and 201 on success.

const register = async (req, res, next) => {
    try {
        const { name, email, password } = req.body;

        const existingUser = await User.findOne({ email });

        if (existingUser) {
            return res.status(409).json({ message: "User already exists" }); // 409 = conflict
        }

        const hashedPassword = await bcrypt.hash(password, 10); // hash before it touches the DB

        const user = await User.create({
            name,
            email,
            password: hashedPassword
        });

        res.status(201).json({ message: "User created", user });
    } catch (error) {
        next(error);
    }
};

Never return the password

Serialized user documents include the hashed password unless you remove it. Strip it before sending any user object to the client.

// Bad: res.json(user);  -> may include password

// Better: exclude it explicitly
const user = await User.findById(id).select("-password");

Logout

  • If the JWT is stored client-side, remove it on the client: localStorage.removeItem("token");
  • If using HTTP-only cookies, clear the cookie on the server: res.clearCookie("token");

Cookies

A cookie is an alternative transport for the token that the browser sends automatically. An httpOnly cookie cannot be read by JavaScript, which reduces token theft via XSS compared with localStorage.

npm install cookie-parser

HTTP-only cookies can store the auth token so JavaScript cannot read it directly, which reduces XSS token theft.

res.cookie("token", token, {
    httpOnly: true,    // JavaScript cannot read it -> blocks XSS theft
    secure: true,      // sent only over HTTPS
    sameSite: "strict" // not sent cross-site -> CSRF defense
});

Security checklist

  • Hash passwords with bcrypt
  • Validate all input
  • Use HTTPS
  • Keep secrets in .env
  • Use a strong JWT secret
  • Never return passwords (.select("-password"))
  • Protect sensitive routes
  • Check user roles
  • Use Helmet for security headers
  • Configure CORS correctly — see Internet & Web Fundamentals
  • Rate-limit login endpoints

Quick recap

  • Authentication = who you are; authorization = what you may do
  • bcrypt: hash(password, 10) / compare(password, hash)
  • User model: unique email, hashed password, role enum
  • Login: find user → compare password → sign JWT → send token
  • jwt.sign(payload, secret, { expiresIn }); secret in .env
  • Client sends Authorization: Bearer TOKEN
  • protect: verify token, set req.user, else 401
  • adminOnly: check req.user.role, else 403
  • Never return the password; use .select("-password")
  • Logout clears the token/cookie; access + refresh tokens extend sessions
  • Harden with Helmet, CORS, rate limiting, and HTTPS
