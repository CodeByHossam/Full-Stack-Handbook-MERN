REST API

How applications communicate over HTTP — methods, status codes, resource naming, request anatomy, CRUD endpoints, filtering, pagination, and versioning. This page owns the API design rules.

Backend API Design HTTP · CRUD

REST vs HTTP

REST is a way for applications to communicate using HTTP. The terms are related but distinct:

  • HTTP — the communication protocol.
  • REST — an architectural style for designing APIs on top of HTTP.
  • Express — the framework used to build the API.
  • MongoDB — the database behind it.

HTTP methods

Each HTTP verb signals the intended action on a resource, which is why REST APIs reuse a small fixed set of methods instead of inventing custom action names. Idempotent means repeating the call has the same effect as calling once (safe to retry).

MethodActionBody?Idempotent
GETRead dataNoYes
POSTCreate dataYesNo
PUTReplace / full updateYesYes
PATCHUpdate part of a resourceYesNo
DELETEDelete dataNoYes

CRUD mapping

CRUD (Create, Read, Update, Delete) maps one-to-one onto HTTP methods. Use this mapping to pick the verb: the verb carries the action, so the URL never needs to.

CREATE → POST
READ   → GET
UPDATE → PUT / PATCH
DELETE → DELETE
GET     /api/products        # list all
GET     /api/products/123    # read one
POST    /api/products        # create
PUT     /api/products/123    # replace one
PATCH   /api/products/123    # update part of one
DELETE  /api/products/123    # delete one

Request anatomy

Every request can carry several parts. Knowing which part to use is the core API design skill.

POST /api/users

Headers:
  Authorization: Bearer TOKEN
  Content-Type: application/json

Body:
{
    "name": "Alice",
    "email": "alice@example.com"
}
PartPurposeExpress access
URL parametersIdentify one resourcereq.params
Query parametersFilter, search, sort, paginatereq.query
BodyData to create/updatereq.body
HeadersMetadata such as auth tokensreq.headers

URL parameters

Used to identify a specific resource within a collection — the :id is a placeholder the router fills from the path.

// GET /api/products/123
router.get("/products/:id", (req, res) => {
    console.log(req.params.id); // "123" — the resource id
});

Query parameters

Used for filtering, searching, sorting, and pagination — they modify how a collection is returned and never identify the resource itself. They are always strings, so convert numbers explicitly.

// /api/products?category=phones&page=2&limit=10
const { category, page, limit } = req.query;   // all strings

Request body

Used mainly with POST / PUT / PATCH to carry the data to create or update. It requires the server to parse it (express.json()).

{
    "name": "Laptop",
    "price": 1000
}
const { name, price } = req.body;   // destructure the parsed payload

Content types and multipart/form-data

The Content-Type header tells the server how to decode the request body. JSON is only one option — the parser you register in Express must match the type being sent.

Content-TypeBody carriesExpress parser
application/jsonA JSON objectexpress.json()
application/x-www-form-urlencodedKey/value text from a plain formexpress.urlencoded()
multipart/form-dataFile bytes plus fields, split by a boundaryMulter (not built in)

multipart/form-data is the type a browser uses when a form contains a file input. Express does not parse it — express.json() ignores it — so an upload endpoint needs Multer middleware.

const multer = require("multer");
const upload = multer({ dest: "uploads/" });

// POST /api/products with a multipart body
router.post("/products", upload.single("image"), createProduct);
// file -> req.file, other fields -> req.body

Full client and server mechanics are owned by File Uploads.

Headers

Headers carry metadata about the request — content type, caching, and authentication. The Authorization header is how a JWT reaches the server.

Authorization: Bearer TOKEN
Content-Type: application/json
req.headers.authorization;   // header names are lower-cased

Response shape

The server sends a status code, headers, and (usually) a body. Keep the body shape consistent so the client can parse every endpoint the same way.

res.status(200).json({   // 200 = success
    message: "Success"
});

Status codes

The status code is the first thing a client checks, so getting it right matters more than the message text. Codes group by first digit: 2xx success, 4xx the client did something wrong, 5xx the server failed. This table is the single source of truth for status codes across the library.

CodeNameMeaning
200OKRequest successful
201CreatedNew resource created
204No ContentSuccessful, no response body
400Bad RequestInvalid request
401UnauthorizedNot authenticated
403ForbiddenAuthenticated but not allowed
404Not FoundResource does not exist
409ConflictConflict, e.g. duplicate email
422Unprocessable EntityValidation error
500Internal Server ErrorServer problem

REST naming rules

Prefer nouns for resources. The HTTP method already describes the action, so verbs in the path are redundant.

GoodAvoid
/api/users/api/getUsers
/api/products/api/createProduct
/api/orders/api/deleteOrder

CRUD endpoints in practice

The same URL plus a different verb gives each CRUD operation its own endpoint. Notice the response status changes with the action — not always 200.

Get all

Lists the whole collection. It returns 200 OK with a JSON array; on a real dataset this endpoint also applies filtering, sorting, and pagination.

GET /api/products        # 200 OK, returns an array

[
    { "_id": "1", "name": "Laptop" },
    { "_id": "2", "name": "Phone" }
]

Get one

Fetches a single resource by the id in the URL path. If no document matches, the correct response is 404 Not Found rather than an empty object.

GET /api/products/123    # 200 OK, or 404 if the id does not exist

{
    "_id": "123",
    "name": "Laptop",
    "price": 1000
}

Create

Creates a new resource with POST. The new data travels in the request body and the server answers 201 Created with the created document.

POST /api/products

Body:
{ "name": "Laptop", "price": 1000 }

Response: 201 Created    # 201 signals a new resource was made
{ "_id": "123", "name": "Laptop", "price": 1000 }

Update

Changes an existing resource with PATCH (partial) or PUT (full replace). Send only the fields that changed and return the updated document to confirm.

PATCH /api/products/123   # send only the changed fields

Body:
{ "price": 900 }

Response:
{ "_id": "123", "name": "Laptop", "price": 900 }

Delete

Removes a resource by id with DELETE. Reply 200 with a message, or 204 No Content with an empty body.

DELETE /api/products/123

Response:                 # 200 with a message, or 204 with no body
{ "message": "Product deleted" }

Filtering

Filtering narrows a collection by an exact field match, passed as a query parameter and turned into a Mongoose filter object. It reduces payload size and is the first thing to add to a list endpoint.

// GET /api/products?category=phones
const { category } = req.query;

const products = await Product.find({ category });  // { category: "phones" }

Searching

Searching matches part of a string rather than an exact value. The $regex operator does a pattern match and "i" makes it case-insensitive.

// GET /api/products?search=laptop
const { search } = req.query;

const products = await Product.find({
    name: {
        $regex: search,     // substring / pattern match
        $options: "i"       // case-insensitive
    }
});
Watch out

Unanchored $regex cannot use an index and is slow on large collections. Escape user input and consider a text index for real search.

Sorting

Sorting orders results by one or more fields. In Mongoose the value is 1 for ascending and -1 for descending.

// GET /api/products?sort=price
Product.find().sort({ price: 1 });   // cheapest first

// 1  → ascending
// -1 → descending

Pagination

Pagination returns one page of results at a time so a list endpoint does not send thousands of documents. Convert the string query params to numbers and use skip / limit.

/api/products?page=2&limit=10

page 1: skip 0
page 2: skip 10
page 3: skip 20

skip = (page - 1) * limit
const skip = (page - 1) * limit;   // page 2 with limit 10 -> skip 10

const products = await Product.find()
    .skip(skip)      // drop earlier pages
    .limit(limit);   // cap the page size

Combining filter + search + sort + pagination

Real list endpoints combine several query parameters at once. This is the full request shape you build toward, with each option doing one job.

GET /api/products
  ?search=laptop
  &category=electronics
  &page=2
  &limit=10
  &sort=price

This is a very common real-world API pattern. Apply each clause conditionally, then sort and paginate.

const { search, category, sort, page = 1, limit = 10 } = req.query;

const filter = {};                       // build the query up piece by piece
if (category) filter.category = category;
if (search) filter.name = { $regex: search, $options: "i" };

const products = await Product.find(filter)
    .sort({ [sort]: 1 })                 // sort by the requested field
    .skip((page - 1) * limit)            // page offset
    .limit(Number(limit));               // cap results per page

Authenticated request

React sends the token in the Authorization header; middleware verifies it before the controller runs. The implementation is owned by Authentication & JWT.

Authorization: Bearer JWT_TOKEN
const token = req.headers.authorization?.split(" ")[1];  // strip "Bearer "

Protected route

Adding protect as the second argument runs auth before the controller, so only requests with a valid token reach the handler.

router.get("/profile", protect, getProfile);  // protect runs first

Error response envelope

Return a consistent shape so clients can always read success and message.

{
    "success": false,
    "message": "Product not found"
}
res.status(404).json({   // 404 = the resource was not found
    success: false,
    message: "Product not found"
});

Success response envelope

Wrap success responses in the same { success, data } shape so the client always knows where the payload lives. Mixing bare arrays and envelopes across endpoints makes the frontend harder to write.

res.status(200).json({
    success: true,
    data: products   // the actual payload goes under "data"
});

Validation

Never trust req.body. Check required fields, then prefer a schema validator.

if (!name) {
    return res.status(400).json({   // reject early with a client error
        success: false,
        message: "Name is required"
    });
}
Note

Better options: Joi, Zod, or express-validator. They generate consistent 422 validation errors.

REST API routes with Express

Each REST operation becomes one Express route pointing at a controller. Keep the route table flat and noun-based so it maps directly to the resource.

router.get("/products", getProducts);        // GET    list
router.get("/products/:id", getProduct);     // GET    one
router.post("/products", createProduct);     // POST   create
router.patch("/products/:id", updateProduct); // PATCH  part update
router.delete("/products/:id", deleteProduct); // DELETE remove

API versioning

Version the URL so you can change an API without breaking existing clients. Old versions keep working while new ones roll out — critical once mobile apps or third parties depend on the API.

/api/v1/users        # current stable version pinned in the path
/api/v1/products

# later, a breaking change ships without touching v1 clients
/api/v2/users

Quick recap

  • HTTP is the protocol; REST is the API design style; Express builds it
  • Methods: GET, POST, PUT, PATCH, DELETE
  • CRUD: POST create, GET read, PUT/PATCH update, DELETE delete
  • Request parts: params, query, body, headers
  • Status codes: 200/201/204, 400/401/403/404/409/422, 500
  • Name resources with nouns, not verbs
  • Filter, search ($regex), sort (1/-1), paginate (skip = (page-1)*limit)
  • Use consistent response envelopes: success, message, data
  • Validate req.body (Joi / Zod / express-validator)
  • Version APIs: /api/v1/…
  • Token auth: Authorization: Bearer … → protect → req.user
