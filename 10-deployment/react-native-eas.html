Deploy React Native with EAS

A complete, step-by-step guide from account creation to production deployment on Android, iOS, and the Web.

Deployment React Native EAS CLI

What is EAS and why do we need it?

Purpose: Before you start running commands, you need to understand the tool.

EAS (Expo Application Services) is Expo's cloud build and submission service. In the past, to compile an Android app you had to install Android Studio locally; to compile an iOS app you had to have a Mac with Xcode. EAS moves compilation to the cloud—you just run one command, and it compiles your code into an installable binary file on Expo's servers, and even submits it directly to Google Play or the App Store for you.

What is EAS CLI? CLI stands for Command Line Interface. eas-cli is the command-line tool you install on your computer; you interact with EAS services by typing commands in the terminal. It's the "remote control" you use to operate EAS.

The JavaScript Lifecycle (Where does your code live?)

Purpose: To understand how your app actually runs and where the JavaScript code is stored at each stage.

In React Native, the "app" you install is just a native shell (written in Java/Kotlin for Android or Swift for iOS). The actual UI and logic you write in JavaScript/React must be loaded into that shell. Here is where that JavaScript lives depending on your build type:

App Type Where is the JavaScript Code? How it is Loaded
Expo Go On your computer (in your project folder). Expo Go scans a QR code and downloads the JS bundle from your computer's Metro server over Wi-Fi.
Development Build On your computer (in your project folder). The app connects to your computer's Metro server. You get hot-reloading and instant updates.
Preview Build Inside the APK/IPA file. EAS bundles all your JS into a single minified file and bakes it into the app. It runs completely standalone.
Production Build Inside the AAB/IPA file. Same as Preview, but further optimized (Hermes engine, minified, no dev tools) for app store distribution.

Do I Need to Run a Server on My Computer?

Purpose: To know when you can turn off your computer and still use the app.

The "server" in question is the Metro Bundler (run via npx expo start). It serves your JavaScript code to your phone.

  • Expo Go → YES: The computer must be on, connected to the same Wi-Fi, and running npx expo start. If you turn off the server, the app will show a red error screen ("Could not connect to development server").
  • Development Build → YES: Same as Expo Go. It needs the server to load the JS. This is the trade-off for having hot-reload and debugging tools.
  • Preview Build → NO: The JS is baked inside the APK. You can turn off your computer, go to a different city, and the app will open and work perfectly. Note: API calls to your backend (e.g., Firebase, Node.js server) will still require internet, but the app itself does not need your computer.
  • Production Build → NO: It is a completely standalone app, ready for users who will never have your computer.
Summary: If you are testing code actively, use the server. If you want to show the app to a friend, use a Preview build so you don't have to keep your laptop open.

The Golden Rule: Expo Go vs. Development Build

Purpose: To understand which tool to use during development.

Feature Expo Go (The Sandbox) Development Build (The Real App)
What is it? A universal app provided by Expo with built-in native libraries. Your own app, compiled by you, containing your icon, name, and required native libraries.
Can it be modified? No. Native code is fixed. You cannot add new native modules or change the icon. Yes. You control all native configuration via app.json.
Limitations Cannot test push notifications, app icons, splash screens, or third-party native libraries. No limitations. Behaves exactly like the final production version.
One-sentence summary Expo Go is for quick prototyping and learning. When you need to test real app icons, push notifications, or native libraries, you must switch to a Development Build.

1. Account Registration & Setup

Purpose: To create your developer identity and install the tools needed to communicate with Expo's servers.

  1. Create an Expo account: This is your identity on EAS. It links your builds, credentials, and app submissions together.
  2. Install EAS CLI: This is the command-line tool you will use for everything from building to submitting.
  3. Log in: Authenticates your terminal session so EAS knows who is requesting builds. 
# 1. Register at https://expo.dev/signup

# 2. Install the EAS CLI globally (purpose: enables the `eas` command)
npm install -g eas-cli

# 3. Verify the installation
eas --version

# 4. Log in to your Expo account (purpose: authenticate your machine)
eas login

# 5. Confirm your identity (purpose: ensures you are building under the correct account)
eas whoami

Troubleshooting Setup

  • eas: command not found: Your npm global bin directory isn't in your PATH. Use npx eas-cli instead, or reinstall Node.js.
  • Login fails / 2FA blocked: Try eas login --sso or set the EXPO_TOKEN environment variable.

2. Project Connection & Configuration

Purpose: To link your local codebase to a cloud project so EAS knows exactly what to compile and where to send the results.

  1. Initialize EAS project: Creates a unique projectId on Expo's servers and writes it into your app.json.
  2. Configure native identifiers: Tells the operating systems (Android/iOS) what your app is called internally. This cannot be changed after publishing. 
# Initialize the EAS project (purpose: links local code to the cloud)
eas init

# Generate the eas.json configuration file (purpose: defines build profiles)
eas build:configure

Next, ensure your app.json has the correct native identifiers:

  • android.package: Must be a unique reverse domain name (e.g., com.yourcompany.yourapp). Must be all lowercase.
  • ios.bundleIdentifier: Must match the Bundle ID registered in App Store Connect.

Understanding the eas.json Profiles

Purpose: To define different build types for different stages of testing.

Your eas.json defines how the app is built. Here is a typical configuration: 

{
  "cli": { "version": ">= 12.0.0" },
  "build": {
    "development": {
      "developmentClient": true,
      "distribution": "internal"
    },
    "preview": {
      "distribution": "internal",
      "android": { "buildType": "apk" }
    },
    "production": {}
  },
  "submit": { "production": {} }
}
  • development: Includes the Dev Client for debugging native code.
  • preview: Release-mode binary for internal QA. Android outputs an APK for direct installation.
  • production: Store-ready version. Android outputs an AAB (for Play Store), iOS outputs an IPA.

3. Building the App (Dev, Preview, Production)

Purpose: To generate installable binary files from your JavaScript code.

Development Build

Purpose: For daily development, hot-reloading, and testing native libraries. 

eas build --profile development --platform android
eas build --profile development --platform ios

After building, install the APK/IPA on your device. Then run npx expo start in your terminal to connect the app to your local dev server.

Preview Build (Internal Testing)

Purpose: Give testers a version close to production for functional acceptance. 

eas build --profile preview --platform all

Android produces an APK you can share directly. iOS requires registering tester device UDIDs via eas device:create first.

Production Build (Store Ready)

Purpose: Generate the final binary that Google Play and the App Store will accept. 

eas build --profile production --platform android
eas build --profile production --platform ios
Crucial Note: Android Production builds output an .aab (Android App Bundle) file. You cannot install an AAB directly on a phone. It must be uploaded to the Google Play Console. If you want to test a production build on your phone, use the preview profile.

If you encounter weird build errors, always try adding --clear-cache to the end of the command.

4. Web Deployment

Purpose: To export your app as a website and host it for browser testing. 

# 1. Export the static web files (creates a /dist folder)
npx expo export --platform web

# 2. Deploy to EAS Hosting
eas deploy

eas deploy will upload the dist folder and give you a public URL (e.g., https://your-app.expo.app).

Important app.json check: Ensure "web": { "output": "static" } is set in your app.json. If it is set to "server", EAS Hosting expects a Node.js server to be running and a simple static deploy will fail with a "generated" error.

5. Uploading to Google Play Store

Purpose: To create a developer account and publish your Android App Bundle (.aab) to the Play Store.

Step 5.1: Create a Google Play Developer Account

  1. Go to the Google Play Console and sign in with your Google account.
  2. Pay the one-time $25 registration fee.
  3. Complete identity verification (you may need to upload a government-issued ID).
  4. Choose your account type (Personal or Organization). Note: Personal accounts created after Nov 2023 must run a closed test with at least 12 testers for 14 days before applying for production access.

Step 5.2: Create the App in Play Console

  1. In the Play Console dashboard, click Create app.
  2. Fill in the App name (max 30 characters), Default language, and App/Game type.
  3. Complete the App content forms (Privacy Policy, Ads declaration, Content rating, Target audience, Data safety).

Step 5.3: Upload the Build (.aab)

Option A: Using EAS Submit (Automated)

eas submit --platform android --latest

This uploads your latest production .aab to the Internal Testing track. You need to configure a Google Service Account JSON first (EAS will prompt you).

Option B: Manual Upload

  1. Download the .aab file from your EAS build page.
  2. In Play Console, go to Test and release > Testing > Internal testing.
  3. Click Create new release.
  4. Upload the .aab, add release notes, and save.
  5. Once tested, promote the release to Production.

6. Uploading to Apple App Store

Purpose: To create an Apple Developer account and submit your iOS build (.ipa) to TestFlight and the App Store.

Step 6.1: Create an Apple Developer Account

  1. Go to the Apple Developer Portal and sign up.
  2. Pay the annual $99 fee (required for App Store submission).
  3. Accept the developer agreement.

Step 6.2: Create the App Record in App Store Connect

  1. Go to App Store Connect and sign in.
  2. Click Apps > + > New App.
  3. Fill in the Platform (iOS), App Name, Primary Language, Bundle ID (must match your app.json), and SKU.
  4. Click Create.

Step 6.3: Upload the Build (.ipa)

Option A: Using EAS Submit (Recommended)

eas submit --platform ios --latest

This uploads your .ipa to App Store Connect. The build will appear in TestFlight after 10-15 minutes of processing.

Option B: Manual Upload

  1. Download the .ipa from EAS.
  2. Use the Transporter app (Mac) or xcrun altool to upload the .ipa to App Store Connect.
  3. Once processed, it appears in TestFlight.

Step 6.4: Submit for Review

  1. In App Store Connect, go to your app > TestFlight.
  2. Select the build you uploaded.
  3. Go to the App Store tab, fill in all metadata (screenshots, description, keywords).
  4. Click Submit for Review.

7. Most Common Deployment Problems

Issue Cause Solution
Slug / projectId mismatch Project linked to EAS, but slug in app.json was changed. Restore original slug, or delete extra.eas.projectId and re-run eas init.
App icon has checkerboard on Android Adaptive icon adaptive-icon.png has a baked-in grey background, not true transparency. Ensure the foreground image is a true RGBA PNG with transparent background and enough padding.
Web deploy "generated" error web.output set to "server" but missing server runtime. Change app.json to "web": { "output": "static" } and redeploy.
Android "App not installed" Old version with different signature installed, or storage full. Uninstall the old app completely, then install the new APK.
iOS build fails: No Apple account No paid Apple Developer account. Must subscribe ($99/year) to build iOS apps.
