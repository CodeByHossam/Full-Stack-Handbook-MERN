Internet & Web Fundamentals

The vocabulary every MERN developer needs: how the internet and the web differ, how requests and responses travel, and the protocols, addresses, and security layers behind every page load.

Fundamentals HTTP & networking Web for developers

Internet vs web

The Internet is a global network of connected computers — the physical and logical infrastructure. The Web is just one service that runs on top of the Internet (websites and web applications). Many other services also use the Internet: email, online games, video calls, file transfer, and APIs.

Client and server

A client is usually your browser, a mobile app, or a desktop application. A server is a computer that provides services or data. Clients ask; servers answer.

Request and response

When you open example.com, the browser sends a request and the server sends back a response. Think of it as:

  • Client: "Give me this resource."
  • Server: "Here it is."

HTTP and HTTPS

HTTP (HyperText Transfer Protocol) defines how clients and servers communicate over the web. HTTPS is HTTP with encryption (TLS). With plain HTTP, data can be observed or intercepted more easily; with HTTPS, the communication is encrypted using TLS.

AspectHTTPHTTPS
What it isPlain-text request/response protocolHTTP inside a TLS-encrypted channel
Default port80443
On the wireReadable if interceptedCiphertext (unreadable without keys)
IntegrityNoneTampering is detected (MAC/AEAD)
AuthenticationNoneServer proves its identity with a certificate
Use whenLocal experiments onlyEverything in production
Key point

Always use HTTPS in production. It protects passwords, tokens, personal data, and API requests in transit.

Watch out

HTTPS does not make an insecure app secure: it does not fix application bugs, does not hide the domain name (SNI is usually visible), does not encrypt DNS lookups by default, and does not stop malware or phishing on the client. It secures the transport, not the application.

SSL vs TLS

SSL (Secure Sockets Layer) was the original protocol for encrypted connections. TLS (Transport Layer Security) is its modern successor. SSL 2.0/3.0 and TLS 1.0/1.1 are deprecated and insecure; today's connections use TLS 1.2 or 1.3.

SSL 2.0 / 3.0   (obsolete, insecure)
      ↓
TLS 1.0 / 1.1   (deprecated)
      ↓
TLS 1.2         (widely supported)
      ↓
TLS 1.3         (modern, faster)

People still say "SSL certificate" out of habit, even though the certificate is used with TLS. Technically, the protocol in use is TLS.

Encryption scrambles readable data (plaintext) into unreadable data (ciphertext); only a party with the correct key can decrypt it back to plaintext.

TLS certificates and the chain of trust

A TLS certificate is a digital ID card for a server. It binds a domain name to a public key and is signed by a Certificate Authority (CA) such as Let's Encrypt, DigiCert, or Sectigo. It proves the server really is example.com and not an impostor.

A certificate contains the domain it is valid for, the server's public key, the issuer (the signing CA), the subject, the validity period, and the CA's signature. It never contains the private key.

Certificates form a chain of trust: the browser trusts a root CA, that root signs an intermediate CA, and the intermediate signs the server certificate.

Root CA (in the browser's trust store)
   ↓ signs
Intermediate CA
   ↓ signs
example.com certificate

When the browser receives a certificate it checks the validity dates, that the domain matches, that it chains to a trusted CA, and that it has not been revoked (via CRL or OCSP). If any check fails, it shows a security warning.

Watch out

A self-signed certificate is signed by the server itself, not a trusted CA. Browsers warn because they cannot verify identity. It is fine for local development but must never be used in production. For real sites, use a free automated CA such as Let's Encrypt.

The TLS handshake

Before any HTTP data is sent, the client and server run a handshake to agree on encryption and establish shared session keys. In TLS 1.3 it takes a single round trip.

  1. ClientHello — the browser sends the TLS versions and cipher suites it supports, an elliptic-curve key share for ECDHE, a random value, and the SNI hostname.
  2. ServerHello — the server picks the version and cipher suite and returns its own ECDHE key share and random value.
  3. Encrypted server parameters — the server sends its certificate, a CertificateVerify signature proving it owns the private key, and a Finished message. Everything after ServerHello is encrypted.
  4. Client Finished — the browser verifies the certificate, derives the shared secret, and confirms. Encrypted HTTP can now flow.

Both sides compute the same secret using ECDHE (Elliptic Curve Diffie-Hellman Ephemeral) without ever sending it over the network. Because the keys are ephemeral (per session), a later compromise of the server's long-term key cannot decrypt past sessions — this property is forward secrecy.

FeatureTLS 1.2TLS 1.3
Round trips2 RTT (full handshake)1 RTT (full handshake)
Handshake encryptionSome messages in the clearMost encrypted after ServerHello
Cipher suitesMany, including weak onesOnly strong AEAD ciphers
Forward secrecyOptionalMandatory (ECDHE)
Removed legacy cryptoRSA key exchange, CBC, RC4, SHA-1All removed

TLS termination

TLS termination means the encryption ends at a proxy (typically Nginx) rather than at the application. Nginx decrypts incoming HTTPS and forwards a plain HTTP request to the app over the loopback interface.

Browser
   ↓ HTTPS (encrypted)
Nginx :443
   ↓ TLS decrypted, plain HTTP
Application 127.0.0.1:3000

This offloads the expensive crypto work to Nginx and lets the app handle ordinary HTTP. Because the Nginx-to-app hop never leaves the machine, plain HTTP there is acceptable. When the app runs on a different machine, Nginx can instead decrypt and re-encrypt (TLS re-encryption) to keep end-to-end protection.

Port 80 is usually kept only to redirect to 443: a request to http://example.com receives a 301 permanent redirect to the same path over https://.

Domain

A domain name such as google.com is a human-friendly label. Humans remember names; computers ultimately communicate using IP addresses. The domain is the name that gets translated into an IP address.

IP address

An IP address identifies a device or network endpoint. There are two common versions:

  • IPv4 — e.g. 142.250.x.x, 192.168.1.10
  • IPv6 — e.g. 2001:db8::1

For a deeper look at how IP and MAC addresses cooperate, see Networking Layers.

DNS

DNS (Domain Name System) translates a domain name into an IP address — like a phone book for the Internet.

google.com
   ↓
DNS
   ↓
IP address

You normally do not need to know every DNS server involved, but understand the purpose.

What happens when you enter a website

Typing https://example.com and pressing Enter triggers a fixed sequence:

1.  Browser parses the URL              (application)
2.  DNS resolves the hostname to an IP  (DNS, port 53)
3.  TCP connection to port 443          (transport)
4.  TLS handshake and cert check        (encryption)
5.  Browser sends the HTTP request      (encrypted by TLS)
6.  Server (or a proxy) processes it
7.  Server may query the database
8.  Server sends the HTTP response
9.  Browser receives and decrypts it
10. Browser renders the page

For the full layer-by-layer breakdown, see Web Request Flow.

DNS in more detail

Resolution usually walks a hierarchy: a resolver asks a root server, then the TLD server (for .com), then the domain's authoritative name server, and finally caches the answer for a TTL so later lookups are instant. Names exist because they are stable while IP addresses can change.

Browser
   ↓
DNS resolver
   ↓
DNS servers
   ↓
IP address
   ↓
Server

Common DNS record types:

  • A — maps a name to an IPv4 address (for example example.com → 203.0.113.10).
  • AAAA — maps a name to an IPv6 address.
  • CNAME — an alias that points one name to another.
  • NS — which name servers are authoritative for the domain.
  • TTL — how long a record may be cached before it is re-fetched.

Ports

One computer can run many network services at once. Ports identify the service endpoint. A port is a 16-bit number (0–65535); ports below 1024 are "privileged" system ports, and clients pick a random high port for each outgoing connection.

ServicePort
HTTP80
HTTPS443
SSH22
React / Vite (dev)5173
Express (dev)5000
MongoDB27017
Watch out

Only one process can listen on a given port. An EADDRINUSE "port already in use" error means another server (often a previous run) still holds it.

Localhost

localhost means "this same computer." For example, http://localhost:5000 connects the browser to a server running on your own machine.

Warning

On a phone, localhost means the phone itself — it does not automatically mean your development computer.

The loopback address 127.0.0.1

127.0.0.1 is the common IPv4 loopback address. In practice, localhost usually points to 127.0.0.1.

LAN, router, and ISP

  • LAN (Local Area Network): your computer, phone, printer, and router connected at home or work. A typical private IP looks like 192.168.1.20.
  • Router: connects your local network to other networks and the Internet.
  • ISP (Internet Service Provider): the company that provides your Internet connection.

Packets, TCP, and UDP

Data sent across networks is broken into packets. The receiving side reassembles and processes them.

Your request
     ↓
Packets
     ↓
Network
     ↓
Server

TCP provides reliable, ordered communication: data arrives, stays in order, and lost data can be retransmitted. HTTP traditionally runs over TCP, and HTTPS over TCP + TLS.

UDP is connectionless with less overhead. It is useful when speed/latency matters more than guaranteed delivery: streaming, gaming, and voice/video communication. Modern HTTP/3 uses QUIC, which runs over UDP.

AspectTCPUDP
ConnectionEstablished (handshake)None (connectionless)
ReliabilityOrdered, ACKs, retransmitsBest-effort, may drop/reorder
Speed / overheadSlower, more overheadFaster, less overhead
Typical useWeb, email, file transferStreaming, gaming, DNS, QUIC

HTTP methods

Each method states the intent of a request against a resource. GET is read-only ("safe") and should never change data; POST, PUT, PATCH, and DELETE change state. Knowing the intent is what keeps an API predictable.

A method is idempotent when repeating the same request produces the same result — this is what makes a request safe to retry after a timeout.

MethodPurposeExampleIdempotent?
GETRead dataGET /api/productsYes
POSTCreate / send dataPOST /api/productsNo
PUTReplace a resourcePUT /api/products/10Yes
PATCHPartially update a resourcePATCH /api/products/10No
DELETEDelete a resourceDELETE /api/products/10Yes
HEADLike GET but headers onlyHEAD /api/productsYes
OPTIONSDescribe allowed options (CORS preflight)OPTIONS /api/productsYes
Note

Methods and REST naming conventions are owned by REST API. This page only summarizes them.

A request can also contain data in the body:

POST /api/users

{
    "name": "Alice",
    "email": "alice@example.com"
}

In Express this is available as req.body.

When a reverse proxy such as Nginx forwards a request, it adds headers so the app can see the real client: X-Real-IP (the original client IP), X-Forwarded-For (the chain of proxy IPs), and X-Forwarded-Proto (the original scheme, http or https). Without them the app only sees the proxy's own address.

Watch out

req.body is empty unless body parsing is enabled — add app.use(express.json()) before your routes for JSON payloads.

HTTP request and response messages

Every HTTP exchange has the same shape: a start line, a set of headers, a blank line, then an optional body.

Request message:

GET /api/users HTTP/1.1
Host: example.com
Accept: application/json
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
Connection: keep-alive

Response message:

HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Content-Length: 1247
Set-Cookie: session=xyz789; HttpOnly; Secure; SameSite=Lax
Cache-Control: no-cache, no-store, must-revalidate
Server: nginx/1.24.0

{"users":[{"id":1,"name":"Alice"}]}
  • The start line is the method, path, and version for a request, or the version, status code, and reason for a response.
  • Headers are Name: value pairs (see the header table above).
  • A blank line separates the headers from the body.
  • The body carries the payload (JSON for a typical API) and may be absent.

JSON

JSON (JavaScript Object Notation) is the common format for APIs. React receives JSON; Express sends JSON.

{
    "name": "Laptop",
    "price": 1000
}
Watch out

JSON looks like a JavaScript object but is stricter: keys must use double quotes, and it allows no trailing commas or comments. Parse incoming text with JSON.parse() and serialize with JSON.stringify().

REST API

REST is a common style for designing HTTP APIs. The same resource is addressed with different methods:

GET    /api/products
GET    /api/products/10
POST   /api/products
PATCH  /api/products/10
DELETE /api/products/10

The design details (naming, filtering, pagination, versioning) are owned by REST API.

CORS and same-origin

CORS (Cross-Origin Resource Sharing) matters when the frontend and backend live at different origins. Example: frontend at http://localhost:5173 and backend at http://localhost:5000 are different origins. The browser may block certain cross-origin requests unless the server allows them.

app.use(
    cors({
        origin: "http://localhost:5173" // allow only this frontend to call the API
    })
);
Watch out

CORS is enforced by the browser, not the server — the server must send the allow headers. To send cookies cross-origin you also need credentials: true, and you cannot combine that with origin: "*".

An origin consists of protocol + host + port. So http://localhost:5173 and http://localhost:5000 are different origins because the ports differ.

CDN and cache

A CDN (Content Delivery Network) copies and caches content closer to users. A user in one region fetches an image from a nearby CDN node instead of a far-away server. This is useful for images, CSS, JavaScript, video, and static assets.

Caching stores data temporarily so it can be reused faster. The browser can reuse a cached image on the next visit, reducing network traffic.

TLS, firewall, reverse proxy, load balancer

TLS encrypts communication between client and server to protect passwords, tokens, personal data, and API requests.

Browser
   ⇅
Encrypted HTTPS connection
   ⇅

A firewall controls network traffic based on rules — for example, allow 443 HTTPS and block unwanted traffic. Servers often use cloud firewalls, OS firewalls, or cloud security groups. A port such as the app's 3000 is usually left unopened so only a proxy can reach the application.

Note

Where a service listens matters too: binding to 0.0.0.0 exposes it on all interfaces (reachable from other machines, if the firewall allows), while binding to 127.0.0.1 keeps it reachable only from the same machine — a defense even if the firewall is misconfigured.

A reverse proxy sits in front of your application. It can handle HTTPS, routing, compression, caching, static files, and load balancing.

WebSockets

Normal HTTP is request/response: the client asks, the server answers. A WebSocket is a persistent, two-way connection.

HTTP:      Client → Request   Server → Response
WebSocket: Client ⇄ Server

It is useful for chat, live notifications, real-time dashboards, and multiplayer games.

A WebSocket begins as a normal HTTP request asking to upgrade: the client sends Upgrade: websocket with Connection: Upgrade and a Sec-WebSocket-Key. If the server agrees it replies 101 Switching Protocols, and the connection becomes a bidirectional WebSocket.

GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13

Verifying HTTPS with curl and openssl

On the client side, what verifies a server certificate is the CA bundle — a file of trusted root CA public keys (for example /etc/ssl/certs/ca-certificates.crt). It is a list of trusted signers, not a list of websites. Verification is a chain check: the server sends its certificate, the client reads the issuer, looks that issuer up in its CA bundle, and uses the issuer's public key to verify the signature.

Inspect a live site's connection and certificate chain:

# Show the TLS version, cipher, and whether verification passed
curl -v https://example.com 2>&1 | head -30

# Inspect the certificate chain presented by the server
openssl s_client -connect example.com:443 -showcerts < /dev/null

Look for SSL certificate verify ok. from curl, or Verify return code: 0 (ok) from openssl — both mean the chain is trusted. For an internal server using a private CA, point curl at that CA explicitly:

curl --cacert /path/to/my-ca.crt https://internal.example.com
ErrorMeaning / fix
self-signed certificateThe cert is not signed by a trusted CA. Trust it with --cacert in dev; never disable verification in production.
unable to get local issuer certificateThe CA bundle is missing or incomplete — install ca-certificates.
certificate has expiredRenew the certificate.
hostname does not matchThe cert is for a different domain.
UNABLE_TO_VERIFY_LEAF_SIGNATURE (Node)Node cannot find the CA bundle — install ca-certificates or set NODE_EXTRA_CA_CERTS.
Watch out

Never use curl -k (or NODE_TLS_REJECT_UNAUTHORIZED=0) in production — it disables verification and silently accepts any certificate, including an attacker's. Server-side setup (obtaining a certificate, Let's Encrypt, configuring Nginx) belongs to Deploy on Linux (Nginx/PM2).

Quick recap

  • The Internet is the infrastructure; the Web is one service on top of it.
  • A client sends a request; a server sends a response over HTTP/HTTPS.
  • A URL carries protocol, domain, path, and query string.
  • DNS turns domain names into IP addresses; ports identify services.
  • Data travels as packets over TCP (reliable) or UDP (fast, best-effort).
  • HTTP methods and status codes describe intent and outcome.
  • Cookies, sessions, and JWTs carry identity; CORS governs cross-origin access.
  • CDNs and caches speed up delivery; TLS, firewalls, reverse proxies, and load balancers add safety and scale.
  • HTTPS is HTTP over TLS; "SSL" is the deprecated predecessor.
  • TLS is hybrid: an asymmetric ECDHE handshake, then fast symmetric encryption (AES/ChaCha20).
  • Certificates chain from a root CA through an intermediate to the server; verify them with curl or openssl.
  • When something fails, ask: DNS? network? CORS? wrong port? server down? auth? wrong endpoint? database? 500? frontend?
