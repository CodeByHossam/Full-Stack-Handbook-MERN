Deploy a MERN App on a Linux Server

The complete production deployment path: SSH, Git, Node.js, PM2, Nginx, DNS, HTTPS, and the firewall — from a fresh server to a live application.

Key point

SSH is used by you to control the server. Nginx is used to handle requests from users. They are different tools serving different people.

SSH access

SSH (Secure Shell) lets you remotely control a Linux server from your computer:

ssh username@SERVER_IP
Windows / macOS PC

        | SSH
        v
   Linux Server
        |
        v
   Linux Terminal

Once connected, commands such as ls, cd /var/www, and node -v are executed on the Linux server, not your computer.

Key point

SSH does not run your application by itself. It gives you secure access to control the server. Think of SSH as the remote control for the server.

When you connect you interact with a shell, usually Bash. You type a command, Bash interprets it, and Linux runs the corresponding program:

Log in with a key instead of a password

Password login works, but production servers should use SSH keys: the public key is installed on the server and the private key never leaves your computer. Generate a pair, then copy the public key to the server:

ssh-keygen -t ed25519 -C "you@example.com"   # create a private + public key pair
ssh-copy-id username@SERVER_IP               # install the public key on the server

The public key ends up in ~/.ssh/authorized_keys on the server; only a matching private key can log in afterwards. The key handshake is explained in depth on the SSH into Docker page.

VPS vs shared hosting

A MERN backend needs a machine where you can install Node.js and keep a process running continuously. That requirement decides the hosting type before any command is typed.

OptionWhat you getCan it run MERN?
VPSFull root access, your own IP, install anything, long-running processes.Yes — install Node, Git, PM2, Nginx, and a database.
Shared hostingNo root, no shell, serves static files and PHP only.No — it will not keep a Node process alive.

A Hostinger VPS, a DigitalOcean droplet, and any cloud VM are all the same thing for deployment purposes: a remote Linux machine with an IP, a username, and SSH access. Everything on this page applies to all of them.

Server preparation

A common choice is Ubuntu Linux. After creating the server you receive a public IP, a username, and SSH access.

# connect to the server
ssh username@123.123.123.123

# update the package list, then upgrade installed packages
sudo apt update
sudo apt upgrade

# install Git
sudo apt install git

# verify Git
git --version

Install a supported Node.js LTS version compatible with the version you used during development. The default Ubuntu repository often ships an old Node, so add the NodeSource repository to get a current release:

# add the NodeSource repository, then install Node.js and npm
curl -fsSL https://deb.nodesource.com/setup_20.x | sudo -E bash -
sudo apt install -y nodejs

# verify the runtime and package manager
node -v
npm -v
Watch out

Installing nodejs straight from the default repository can give a version older than the one you built locally. Prefer NodeSource and match the major version you developed against.

Your Express application typically listens internally on 127.0.0.1:5000:

const PORT = process.env.PORT || 5000;

app.listen(PORT, () => {
    console.log(`Server running on port ${PORT}`);
});

Application directory

A common location for web applications is /var/www:

cd /var/www   # standard web-root location on Ubuntu

Clone the project

Pull the repository straight from GitHub onto the server. The trailing argument names the folder that is created.

git clone YOUR_REPOSITORY_URL notes-app   # clone into ./notes-app

You now have a project directory with a client and a server:

notes-app/
+-- client/
+-- server/

Install backend dependencies

Install exactly the versions recorded in package-lock.json. This makes every deploy reproducible, so the server matches what you tested locally.

cd /var/www/notes-app/server
npm ci   # clean, lockfile-exact install

npm ci installs exactly the versions from package-lock.json, which is what you want in production. If there is no lock file, fall back to npm install.

Create the production .env

Inside /var/www/notes-app/server create the environment file:

nano .env
PORT=5000
MONGO_URI=your-production-mongodb-connection
JWT_SECRET=your-production-secret
NODE_ENV=production

Never hard-code secrets in your source code. Read them through process.env instead:

// bad
mongoose.connect("mongodb+srv://username:password@...");

// good
mongoose.connect(process.env.MONGO_URI);
Common mistake

The .env file must not be committed to Git. It lives only on the server and contains the production database credentials and secrets.

Restrict the file so only the owner can read it, since it holds production secrets:

chmod 600 .env   # owner read/write only; nobody else

Test Node before PM2

Before adding PM2 or Nginx, make sure the backend works on its own:

node app.js

You should see output similar to:

MongoDB connected
Server running on port 5000

Test it from the server itself, then stop it with Ctrl + C:

curl http://127.0.0.1:5000
Key point

If Node does not work directly, do not troubleshoot PM2 or Nginx yet. The correct order is: Node works, then PM2, then Nginx.

PM2: keep the backend alive

PM2 is a process manager for Node.js. Without it, closing your SSH session can stop your application:

SSH → node app.js → Node running → SSH closes → application may stop

With PM2, the process runs in the background and is supervised:

PM2 → Node.js → Express → running in the background

Install it globally and check the version:

sudo npm install -g pm2
pm2 -v

Start the backend with a clear name:

cd /var/www/notes-app/server
pm2 start app.js --name notes-app-api
pm2 status

You should see the process listed as online.

Important PM2 commands

Once your app runs under PM2, these are the commands you use to inspect, restart, and manage it.

CommandPurpose
pm2 listShow all managed applications.
pm2 logs notes-app-apiShow the application logs.
pm2 restart notes-app-apiRestart the application.
pm2 stop notes-app-apiStop the application.
pm2 delete notes-app-apiRemove it from PM2.

Start PM2 automatically on reboot

You want the Node application to come back after the server reboots:

pm2 startup

PM2 prints a command — run exactly the command it gives you. Then save the current process list:

Why not npm run dev in production?

npm run dev is built for development. It provides hot reload, development tooling, debugging features, and a development server. Production should serve the built output instead:

React → npm run build → dist/ → Nginx
PM2 → Node → Express

And in production, NODE_ENV=production lets Express and libraries switch to optimized behavior.

Install Nginx

Nginx is a web server and reverse proxy — the front door of the server. It receives public requests and decides where they go.

Without Nginx:
Browser → SERVER_IP:5000 → Node

With Nginx:
Browser → https://example.com → Nginx → Node :5000
sudo apt update
sudo apt install nginx

# check, start, and enable at boot
sudo systemctl status nginx
sudo systemctl start nginx
sudo systemctl enable nginx

Nginx can serve React static files, forward API requests to Express, handle HTTP and HTTPS, work with SSL certificates, hide the internal Node port, and route URLs to different services.

Build the React application

Compile the React source into static files. Vite writes them to dist/, which is what Nginx will serve.

cd /var/www/notes-app/client
npm ci          # install exact dependencies
npm run build   # produce dist/

This produces the production frontend:

client/
+-- dist/
     +-- index.html
     +-- assets/

Nginx serves files from /var/www/notes-app/client/dist, and the request flow becomes:

Browser → Nginx → React dist/ → index.html → React application

Nginx configuration: React + /api proxy

Create a site file:

sudo nano /etc/nginx/sites-available/notes-app
server {
    listen 80;                                  # accept HTTP on port 80

    server_name example.com www.example.com;    # domains this block serves

    root /var/www/notes-app/client/dist;        # where the React build lives

    index index.html;

    location / {
        try_files $uri $uri/ /index.html;       # serve real files, else fall back to React Router
    }

    location /api/ {
        proxy_pass http://127.0.0.1:5000;       # forward API calls to Node

        proxy_http_version 1.1;                 # enable keep-alive

        proxy_set_header Host $host;            # pass the original host
        proxy_set_header X-Real-IP $remote_addr;              # real client IP
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;           # http or https
    }
}

Replace example.com with your real domain. Two parts deserve special attention:

Understanding root

root /var/www/notes-app/client/dist; tells Nginx where the React production files live. A request for https://example.com is served from /var/www/notes-app/client/dist/index.html.

Understanding location /

The block:

location / {
    try_files $uri $uri/ /index.html;
}

is essential for React Router. If a user directly opens https://example.com/notes, Nginx would look for a physical /notes file that does not exist. try_files falls back to index.html, and React Router takes over the route.

Understanding location /api/

This block is the reverse proxy: any request whose path starts with /api/ is forwarded to the Node process on 127.0.0.1:5000 instead of being served from disk. The trailing slash keeps the prefix intact, so /api/notes reaches the backend as http://127.0.0.1:5000/api/notes.

location /api/ {
    proxy_pass http://127.0.0.1:5000;
}

Requests under /api/* are forwarded to Node on port 5000. For example, https://example.com/api/notes is forwarded internally to http://127.0.0.1:5000/api/notes.

Browser
   |
   v
https://example.com/api/notes
   |
   v
Nginx
   |
   v
127.0.0.1:5000
   |
   v
 Express → Controller → Mongoose → MongoDB

WebSocket support

If the backend uses WebSockets (for example Socket.IO), the proxy must forward the connection upgrade rather than terminate it. Add these two headers inside the location /api/ block:

proxy_set_header Upgrade $http_upgrade;
proxy_set_header Connection "upgrade";

Without them the initial HTTP request succeeds but the socket never upgrades, so live features silently stay disconnected.

Enable the site and test the configuration

Create a symbolic link to enable the site, disable the default site, then test and reload:

sudo ln -s /etc/nginx/sites-available/notes-app /etc/nginx/sites-enabled/notes-app
sudo rm /etc/nginx/sites-enabled/default

# always test before reloading
sudo nginx -t

# apply the configuration
sudo systemctl reload nginx

If the test succeeds you will see syntax is ok and test is successful.

Warning

Never reload Nginx blindly. Always run sudo nginx -t first — a broken configuration can take the site offline.

Domain and DNS

DNS connects your domain name to the server IP:

example.com
     |
     v
    DNS
     |
     v
 SERVER_IP

Usually you create an A record for the apex domain and one for www:

Type: A    Name: @      Value: SERVER_IP
Type: A    Name: www    Value: SERVER_IP

DNS changes can take some time to propagate.

HTTPS with Certbot

HTTP sends data in plain text; HTTPS encrypts communication between the browser and Nginx. In production, HTTPS should normally be used.

Let's Encrypt provides free certificates, and Certbot configures Nginx automatically:

sudo apt install certbot python3-certbot-nginx
sudo certbot --nginx -d example.com -d www.example.com

After HTTPS is configured, the flow becomes:

Browser
   |
   | HTTPS :443
   v
Nginx
   |
   v
Node :5000

Certbot also configures automatic renewal, so the certificate stays valid without manual work. Verify the renewal path with a dry run, which does not touch the live certificate:

sudo certbot renew --dry-run
Common mistake

If the request fails with Challenge failed for domain, the usual causes are: DNS is not pointing at the server, port 80 or 443 is blocked, or the domain is not publicly reachable. Certbot must complete an HTTP challenge before it can issue the certificate.

Firewall (UFW)

A firewall controls which network connections may reach the server. The common public ports are 22 (SSH), 80 (HTTP), and 443 (HTTPS). Node on port 5000 does not need to be publicly accessible because Nginx proxies to it internally.

sudo ufw status
sudo ufw allow OpenSSH
sudo ufw allow 'Nginx Full'
sudo ufw enable
Warning

Be careful with SSH. If you enable the firewall without allowing SSH first, you can lock yourself out of the server.

Updating the application later

After the first deployment you do not repeat the entire process. The typical update flow is:

Modify locally → Test locally → git push
      → SSH into server → git pull
      → Install dependencies if needed
      → Build React → Restart Node

On the server:

cd /var/www/notes-app
git pull

Update the backend

Pull the new backend code, refresh dependencies, then restart the PM2 process so the running server picks up the changes. The restart is required — PM2 keeps the old process in memory until it is told to reload.

cd /var/www/notes-app/server
npm ci
pm2 restart notes-app-api

If you changed .env, restart the process so the new values take effect:

pm2 restart notes-app-api

Update the frontend

Rebuild the React source into fresh dist/ files. Nginx serves whatever is in that folder, so a rebuild is enough — frontend-only changes never require restarting Nginx.

cd /var/www/notes-app/client
npm ci
npm run build

Nginx serves the newly generated dist/ files automatically — you do not need to restart Nginx just because React files changed.

If the Nginx configuration changes

After editing the site file, always test and reload:

sudo nginx -t
sudo systemctl reload nginx

Getting files to the server

Git is the default for backend code, but other methods are useful for static builds and one-off files. Pick based on the deployment model, not habit.

Git pull is the standard for bare-metal backends — clone once, then git pull and restart. It is covered in the Git workflow and Updating the application sections above.

rsync / SCP

Command-line copy over SSH, best for sending the built React dist/ directory:

# simple recursive copy — sends everything
scp -r ./dist/* root@SERVER_IP:/var/www/frontend/

# incremental sync — only changed files, removes stale server files
rsync -avz --delete ./dist/ root@SERVER_IP:/var/www/frontend/

scp copies everything each time; rsync transfers only what changed, which is much faster for large builds. The flags -avz mean archive, verbose, and compression; --delete removes files on the server that are no longer present locally.

SFTP with a GUI client

A graphical client such as FileZilla can drag and drop files over SFTP (protocol SFTP, host = server IP, port 22, user and key or password). It is convenient for a single static site, but it keeps no history or rollback, so avoid it for real backends.

CI/CD

Automation is how teams deploy: every git push to the main branch triggers a pipeline that builds and ships the change, so nobody touches the server by hand. Add it once the manual flow is understood.

Which method should I use?

Your situationUse thisWhy
Learning, personal project, VPSGit pullSimple, versioned, teaches core skills.
Static React build to a VPSrsync / SCPFast and simple for static output.
Team, production, real usersCI/CDAutomated, auditable, rollback-friendly.
Shared hosting, no SSHSFTP (FileZilla)The only available option.
Quick one-off file fixSCPFaster than Git for a single file.
Common mistake

Anti-patterns to avoid: editing code directly on the server with nano (the server becomes the source of truth and drifts from Git), uploading via SFTP into production (no history or rollback), and committing node_modules/ or .env (huge repos, leaked secrets).

Troubleshooting by request path

Always troubleshoot according to the request path — frontend, then API, then database.

The website does not open

When nothing loads at all, walk the request path from the outside in: confirm the domain resolves (DNS), that the firewall allows 80 and 443, and finally that Nginx is running with a valid config. The commands below check the last two.

Domain → DNS → Server → Firewall → Nginx
sudo systemctl status nginx
sudo nginx -t
sudo ufw status

Frontend works but the API does not

If the page loads but data calls fail, the break is between Nginx and Node. First confirm PM2 is keeping the backend online, check its logs for errors, then bypass Nginx entirely with a direct curl to the Node port.

A 502 Bad Gateway is Nginx reporting exactly this: it reached the proxy target but Node was not listening. Check pm2 status and that the port in proxy_pass matches the port the backend uses.

Browser → Nginx → Node

First check PM2, then the logs, then test Node directly:

pm2 status
pm2 logs notes-app-api
curl http://127.0.0.1:5000

If Node works directly but the API through the domain does not, the problem is in Nginx.

API works but the database does not

If the API responds but returns empty or error results, the backend is reachable and the fault is in the data layer. Verify the connection string, credentials and (for Atlas) the network access list before reading the process logs.

Node → Mongoose → MongoDB

Check the MONGO_URI, database credentials, MongoDB Atlas network access, the database server status if MongoDB runs locally, the .env, and the logs:

pm2 logs notes-app-api

Deployment FAQ

Do I need a VPN to host a site?

No. A VPN hides or changes your IP; a VPS is the server you host on. The names are similar but the concepts are unrelated.

I uploaded the React build — why is the backend not working?

Static hosting serves the frontend only. Running Express needs a VPS with Node.js and a process manager such as PM2, not just uploaded files.

My new VPS looks empty — is that normal?

Yes. A fresh VPS ships with no application. You SSH in, install Node and Git, clone the repository, build React, and start the backend under PM2.

How do I know the app is live?

Visit the server IP first, then the domain once DNS propagates. With Nginx and Certbot configured, open https://yourdomain.com.

Why am I getting a 502 Bad Gateway?

Nginx cannot reach Node. Check pm2 status and pm2 logs, and confirm the backend listens on the same port the proxy targets.

Install MySQL on the server

MERN stores data in MongoDB, but some projects also run a SQL database. On Ubuntu, install MySQL Server and secure it:

sudo apt update
sudo apt install -y mysql-server     # install the database server

sudo mysql_secure_installation       # set the root password, remove insecure defaults

sudo systemctl start mysql           # start it now
sudo systemctl enable mysql          # start it automatically on boot

After these steps the MySQL service runs on 127.0.0.1:3306 by default and is not exposed publicly. This section covers installing and running the server only — writing queries, schemas, and connecting from Node belong to the database pages.

Key point

SSH controls the server, Git moves your source code, Node runs your backend JavaScript, Express runs the API, PM2 keeps Node alive, Nginx routes web traffic, dist/ is the production frontend, MongoDB stores data, DNS connects the domain, HTTPS secures the browser connection, and UFW controls network access.

Quick recap

  • Nginx is the front door; Node stays internal.
  • SSH controls the server; Git moves the code.
  • Test Node directly before adding PM2 or Nginx.
  • PM2 keeps the backend alive and restarts it on reboot.
  • Keep secrets in a server-only .env.
  • Build React to dist/ and serve it with Nginx.
  • Proxy /api to Node and use try_files for React Router.
  • Always run nginx -t before reloading.
  • Point DNS at the server and enable HTTPS with Certbot.
  • Allow SSH in the firewall before enabling it.
  • Update with git pull, rebuild, and restart.
  • Choose a VPS — shared hosting cannot keep Node running.
  • Move code with Git; send static builds with rsync or SCP.
  • Match the setup to the project: API-only, frontend-only, or full MERN.
