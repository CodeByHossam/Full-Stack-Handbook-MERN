Docker & Deployment

Containerize a MERN stack with Docker and Compose, then ship it with the deployment concepts — builds, environment variables, CORS, HTTPS, Nginx, PM2, CI/CD, MongoDB Atlas, and a VPS walkthrough.

Deployment Docker Production

Why containerize a MERN app?

A MERN application has three moving parts:

  • React frontend — runs in the browser, but is built with Node.js tooling (Vite).
  • Node.js + Express backend — runs on a server and exposes a REST API.
  • MongoDB — the database that stores your data.

Without containers, each part must be installed and configured on every machine. Different Node versions, missing libraries, or different configuration cause the classic "works on my machine" problem. Containerization packages each part — code, runtime, dependencies, and config — into isolated, portable units. The same container runs identically on your laptop, a teammate's laptop, a CI pipeline, and a VPS.

Traditional MERN (everything on the host OS)

Computer
 ├── OS (Linux / macOS / Windows)
 ├── Node.js v20        must match everywhere
 ├── npm packages       installed per project
 ├── MongoDB            installed as a system service
 ├── React (Vite dev or dist/)
 └── Express backend    started with npm start


Dockerized MERN (each part is a container)

Computer
 ├── Host OS
 └── Docker Engine
      ├── Container: frontend  (Nginx + built React)
      ├── Container: backend   (Node.js 20 + Express)
      └── Container: mongo     (MongoDB server)
Key benefit

You can start the entire stack — frontend, backend, database — with a single command: docker compose up. No installing Node, npm, or MongoDB by hand.

Image vs container

These two terms are the foundation of everything else:

  • Docker image — a read-only blueprint/template built from a Dockerfile.
  • Docker container — a running instance of an image. You can run many containers from one image.
  • Base image — the starting point. For MERN you typically use node:20-alpine, nginx:alpine, and mongo:7.
Dockerfile
    ↓ build
Image
    ↓ run
Container
    ↓
Running application (Node / Nginx / MongoDB)
Note

Official images such as node, nginx, and mongo are maintained by Docker and the community. A Node image is Linux plus Node — you never add a separate Linux base.

Containers vs virtual machines

A virtual machine runs a full guest operating system on a hypervisor — heavy (gigabytes) and slow to boot. A container shares the host kernel and only packages the application plus its dependencies — small (megabytes) and fast to start.

FeatureVirtual machineDocker container
Guest OSYes — full OS per VMNo — shares host kernel
SizeGigabytesMegabytes
StartupMinutesSeconds or less
IsolationStrong (hardware level)Good (process level)
Resource usageHighLow
Typical useDifferent OSes, strong isolationMicroservices, packaging, CI/CD

Containers are not small VMs — they are isolated processes that share the host kernel.

Dockerfile basics (backend example)

A Dockerfile is a text file with instructions that build an image. The common instructions for a MERN backend are:

InstructionMeaning
FROMSets the base image.
WORKDIRSets the working directory inside the container.
COPYCopies files from your machine into the image.
RUNExecutes a command during the build (for example npm install).
EXPOSEDocuments which port the container listens on (it does not publish it).
CMDThe command that runs when the container starts.
ENVSets environment variables inside the image.

A complete backend Dockerfile at server/Dockerfile:

FROM node:20-alpine        # base image: Alpine Linux + Node 20

WORKDIR /app               # all following commands run here

COPY package*.json ./      # copy manifests first so npm install is cached

RUN npm install

COPY . .

EXPOSE 5000                # documents the port; it does not publish it

CMD ["npm", "start"]
  • FROM node:20-alpine — start from Alpine Linux + Node.js 20.
  • WORKDIR /app — all following commands run inside /app.
  • COPY package*.json ./ — copy the manifests first so Docker caches the dependency layer.
  • RUN npm install — install Express, Mongoose, dotenv, and the rest inside the image.
  • COPY . . — copy the remaining backend source.
  • EXPOSE 5000 — documents the container port.
  • CMD ["npm", "start"] — start the Node server when the container runs.

One Dockerfile, two targets (dev and prod)

A single Dockerfile can define a shared base plus a development target (with dev dependencies such as Nodemon) and a production target (production dependencies only). Compose selects the target with build.target.

FROM node:20-alpine AS base
WORKDIR /app
COPY package*.json ./

FROM base AS development
RUN npm ci
COPY . .
EXPOSE 5000
USER node
CMD ["npm", "run", "dev"]

FROM base AS production
RUN npm ci --omit=dev
COPY . .
EXPOSE 5000
USER node
CMD ["node", "server.js"]

Two small choices matter here:

  • USER node runs the process as the unprivileged node user built into the image instead of root, so a compromised process has fewer privileges.
  • CMD ["node", "server.js"] uses exec form. The shell form (CMD node server.js) wraps the process in /bin/sh, which does not forward SIGTERM and breaks graceful shutdown.
Key point

Use npm ci rather than npm install inside an image. It requires the lockfile, installs the exact locked versions, and is faster and reproducible.

Multi-stage build (React frontend)

React is compiled into static files. A multi-stage Dockerfile uses one stage to build and a second stage to serve — the final image contains only Nginx and the built files, not the whole toolchain.

Stage 1 (build):  node:20-alpine
      npm install → npm run build → dist/

Stage 2 (serve):  nginx:alpine
      COPY --from=build /app/dist → /usr/share/nginx/html
      final image: Nginx + static React

client/Dockerfile:

# ---- Stage 1: Build the React app ----
FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
RUN npm run build

# ---- Stage 2: Serve with Nginx ----
FROM nginx:alpine
COPY --from=build /app/dist /usr/share/nginx/html
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
Note

There are two valid ways to serve the built React app: Express can serve the dist/ files, or Nginx can. Nginx is the standard production choice because it is faster for static assets, handles caching and SSL, and sits in front as a reverse proxy.

Nginx config: SPA fallback and API proxy

The built React app is a single-page app, so Nginx must send unknown routes to index.html. The same config can proxy /api/ to the backend so the browser stays on one origin.

server {
    listen 80;
    server_name _;

    root /usr/share/nginx/html;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;   # SPA fallback
    }

    location /api/ {
        proxy_pass http://backend:5000/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

Copy it into the image in the serve stage with COPY nginx.conf /etc/nginx/conf.d/default.conf.

Passing the API URL at build time

Vite bakes VITE_* values into the bundle during npm run build, not at container start, so an env var set in Compose is ignored. If the frontend must know an absolute API URL, declare a build argument in the Dockerfile and pass it from Compose:

# inside the build stage, before npm run build
ARG VITE_API_URL
ENV VITE_API_URL=$VITE_API_URL
RUN npm run build

The relative-URL approach (fetch("/api/users")) avoids the build argument entirely and is the recommended production choice — see Environment variables.

Build, run, and manage containers

Once a Dockerfile exists, build an image and run it:

# build an image from the Dockerfile in the current folder
docker build -t my-backend .

# run a container, mapping host port 5000 to container port 5000
docker run -p 5000:5000 my-backend

Day-to-day lifecycle commands:

CommandWhat it does

docker psList running containers.
docker ps -aList all containers, including stopped ones.
docker start <container>Start a stopped container.
docker stop <container>Stop a running container (keeps it).

Note

Stop, remove, and image removal are three different actions: docker stop pauses a container but keeps it, docker rm deletes a stopped container, and docker rmi deletes the image.

Port mapping

The -p flag uses the format HOST_PORT:CONTAINER_PORT:

docker run -p 5000:5000 my-backend   # HOST_PORT:CONTAINER_PORT

The first number is the port on your computer or server; the second is the port inside the container. Only ports you explicitly map are reachable from outside Docker.

Warning

Ports must be published when the container is created. You cannot add -p to a container that is already running.

Volumes and persistence

Containers are disposable. When you delete a MongoDB container its data would be lost. A volume is a directory that lives outside the container and survives even after the container is removed. MongoDB stores its databases in /data/db, so that is where we mount the volume.

volumes:
  - mongo_data:/data/db   # named volume : path inside the container
MongoDB container
      ↓
   /data/db          inside container (ephemeral)
      ↓
mongo_data volume    on host disk (persistent)

Even after docker compose down the volume stays, so the data is safe. To delete the data you must explicitly run docker compose down -v.

Named, bind, and anonymous volumes

Docker has three ways to attach storage, and they behave differently:

TypeSyntaxHost locationManaged by
Namedmongo-data:/data/db/var/lib/docker/volumes/mongo-data/_data/Docker
Bind./local-folder:/data/dbExactly the path you wroteYou
Anonymous/data/dbRandom hash directoryDocker, hard to find
  • Named volumes are the default for databases — Docker manages the location and they are easy to back up and reuse.
  • Bind mounts are best for source code in development (hot reload) because you control the exact host path.
  • Anonymous volumes have no name, are hard to locate, and are easily orphaned — prefer a named volume instead.

Remember the two-part rule from the previous section: the top-level volumes: key registers a volume, and the entry inside a service mounts it.

Backing up and restoring MongoDB

Use the logical dump tools rather than copying the raw volume directory; the internal .wt files are only safe to copy while MongoDB is stopped.

# backup: dump inside the container, then copy the archive to the host
docker exec mern-mongodb mongodump --db=mydatabase --archive=/tmp/backup.gz --gzip
docker cp mern-mongodb:/tmp/backup.gz ./backup-$(date +%F).gz

# restore: copy the archive back, then mongorestore (--drop replaces collections)
docker cp ./backup.gz mern-mongodb:/tmp/backup.gz
docker exec mern-mongodb mongorestore --archive=/tmp/backup.gz --gzip --drop
Watch out

Never edit or delete files inside /var/lib/docker/volumes/.../_data while MongoDB is running — you will corrupt the database. On macOS and Windows the volume lives inside the Docker Desktop VM and is not directly browsable; use docker volume inspect and docker exec instead.

The .dockerignore file

Like .gitignore, a .dockerignore keeps unwanted files out of the build context — which keeps images small and prevents secrets from leaking in.

Place one in the project root and also inside client/ and server/. In particular, never copy .env or node_modules into an image. Ignoring node_modules means the host's dependencies are not sent into the build context; the container installs its own with npm ci. Keep package-lock.json out of this file — npm ci needs it.

Docker Compose for the MERN stack

Compose defines and runs all services together. Instead of many docker run commands, you write one docker-compose.yml. Key terms: a service is a container definition, a network lets services talk by name, and a volume persists data.

services:
  frontend:
    build: ./client          # build from client/Dockerfile
    ports:
      - "80:80"              # host 80 to container 80
    depends_on:
      - backend

  backend:
    build: ./server          # build from server/Dockerfile
    ports:
      - "5000:5000"
    environment:
      MONGO_URI: mongodb://mongo:27017/mydatabase
      NODE_ENV: production
    depends_on:
      - mongo

  mongo:
    image: mongo:7           # official image, no Dockerfile needed
    volumes:
      - mongo_data:/data/db  # persist MongoDB data

volumes:
  mongo_data:

There is no Dockerfile for MongoDB because the official mongo:7 image already contains everything required.

Warning

Inside the backend container, mongo is the service name. Docker's internal DNS resolves it to the MongoDB container. Using mongodb://localhost:27017 would look inside the backend container and fail. Always use mongodb://mongo:27017.

Top-level keys

A Compose file is built from a few top-level keys:

KeyPurpose
services:One entry per container: image or build, ports, env, volumes, networks.
volumes:Declares named volumes used by services.
networks:Declares custom networks used by services.
secrets: (advanced)Declares secret files for production.
configs: (advanced)Declares config files mounted into services.
Golden rule

Top-level volumes: and networks: are declarations; the matching lines inside a service are usages. The names must match exactly.

Two optional per-service keys are worth knowing:

  • container_name fixes the container name (otherwise Compose generates <project>-<service>-1), which makes docker exec and scripts predictable.
  • restart: unless-stopped restarts the container after a crash or host reboot unless you stopped it on purpose. See Startup order and restart policies.

Injecting environment variables with Compose

Compose can supply variables to a service two ways. Both inject at container start; they differ in where the values live.

OptionProsWhen to choose
environment: (inline)Visible next to the service; convenient for a few values or per-service overrides.Simple, non-sensitive values and intentional overrides.
env_file:Keeps many settings out of YAML; can be reused and easily gitignored.A larger set of runtime values.

If the same key appears in both, environment: wins. That lets a file hold shared defaults while YAML overrides one value:

env_file:
  - ./server/.env
environment:
  - PORT=4000        # overrides PORT from the file; other file keys remain

Compose also reads a file named .env sitting next to docker-compose.yml. Values there are substituted on the host with ${VAR} before the config is sent, so the container only sees the final value:

services:
  mongo:
    environment:
      - MONGO_INITDB_ROOT_PASSWORD=${MONGO_ROOT_PASSWORD}
  frontend:
    build:
      args:
        - VITE_API_URL=${VITE_API_URL}

That project .env is for Compose substitution (and for the Vite build arg) — it is not injected into every container automatically.

Warning

An env file is not a secrets manager. Add it to .gitignore, keep it out of the build context with .dockerignore, set chmod 600 on the server, and use Docker secrets or a vault for serious production secrets.

Compose commands

These are the commands you run day to day to control the whole stack defined in docker-compose.yml — starting, rebuilding, inspecting logs, and tearing down.

# start all services
docker compose up

# start in the background
docker compose up -d

# rebuild images, then start
docker compose up -d --build

# list containers
docker compose ps

# follow logs
docker compose logs -f

# restart services
docker compose restart

# stop and remove containers and networks (keeps volumes)
docker compose down

# also remove volumes (deletes MongoDB data)
docker compose down -v
Common mistake

docker compose down -v removes volumes and therefore deletes all MongoDB data. Use it only when you truly want a clean database.

Startup order and restart policies

depends_on controls start order, not readiness. Compose starts the dependency first, but it does not wait until that dependency is ready to accept connections — so Express can still start before MongoDB is listening.

ScenarioDoes depends_on help?
MongoDB container must exist before Express startsPartly — the container is running, but may not accept connections yet.
Express must be ready before the first requestNo — handle retries in the application.

The robust fix is to retry the database connection in the app, so it survives transient failures at any time, not just at startup:

async function connectWithRetry(retries = 10, delayMs = 3000) {
    for (let i = 1; i <= retries; i++) {
        try {
            await mongoose.connect(process.env.MONGO_URI);
            console.log("MongoDB connected");
            return;
        } catch (err) {
            console.log(`Mongo connect attempt ${i} failed, retrying in ${delayMs}ms`);
            await new Promise((r) => setTimeout(r, delayMs));
        }
    }
    throw new Error("Could not connect to MongoDB");
}

Restart policies

The restart: key decides what happens when a container exits:

ValueBehavior
no (default)Never restart automatically.
alwaysAlways restart, even after a manual stop.
on-failureRestart only when the exit code is not 0.
unless-stoppedRestart unless you explicitly stopped it — the recommended default.

Development bind mounts and hot reload

In development you want host source edits to reach the running container. Mount the source as a bind mount and let a watcher (Nodemon) restart the process on change:

services:
  backend:
    build:
      context: ./server
      target: development
    volumes:
      - ./server:/app        # bind mount: host source -> container /app
      - /app/node_modules    # anonymous volume: keep the image's dependencies
    command: npm run dev     # nodemon watches and restarts on change

The second mount is the subtle part. The bind mount replaces everything at /app with the host folder, including node_modules. The anonymous volume is a small nested mount at /app/node_modules that shadows only that subfolder, so the container keeps the dependencies it installed and never loads host-built native modules.

/app                  <-- bind mount from the host (your code)
  /app/node_modules   <-- anonymous volume (container dependencies, protected)
  • A volume only syncs files — it does not restart Node. Nodemon does that.
  • Install Nodemon as a dev dependency (npm install --save-dev nodemon) and set the dev script to "dev": "nodemon server.js".
  • Add node_modules to .dockerignore so the host folder is never sent into the build context.
  • Production has no source bind mount, so the image's own dependencies are used and this workaround is unnecessary there.
Note

Native modules such as bcrypt, sharp, or esbuild are compiled for a specific OS and CPU. Reusing host-installed modules inside a Linux container can fail with errors such as invalid ELF header; the anonymous volume avoids this.

Networking between services

Compose creates a default network. Containers reach each other by service name, not by IP.

frontend (Nginx + React)
   ↓  /api requests
backend (Express)
   ↓  Mongoose connection
mongo (MongoDB)

Inside a container, localhost means the container itself. Containers can talk internally without exposing ports to the host — for example, the backend reaches MongoDB on port 27017 without publishing it.

Your machine (host)
   │  localhost:5000
   ▼
Docker Engine
  ┌───────────────────┐
  │ backend  :5000    │
  ├───────────────────┤
  │ mongo    :27017   │  (internal only)
  └───────────────────┘

Network isolation and ports vs expose

Rather than putting every service on one network, split them so each service can only reach what it needs. A common two-network layout:

services:
  mongo:
    networks: [backend-net]                 # reachable only by the backend
  backend:
    networks: [backend-net, frontend-net]   # the bridge between both
  frontend:
    networks: [frontend-net]                # cannot reach the database

networks:
  frontend-net:
  backend-net:

The frontend can talk to the backend and the backend can talk to MongoDB, but the frontend can never reach MongoDB directly. Containers on different networks cannot see each other unless they share a network.

DirectiveEffectTypical use
ports: "5000:5000"Publishes to the host, reachable from outside Docker.Development, or a service behind a proxy.
expose: [5000]Only visible to containers on the same network.Internal-only services.
NeitherStill reachable by other containers via service name on a shared network.Pure internal services.
Watch out

Network isolation is container-to-container only. If MongoDB publishes ports: "27017:27017", anything on the host — or the LAN if the firewall allows — can reach it, bypassing the network restriction. Remove that line in production.

Inspecting and debugging the network

When containers cannot reach each other, inspect the network and test name resolution and connectivity from inside a container before changing anything else.

docker network ls                                # list networks
docker network inspect <project>_backend-net     # containers, subnet, gateway
docker exec -it backend getent hosts mongo       # test DNS resolution by name
docker exec -it backend nc -zv mongo 27017       # test TCP connectivity to a port
docker exec -it backend netstat -tlnp            # listening ports inside the container

Docker runs a DNS resolver at 127.0.0.11 inside each container, which is what maps a service name to its container IP.

React API URLs in the MERN stack

In development, React runs on localhost:5173 (Vite) and the backend on localhost:5000, so the browser calls http://localhost:5000/api/users directly.

In production with a reverse proxy, React is served by Nginx and API requests go to /api, which Nginx forwards to the backend. That lets React use a relative URL:

fetch("/api/users")

instead of:

fetch("http://localhost:5000/api/users")
Browser
   ↓
Nginx (port 80)
   ├── /        serves React static files
   └── /api/*   reverse proxy to backend:5000
                    ↓
                Express container
                    ↓
                MongoDB

Because the request is same-origin, this also avoids CORS issues. A minimal Nginx reverse-proxy location looks like this:

location /api {                          # match requests under /api
    proxy_pass http://backend:5000;      # forward to the backend service
    proxy_set_header Host $host;         # pass the original host header
    proxy_set_header X-Real-IP $remote_addr;  # keep the client's real IP
}

Production architecture variants

A production MERN deployment has three tiers — frontend, backend, and database. Docker packages each into its own container and Nginx sits in front. The only variation is where MongoDB runs.

Variant A — full stack in Docker (MongoDB as a container)

In this variant everything runs on your own infrastructure: Nginx serves the built React app, Express handles /api, and MongoDB runs as a mongo:7 container with its data on a Docker volume. Choose it for self-contained setups, learning, or small apps where you want full control and no external dependency.

Internet (users)
   ↓
Nginx (container, port 80)
   ├── serves React static files
   └── proxies /api/* to Express
                        ↓
                   Backend container (Express :5000)
                        ↓
                   MongoDB container (mongo:7 :27017)
                        ↓
                   Docker volume (mongo_data → /data/db)

Variant B — MongoDB Atlas (database in the cloud)

Here the frontend and backend still run in containers, but the database is a managed MongoDB Atlas cluster reached over the network. Choose it for production because Atlas handles backups, scaling and monitoring for you, and your app keeps no database state locally.

Internet (users)
   ↓
Nginx (container, port 80)
   ├── serves React static files
   └── proxies /api/* to Express
                        ↓
                   Backend container (Express :5000)
                        ↓
                   MongoDB Atlas (managed cloud database)
ComponentVariant A — MongoDB in DockerVariant B — MongoDB Atlas
Frontend (React + Nginx)Docker containerDocker container
Backend (Node/Express)Docker containerDocker container
MongoDBContainer (mongo:7)Managed cloud service
PersistenceVolume (mongo_data)Managed by Atlas
MONGO_URImongodb://mongo:27017/mydatabasemongodb+srv://...@cluster.mongodb.net/...
Compose servicesfrontend, backend, mongofrontend, backend
Best forSelf-contained setups, learning, small appsProduction apps needing managed backups and scaling

Both variants are valid. The frontend and backend containers are identical — only the database location changes.

VPS deployment walkthrough

A Docker-based MERN deployment needs a VPS with root access. Shared hosting does not support Docker.

  1. Create a VPS (Ubuntu 22.04 LTS, at least 2 GB RAM and 1 CPU) and note the public IP.
  2. Connect over SSH: ssh root@YOUR_VPS_IP.
  3. Open ports 22 (SSH), 80 (HTTP), and 443 (HTTPS) in the provider firewall and in ufw.
  4. Install Docker and confirm Compose is available.
  5. Clone the repository into a directory such as /opt/your-mern-app.
  6. Create the production .env with MONGO_URI, JWT_SECRET, and NODE_ENV.
  7. Build and start the containers, then check the logs.
  8. Point the domain at the VPS and enable HTTPS.

The full copy-paste sequence:

# 1. SSH into the VPS
ssh root@YOUR_VPS_IP

# 2. Update the system
apt update && apt upgrade -y

# 3. Install Docker
curl -fsSL https://get.docker.com -o get-docker.sh
sh get-docker.sh

# 4. Verify Docker and Compose
docker --version
docker compose version

# 5. Install git
apt install git -y

# 6. Clone the project
cd /opt
git clone https://github.com/youruser/your-mern-app.git
cd your-mern-app

# 7. Create the production environment file
nano .env

# 8. Build the images
docker compose build

# 9. Start the containers
docker compose up -d

# 10. Check status
docker compose ps

# 11. View logs (press Ctrl+C to exit)
docker compose logs -f

# 12. Open the firewall
ufw allow 22
ufw allow 80
ufw allow 443
ufw enable

# 13. Point DNS (A record) at the VPS IP in your provider's panel

# 14. Enable HTTPS with Certbot
apt install certbot python3-certbot-nginx -y
certbot --nginx -d yourdomain.com -d www.yourdomain.com

# 15. Open https://yourdomain.com in the browser
Note

The same steps apply to any VPS provider. The differences are only in the dashboard used to create the server, manage DNS, and open firewall ports.

Create a non-root user

Running everything as root is convenient but risky. Create a dedicated user, give it sudo, and add it to the docker group so it can run Compose without sudo:

adduser deploy
usermod -aG sudo deploy
usermod -aG docker deploy
# then log out and back in for the group change to take effect
Common mistake

Members of the docker group are effectively root — they can mount host directories into containers. Treat Docker access as a privileged permission.

Keep the production secret file readable only by that user: chmod 600 .env.

Server hardening

A fresh VPS is not secure by default. These four steps close the most common gaps before you expose the app to the internet.

# 1. Disable password SSH logins (edit /etc/ssh/sshd_config):
#      PermitRootLogin no
#      PasswordAuthentication no
systemctl restart ssh

# 2. Firewall: deny by default, allow only what you serve
ufw default deny incoming
ufw default allow outgoing
ufw allow 22/tcp     # SSH
ufw allow 80/tcp     # HTTP
ufw allow 443/tcp    # HTTPS
ufw enable

# 3. Fail2ban blocks SSH brute-force attempts
apt install fail2ban -y

# 4. Automatic security updates
apt install unattended-upgrades -y
dpkg-reconfigure --priority=low unattended-upgrades
Watch out

Allow port 22 before running ufw enable, or you can lock yourself out of the server. Confirm you can log in with your SSH key first.

Production Compose file

Keep the development file and add a production override that removes host ports and builds the production targets. Run Compose with both files using -f; later files override earlier ones.

services:
  mongo:
    image: mongo:6
    restart: always
    volumes:
      - mongo-data:/data/db
    networks: [backend-net]
    # no ports: unreachable from outside the Docker network

  backend:
    build:
      context: ./server
      target: production
    restart: always
    environment:
      - MONGO_URI=mongodb://mongo:27017/mydatabase
      - NODE_ENV=production
    depends_on: [mongo]
    networks: [backend-net, frontend-net]
    # no ports: the frontend's Nginx proxies to it internally

  frontend:
    build:
      context: ./client
      args:
        - VITE_API_URL=          # empty: use the relative /api path
    restart: always
    ports:
      - "80:80"                  # the only thing reachable from the internet
    depends_on: [backend]
    networks: [frontend-net]

volumes:
  mongo-data:

networks:
  frontend-net:
  backend-net:

Removing the MongoDB and backend ports leaves only the frontend public; the frontend's Nginx reaches the backend over the Docker network. The first deploy and every update use the same command:

git pull
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build

Compose recreates only the containers whose image changed, and the mongo-data volume is untouched, so database data survives. For a small app a brief rebuild pause is fine.

Zero-downtime updates (advanced)

  • Run the new version as a second Compose project (for example mern-blue and mern-green).
  • Point the host Nginx upstream (see the Nginx patterns below) at the new project's port.
  • Tear down the old project once traffic has switched.

This is a blue-green pattern; for most small projects up -d --build is enough.

Monitoring, logs, and disk cleanup

Once running, watch resource use and keep logs from filling the disk.

docker stats                # live CPU and memory per container
docker system df            # disk used by images, containers, and volumes
docker image prune -a       # remove unused images
docker system prune -a      # remove unused containers, networks, and images
docker inspect mern-server  # detailed metadata for a container

By default Docker logs grow without limit. Cap them per service with a logging driver:

logging:
  driver: json-file
  options:
    max-size: "10m"
    max-file: "3"
Common mistake

docker system prune -a --volumes deletes unused volumes too, including database data. Never run it with --volumes on a host that stores real data.

The Vite build and dist/

React applications built with Vite are compiled into static files for production:

npm run build   # outputs static files to dist/

This produces a dist/ directory containing index.html and an assets/ folder. That folder is the production frontend — it is what Nginx serves (or what the Nginx stage of the multi-stage Dockerfile copies).

Development vs production

Development optimizes for fast feedback; production optimizes for speed, stability, and uptime. The commands and the artifacts they produce are different.

DevelopmentProduction
Frontendnpm run dev (Vite dev server, hot reload)npm run build then serve dist/
Backendnpm run dev with a watchernpm start, often under PM2 or Docker
GoalFast iteration, debugging, hot reloadOptimized, stable, always available

Never run the development server in production.

Environment variables: VITE_ and NODE_ENV

Vite only exposes variables that begin with VITE_ to the browser build. In .env:

VITE_API_URL=http://localhost:5000/api

And in React code:

const API_URL = import.meta.env.VITE_API_URL;

The backend reads NODE_ENV to switch between development and production behavior:

NODE_ENV=production
if (process.env.NODE_ENV === "production") {
    // production configuration
}
Common mistake

Never put secrets in the Dockerfile or commit .env to Git. Secrets such as MONGO_URI, JWT_SECRET, and STRIPE_SECRET_KEY belong only in environment variables on the server. For the full env-var and secrets reference, see Node.js.

The Vite build-time trap

Vite replaces import.meta.env.VITE_* with the literal value during npm run build. The value is frozen into the JavaScript bundle, so setting the env var at container start has no effect. This is the most common production failure for a Dockerized MERN frontend.

// at build time Vite rewrites this line to the actual string
fetch(`${import.meta.env.VITE_API_URL}/users`);

The classic mistake — an env var that looks right but is ignored:

services:
  frontend:
    build: ./client
    environment:
      - VITE_API_URL=https://api.example.com   # too late: the bundle is already built

There are three fixes:

  • Build argument — declare ARG VITE_API_URL before npm run build and pass it from Compose under build.args. Correct, but one image per environment (rebuild to change).
  • Relative URL — call fetch("/api/users") and let Nginx proxy /api/ to the backend. No build arg, no rebuild, no CORS. Recommended.
  • Runtime injection — build with a placeholder and replace it in an entrypoint script. Works, but adds moving parts.
ApproachPicks up valueRebuild to changeSame image all envsRecommended
environment: at runtimeNo——No
build.argsYesYesNoOK
Relative /api URLN/ANoYesBest
Runtime injectionYesNoYesRare
Key point

If the frontend uses import.meta.env.VITE_*, the value must be decided before vite build — never at container start. To confirm a bundle is wrong, run docker compose exec frontend grep -r "localhost:5000" /usr/share/nginx/html/; if it prints minified JavaScript, the URL is baked in.

CORS

CORS controls which websites are allowed to call your API. In development and production the allowed origin differs:

npm install cors
import cors from "cors";

// production
app.use(
    cors({
        origin: "https://example.com"
    })
);

// development
app.use(
    cors({
        origin: "http://localhost:5173"
    })
);
Note

A "CORS error" is almost always a backend configuration problem — the list of allowed origins does not include the frontend's origin. When React and the API share a domain behind a reverse proxy, same-origin requests avoid CORS entirely.

HTTPS and domains

HTTP sends data in plain text; HTTPS encrypts it. Production applications should always use HTTPS, which is provided by an SSL certificate.

A common MERN domain layout separates the site from the API:

Frontend:  https://myshop.com
Backend:   https://api.myshop.com
Database:  MongoDB Atlas

Domains are connected to the server with DNS records — an A record maps the domain name to the server IP. Changes can take a few minutes to propagate.

Getting and renewing a certificate

On a Docker deployment the certificate belongs on the host Nginx (the public entry point), not inside a container. Certbot obtains a free Let's Encrypt certificate and rewrites the Nginx config:

apt install certbot python3-certbot-nginx -y
certbot --nginx -d example.com -d www.example.com

# renewal is scheduled automatically; verify it
systemctl status certbot.timer
certbot renew --dry-run

Nginx is the reverse proxy and static file server. It receives public traffic, serves the React build, and forwards /api requests to Node. It also handles SSL termination.

Nginx in Docker: host and container Nginx

In a Docker deployment there are two valid ways to place Nginx. Understanding both prevents the classic "why are there two Nginx?" confusion.

Two-Nginx pattern (host + container)

The frontend container runs Nginx, which serves the built React files and proxies /api/* to the backend service over the Docker network. A second Nginx on the host is a thin SSL terminator: it holds the certificate and forwards everything to the frontend container on port 80.

Browser (HTTPS :443)
   |
Host Nginx (VPS :443)            terminates SSL, forwards to 127.0.0.1:80
   |
Frontend container Nginx (:80)   serves static files + proxies /api/
   |            \
   |             \_ /api/*  ->  backend:5000 (Docker DNS)
   v
Backend container (Express :5000)
   |
MongoDB container (internal :27017)

Container Nginx config — static files plus an internal API route:

server {
    listen 80;
    server_name _;

    root /usr/share/nginx/html;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;   # SPA fallback
    }

    location /api/ {
        proxy_pass http://backend:5000/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

Host Nginx config — tiny and stable; it does not need to know about /api at all:

server {
    listen 443 ssl;
    server_name example.com;

    ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:80;   # the frontend container
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
Key point

Two Nginx instances is not redundancy — it is separation of concerns. The host one faces the internet and handles TLS; the container one owns static files and API routing. This keeps the backend off the public network entirely.

One-Nginx pattern (host only)

The alternative is a single Nginx on the host that routes directly to both containers: / to the frontend container and /api/ to the backend container. For that, both containers must be reachable from the host, so their ports are published on loopback.

Browser -> Host Nginx -+- /       -> frontend container (static files)
                       +- /api/*  -> backend container  (Express)
server {
    listen 443 ssl;
    server_name example.com;

    ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;

    location /api/ {
        proxy_pass http://127.0.0.1:5000;   # backend container, loopback-only
        proxy_set_header Host $host;
    }

    location / {
        proxy_pass http://127.0.0.1:8080;   # frontend container, loopback-only
        proxy_set_header Host $host;
    }
}

Nginx picks the longest matching prefix, so /api/ wins for API paths regardless of the order of the two prefix blocks.

Loopback publishing

ports: "5000:5000" exposes the port on every host interface, so anyone who can reach the host can reach the backend. Prefixing the host side with 127.0.0.1 publishes it on loopback only:

ports:
  - "127.0.0.1:5000:5000"   # only host processes (such as host Nginx) can reach it

Now the host Nginx can reach the backend but the public internet cannot, and the firewall needs no rule for port 5000.

Which Nginx pattern to use

Both Docker patterns work; they trade portability against simplicity.

AspectDocker, two NginxDocker, one Nginx
Nginx instances2 (host + container)1 (host)
API routing happensInside the frontend containerOn the host
Frontend container containsNginx + built ReactStatic files only
Backend published?NoYes — loopback only
Host Nginx complexityTrivial (one proxy_pass)Medium (two locations)
Frontend image self-contained?YesNo (just files)
Attack surfaceSmallestMedium
ScenarioRecommended
Real production MERN appTwo Nginx
Shared VPS running other appsTwo Nginx
Planning to move to KubernetesTwo Nginx (maps to an ingress)
Learning Docker + NginxOne Nginx (fewer moving parts)
Very resource-constrained VPSOne Nginx (one less process)

Why two Nginx usually wins: the backend has no published ports at all, the frontend image is portable to any Docker host, the host config stays tiny and never breaks when routes are added, and the failure domains stay separate. The one-Nginx pattern does not remove complexity — it moves the routing decisions onto the host.

Note

If you keep one Nginx, loopback-publish the backend so it stays off the public internet. The bare-metal equivalent (one host Nginx serving dist/ and proxying to PM2) is covered in Deploy on Linux (Nginx/PM2).

MongoDB in production

Do not normally run MongoDB inside the same application container. The common production solution is a managed cloud database:

Backend (Docker or PM2)
      ↓
MongoDB Atlas (managed cloud database)

Atlas handles backups, scaling, and monitoring. In Compose you simply omit the mongo service and the volume, and set the connection string in the backend environment:

MONGO_URI: mongodb+srv://user:pass@cluster0.xxxxx.mongodb.net/mydatabase  # Atlas connection string

Common deployment problems

"Cannot find module"

A dependency or package problem. Reinstall dependencies and make sure they are in package.json, not only installed locally.

"dist not found"

The frontend was not built, or the publish directory is wrong. Run npm run build and point the server at dist/.

"CORS error"

The backend CORS configuration does not allow the frontend's origin. Add it to the allowed origins.

"MongoDB connection failed"

Wrong MONGO_URI or network access is not allowed. Check the connection string and Atlas network access rules.

"500 Internal Server Error"

A backend error. Check the server logs to find the cause.

"API works locally but not in production"

Check, in order: the API URL, environment variables, CORS, HTTPS, and the server logs.

Production checklist

Run through this list before calling a deployment finished; each item is a place where a MERN stack commonly breaks in production.

  • npm run build succeeds and dist/ is deployed.
  • Environment variables are configured on the server.
  • .env is not committed to Git.
  • CORS allows exactly the production origin.
  • MongoDB production connection (Atlas or managed) works.
  • HTTPS is enabled.
  • Error handling and logging are in place.
  • Authentication and the API have been tested.
  • The frontend API URL is correct.
  • Database indexes have been checked.
  • .dockerignore exists in the client and server folders.
  • MongoDB and backend ports are removed from the production Compose file.
  • The frontend image is a multi-stage Nginx build.
  • The Vite API URL is a build arg or a relative path — never a runtime env var.
  • MongoDB authentication is enabled (MONGO_INITDB_ROOT_*).
  • Networks are split into frontend-net and backend-net.
  • restart: always (or unless-stopped) is set on every service.
  • Log rotation is configured and a backup routine has been tested.
  • SSH password login is disabled and the firewall allows only 22, 80, and 443.

Quick recap

  • Docker packages each MERN part into a portable container.
  • An image is a template; a container is a running instance.
  • Multi-stage builds keep the React image small and Nginx-only.
  • docker compose up starts the whole stack.
  • Use service names (mongo) for inter-container networking, never localhost.
  • Volumes persist data across container restarts.
  • React calls /api in production and Nginx proxies it to Node.
  • Vite exposes only VITE_ variables; NODE_ENV drives backend behavior.
  • Configure CORS, HTTPS, domains, and a production database.
  • Use Nginx + PM2 (or Docker) and CI/CD for repeatable deploys.
  • Split services across networks so the frontend can never reach the database.
  • In production publish only the frontend; keep the backend internal or loopback-only.
  • Two Nginx (host TLS + container files/API) is the production default; one Nginx is simpler for learning.
  • Harden the VPS: key-only SSH, a strict firewall, and fail2ban.
