SSH into a Docker Container

A practical, step-by-step reference for building a container with an SSH server, generating and installing SSH keys, connecting over key authentication, and reading the Linux environment once you are inside.

Deployment SSH Docker

Mission and architecture

Goal: connect from a client machine to an Ubuntu Docker container running on a host machine, using SSH keys instead of a password.

Client machine  ──SSH──►  Host machine  ──Docker──►  Ubuntu container
private key               port 2222                    public key
IP: 192.168.1.10          IP: 192.168.1.20             hostname: abc123

This setup is useful because it teaches the same SSH key authentication that GitHub, AWS, and production servers use, and because a container behaves exactly like a remote Linux server while staying a safe sandbox.

Core idea

A public key is a padlock you give to the server. The private key is the only key that opens it — and it never leaves your client machine.

Build a container with an SSH server

Run the container on the host machine, publishing the SSH port. The official Ubuntu image does not include an SSH server, so you install and start one inside it.

# 1. create and start the container, mapping host port 2222 to container port 22
docker run -it -d --name ubuntu-ssh -p 2222:22 ubuntu:22.04

# 2. open a shell inside the running container
docker exec -it ubuntu-ssh bash

# 3. install the SSH server (sshd)
apt update && apt install -y openssh-server

# 4. create the runtime directory and start the daemon
mkdir -p /var/run/sshd && service ssh start

# 5. set a temporary root password so you can log in once while setting up keys
passwd root

# 6. allow root login over SSH for this test container
echo "PermitRootLogin yes" >> /etc/ssh/sshd_config && service ssh restart

The docker run flags:

FlagMeaning
-itInteractive plus a terminal.
-dDetached — run in the background.
--name ubuntu-sshGive the container a friendly name.
-p 2222:22Map host port 2222 to container port 22.
ubuntu:22.04Use the official Ubuntu 22.04 image.
Warning

Ports must be published at creation time. You cannot add -p to a running container. On a real internet-facing server, never allow direct root login — use a normal user with sudo instead.

Common mistake

Starting the SSH daemon is the step people miss. If sshd is not running, every connection fails with "Connection closed by remote host".

Generate SSH keys

On the client machine, create a key pair:

ssh-keygen -t ed25519 -C "your-email@example.com"   # -t type, -C comment label

Press Enter three times to accept the default location and skip the passphrase. -t ed25519 selects a modern elliptic-curve algorithm; -C adds a comment so you can identify the key later.

FileRole
id_ed25519Private key — stays on the client. Never share it or copy it to a server.
id_ed25519.pubPublic key — copied to the server. Safe to share.

Verify the keys are in the default SSH folder. SSH clients only look in ~/.ssh/:

# Windows
dir %USERPROFILE%\.ssh

# Linux / macOS
ls ~/.ssh

If the keys were saved somewhere else, move them into the default folder:

# Windows example
mkdir %USERPROFILE%\.ssh 2>nul
copy D:\test\id_ed25519 %USERPROFILE%\.ssh\
copy D:\test\id_ed25519.pub %USERPROFILE%\.ssh\

Display the public key so you can copy it into the server:

type %USERPROFILE%\.ssh\id_ed25519.pub

The output is one long line starting with ssh-ed25519 AAAA.... That entire line is the public key.

Common mistake

Keys saved outside ~/.ssh/ are ignored by the SSH client, which produces a "no such file" style error even though the keys exist.

Install the public key on the server

Inside the container, create the directory SSH looks in and lock it down:

mkdir -p /root/.ssh   # -p creates parents and ignores "already exists"
chmod 700 /root/.ssh  # owner-only; sshd refuses a world-readable directory

Write the public key into authorized_keys:

echo "ssh-ed25519 AAAAC3...yourPublicKeyHere your-email@example.com" > /root/.ssh/authorized_keys  # > replaces the file

Then fix the file permissions:

chmod 600 /root/.ssh/authorized_keys   # owner read/write only; sshd rejects looser modes
Note

Use > to replace the file with exactly one line. Using >> appends, which creates duplicate keys and can confuse the SSH server. The container now trusts the client's public key.

Connect and test

On the host machine, find the real network IP the client must reach:

ipconfig        # Windows
ip addr         # Linux / macOS

Use the physical Wi-Fi adapter's IP. Ignore virtual adapters such as WSL or VirtualBox — they return addresses like 172.x.x.x that other machines cannot reach.

Open the mapped port in the host firewall so incoming SSH traffic can reach the container:

netsh advfirewall firewall add rule name="Docker SSH 2222" dir=in action=allow protocol=TCP localport=2222  # open the mapped port

From the client machine, connect with verbose output so you can see what SSH is doing:

ssh -v root@192.168.1.20 -p 2222

Watch for Authentication succeeded (publickey) — that confirms the key worked. The prompt then changes to something like root@abc123:~#, meaning you are inside the container with no password needed.

Common mistake

Most SSH failures come from three causes: the daemon is not running, the port is not open in the firewall, or the key files are in the wrong location.

The prompt is your position indicator — it tells you where you are in the filesystem.

|    |       | |
|    |       | # you are root (superuser)
|    |       ~ your home folder (/root)
|    hostname of the container
user = root

Note

ls lists the current folder, not all files on the system. If you were in an empty /root, you saw nothing. After cd /, you see the real root: bin boot dev etc home lib ...

How key authentication works

The SSH key handshake proves identity without ever sending the private key over the network:

1. Client: "I want to log in as root."
2. Server: "Prove it — here is a random challenge."
3. Client: encrypts the challenge with its PRIVATE key.
4. Server: checks the result against the stored PUBLIC key.
5. Match?  login granted.   No match?  access denied.
Why it is safe

The private key never travels over the network. Even if someone records the entire conversation, they cannot replay it to gain access.

Next steps

Once you can SSH into a container, these are natural follow-ups:

  • Auto-start SSH with a Dockerfile so sshd launches automatically every time the container starts.
  • Browse files over SSH with a GUI client such as WinSCP or FileZilla, using the same host, port, user, and private key.
  • Use VS Code Remote-SSH to edit code inside the container as if it were a local folder.
  • Mount a host folder into the container with -v so both sides see the same files.
  • Disable password login for pure key-only authentication.

A Dockerfile that starts the SSH server automatically:

FROM ubuntu:22.04
RUN apt update && apt install -y openssh-server   # install the daemon
RUN mkdir /var/run/sshd                           # runtime dir the daemon needs
EXPOSE 22                                         # the container's SSH port
CMD ["/usr/sbin/sshd", "-D"]                      # run sshd in the foreground

Key-only authentication in /etc/ssh/sshd_config:

PasswordAuthentication no          # allow keys only, no passwords
PermitRootLogin prohibit-password  # root may log in with a key, not a password
Warning

Two things to remember: if the host restarts the container, SSH stops and you must run docker exec -it ubuntu-ssh service ssh start again. If the host IP changes, re-check it and use the new address.

Quick recap

  • Publish the SSH port at container creation with -p 2222:22.
  • Install and start openssh-server inside the container.
  • Generate an ed25519 key pair with ssh-keygen.
  • Keep the private key on the client; install the public key in authorized_keys.
  • Use 700 on .ssh and 600 on authorized_keys.
  • Connect with ssh -v root@IP -p 2222 and look for publickey success.
  • The private key never leaves the client — that is what makes key auth safe.
  • Read the prompt to know where you are in the filesystem.
