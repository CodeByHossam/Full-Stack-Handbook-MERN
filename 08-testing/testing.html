Testing

Automatically checking that your code works: unit, integration and end-to-end tests with Vitest, React Testing Library and Supertest.

Testing Vitest + RTL Supertest

What is testing?

Testing means writing code that automatically checks that your other code works. Instead of clicking through the app by hand after every change, a test runner runs your checks and tells you what broke.

There are three main levels:

TypeWhat it testsScope
UnitOne small piece of code in isolationSmallest
IntegrationMultiple parts working togetherMedium
End-to-endThe whole app like a real userLargest

Unit test

Tests one tiny unit, usually a single function. Example: add(2, 3) should return 5.

Integration test

Tests that several pieces cooperate correctly.

Key point

Vitest and Jest share almost the same API (test, describe, expect), so what you learn here transfers directly. Examples on this page use Vitest.

Vitest install and setup

Vitest is a fast test runner that fits naturally with Vite projects (and works for Node code too).

npm install -D vitest

Add a script to package.json:

"scripts": {
    "test": "vitest"
}

Run the suite:

npm test
Note

For React component tests you also install @testing-library/react and @testing-library/jest-dom, covered below.

A simple test

Export the function you want to test, then import it into a test file.

function add(a, b) {
    return a + b;
}
// add.test.js
import { test, expect } from "vitest";

test("adds two numbers", () => {
    expect(add(2, 3)).toBe(5);
});

test declares a single test case with a description and a callback. expect(...) builds an assertion, and the matcher (toBe) defines what must be true.

Grouping with describe()

describe groups related tests so output reads like a spec. Blocks can nest.

describe("Calculator", () => {
    test("adds numbers", () => {
        expect(add(2, 3)).toBe(5);
    });

    test("multiplies numbers", () => {
        expect(multiply(4, 5)).toBe(20);
    });
});

Common matchers

A matcher is the method chained after expect(...). These are the ones you will reach for most often.

MatcherPasses when
toBe(5)Value is exactly equal (primitives / same reference)
toEqual(object)Value is deeply equal (objects, arrays)
toBeTruthy()Value is truthy
toBeFalsy()Value is falsy
toBeNull()Value is exactly null
toContain("apple")Array or string contains the item
toBeGreaterThan(10)Value is greater than the argument
toBeLessThan(100)Value is less than the argument
toHaveProperty("name")Object has the given property
toHaveValue("text")Input element holds the given value
toHaveBeenCalled()A mock function was called
toBeInTheDocument()Element exists in the DOM (jest-dom)
 
expect(value).toBe(5);
expect(value).toEqual(object);
expect(value).toBeTruthy();
expect(value).toBeFalsy();
expect(value).toBeNull();
expect(array).toContain("apple");
expect(value).toBeGreaterThan(10);
expect(value).toBeLessThan(100);

Testing functions, arrays and objects

The matcher you pick depends on the value's type: primitives use toBe, membership uses toContain, and objects/arrays need toEqual for a deep comparison.

function multiply(a, b) {
    return a * b;
}

test("multiply", () => {
    expect(multiply(4, 5)).toBe(20);
});

Arrays: use toContain for membership and toEqual for exact content.

const fruits = ["apple", "banana", "orange"];

test("contains banana", () => {
    expect(fruits).toContain("banana");
});

Objects: toBe would compare references, so use toEqual for a deep comparison.

const user = { name: "Alice", age: 42 };

test("user data", () => {
    expect(user).toEqual({ name: "Alice", age: 42 });
});

Async tests

Make the test callback async and await the promise so the runner waits for the result.

test("gets user", async () => {
    const user = await getUser();

    expect(user.name).toBe("Alice");
});
Common mistake

Forgetting await (or returning the promise) makes the test finish before the assertion runs, so it passes even when it should fail.

Setup and teardown with beforeEach / afterEach

Use these hooks to prepare state before each test and clean up after it.

beforeEach(() => {
    // setup — runs before every test
});

afterEach(() => {
    // cleanup — runs after every test
});

beforeAll / afterAll run once for the whole block (useful for an expensive database connection).

Mocks with vi.fn()

A mock is a fake function that records its calls and returns canned values instead of doing real work. Use it to stand in for anything slow, external, or side-effectful.

const mockFunction = vi.fn();          // create the mock

mockFunction("hello");                  // call it in place of the real dependency

expect(mockFunction).toHaveBeenCalled();      // did it get called at all?
expect(mockFunction).toHaveBeenCalledWith("hello"); // ...and with these args?

Why mock? Some dependencies are slow, expensive, or unsafe to call during a test: a real API, a real payment system, a real email service, or a real database. Replace them with a mock so the test stays fast, deterministic and offline.

Real function
     ↓
Mock function  (records calls, returns canned values)
Note

In Jest the mock helper is jest.fn(). The concept is identical.

React Testing Library

RTL renders your component into a virtual DOM and lets you query it the way a user would.

npm install -D @testing-library/react @testing-library/jest-dom

Then render a component and assert on what appears on screen.

import { render, screen } from "@testing-library/react";

test("shows hello", () => {
    render(<h1>Hello Alice</h1>);

    expect(screen.getByText("Hello Alice")).toBeInTheDocument();
});

toBeInTheDocument() comes from @testing-library/jest-dom and extends the standard matchers with DOM-aware ones. Import it once in your test setup file.

Finding elements

Each query targets the element the way a user perceives it — by visible text, by role, or by its label — rather than by fragile CSS classes.

screen.getByText("Login");
screen.getByRole("button");
screen.getByLabelText("Email");
screen.getByPlaceholderText("Enter email");
QueryUse it for
getByTextVisible text content
getByRoleAccessible role (button, textbox, heading)
getByLabelTextForm input tied to a label
getByPlaceholderTextInput identified by placeholder
Key point

Prefer getByRole and getByLabelText: they mirror how assistive technology sees the page, so tests stay accessible-friendly. getBy* throws if not found; queryBy* returns null; findBy* is async for elements that appear later.

User interaction with user-event

user-event simulates typing, clicking, and other interactions more realistically than fireEvent — it even awaits the resulting UI updates, which is why the tests below are async.

npm install -D @testing-library/user-event
import userEvent from "@testing-library/user-event";

test("button click", async () => {
    const user = userEvent.setup();

    render(<MyButton />);

    await user.click(screen.getByRole("button"));
});

Typing into an input:

const input = screen.getByRole("textbox");

await user.type(input, "Alice");

expect(input).toHaveValue("Alice");

Testing forms and conditional UI

A full form flow: fill the fields, click submit, then assert on the result.

test("login form", async () => {
    const user = userEvent.setup();

    render(<LoginForm />);

    await user.type(screen.getByLabelText("Email"), "test@email.com");
    await user.type(screen.getByLabelText("Password"), "123456");
    await user.click(screen.getByRole("button", { name: "Login" }));
});

Components often render one of several states. Test all of them, not just the happy path:

Loading
Error
Success
Key point

Render the component in each state (loading, error, success) and assert on what the user sees for each one.

API testing with Supertest

Supertest exercises an Express app end to end over HTTP without starting a real network server.

npm install -D supertest
import request from "supertest";
import app from "../app";

test("GET users", async () => {
    // request(app) drives the Express app in memory — no network port involved
    const response = await request(app).get("/api/users");

    expect(response.status).toBe(200);
});

POST with a body, and asserting on the response payload:

test("create user", async () => {
    const response = await request(app)
        .post("/api/users")
        .send({ name: "Alice", email: "test@email.com" });

    expect(response.status).toBe(201);
    expect(response.body).toHaveProperty("name");
    expect(response.body.name).toBe("Alice");
});

Testing a failure path — an id that does not exist should return 404:

test("user not found", async () => {
    const response = await request(app).get("/api/users/invalid-id");

    expect(response.status).toBe(404);
});

Testing a protected route

Send the token in the Authorization header using .set(). The middleware behind this header is owned by the Authentication & JWT page.

const response = await request(app)
    .get("/api/profile")
    .set("Authorization", `Bearer ${token}`);  // pass the token like a real browser would
Key point

For auth tests, cover all branches: register (valid, duplicate email, missing fields, invalid email), login (correct password, wrong password, missing user), protected routes (valid token, missing token, invalid token) and authorization (admin vs normal user).

For CRUD resources, test every operation plus the failure cases:

  • GET all, GET one, POST, PUT/PATCH, DELETE
  • Validation errors
  • Not found (404)
  • Unauthorized (401)
  • Duplicate data
  • Database errors

The testing pyramid and AAA

Write many fast unit tests, fewer integration tests, and only a handful of expensive end-to-end tests.

            E2E
           /   \
          /     \
     Integration
        /       \
       /         \
      Unit Tests
AAA pattern

Structure each test as Arrange → Act → Assert.

// Arrange
const a = 5;
const b = 3;

// Act
const result = add(a, b);

// Assert
expect(result).toBe(8);
Note

Test behavior, not implementation. Do not test that a specific internal function ran — test that the user gets the correct result.

Test file naming

Co-locate a test next to the file it covers. Either .test or .spec is fine — be consistent.

calculator.js
calculator.test.js
calculator.spec.js

Login.jsx
Login.test.jsx

Coverage

Coverage measures how much of your code the tests exercise. Common metrics:

  • Statements
  • Branches
  • Functions
  • Lines
Warning

Do not chase 100% blindly. Testing the important behavior matters more than a high number. A page full of trivial assertions can be 100% covered and still miss real bugs.

Quick recap

  • Test types: unit (one unit) → integration (parts together) → E2E (real user flow)
  • MERN mapping: React Testing Library for components, Vitest/Jest for logic, Supertest for APIs
  • test runs a case, describe groups them, expect(...).matcher() asserts
  • toBe for primitives, toEqual for deep object/array equality
  • Async tests must await; use beforeEach/afterEach for setup and cleanup
  • Mock slow or external dependencies with vi.fn()
  • Query React UI by role/label/text; simulate users with userEvent
  • Test loading, error and success states — not just the happy path
  • Supertest covers GET/POST/failures and protected routes via a Bearer token
  • Follow the testing pyramid and the Arrange–Act–Assert pattern
  • Test behavior, not implementation; use coverage as a guide, not a goal
