Complete MERN Database Reference

MongoDB Atlas + Mongoose vs PostgreSQL/MySQL: setup, code, platform configuration, function-by-function explanations, comparisons, and how to use both in one MERN app.

Database MongoDB + SQL Full Guide

1. Introduction — the "M" in MERN

MERN = MongoDB · Express · React · Node.js. The "M" stands for MongoDB, but nothing stops you from swapping it with SQL. Understanding both makes you a stronger engineer, because the right database depends on the shape of your data, not on fashion.

Mental modelDatabaseThink of it as
DocumentMongoDBA folder of JSON files
RelationalSQL (Postgres/MySQL)Excel sheets linked by IDs

In MERN we connect from Express using an ODM/ORM or a driver:

  • MongoDB → Mongoose (ODM)
  • SQL → raw driver (pg, mysql2) or an ORM (Prisma, Sequelize, TypeORM)

React never talks to the database directly. React calls Express, and Express talks to the database.

React  --HTTP-->  Express  --driver/ODM-->  MongoDB  |  SQL

2. MongoDB Atlas — platform setup

Atlas is MongoDB's fully managed cloud service. The free tier (M0) is perfect for learning and small apps.

Step 1 — Create an account

Go to mongodb.com/atlas, choose Try Free, and sign up with email or Google.

Step 2 — Create a cluster

  1. Choose M0 Free (512 MB, shared).
  2. Cloud provider: AWS / GCP / Azure (closest to your users).
  3. Region: for example Frankfurt or N. Virginia.
  4. Cluster name: leave Cluster0 or rename to mern-dev.
  5. Click Create Deployment.

Step 3 — Create a database user

  • Database Access → Add New Database User.
  • Authentication: Password.
  • Username: mernUser.
  • Password: autogenerate and store it safely.
  • Role: Read and write to any database (dev only — restrict in production).

Step 4 — Allow network access

  • Network Access → Add IP Address.
  • Development: allow access from anywhere (0.0.0.0/0).
  • Production: whitelist only your server's IP.

Step 5 — Get the connection string

Cluster → Connect → Drivers → Node.js. Copy the URI:

mongodb+srv://mernUser:<password>@cluster0.xxxxx.mongodb.net/?retryWrites=true&w=majority

Replace <password> with the real password and add the database name before the ?, for example /myAppDB.

Step 6 — Store it as an environment variable

An environment variable keeps credentials out of your source code: the backend reads the URI via process.env.MONGO_URI, so the same code can point at different databases in dev and production. In a .env file each line is one KEY=VALUE pair, with no spaces around the =.

MONGO_URI=mongodb+srv://mernUser:PASSWORD@cluster0.xxxxx.mongodb.net/myAppDB?retryWrites=true&w=majority
PORT=5000
Warning

Add .env to .gitignore immediately. Never commit credentials. Env handling is covered on the Node.js page.

3. Mongoose — install, connect, configure

Mongoose is the ODM (Object Data Modeling) library that gives MongoDB structure, validation, and clean JavaScript APIs.

npm install mongoose dotenv

config/db.js

A single connection module keeps startup logic in one place. autoIndex builds schema indexes automatically in development but is switched off in production to avoid surprise rebuilds.

const mongoose = require("mongoose");

const connectDB = async () => {
    try {
        const conn = await mongoose.connect(process.env.MONGO_URI, {
            autoIndex: process.env.NODE_ENV !== "production"
        });
        console.log("MongoDB connected: " + conn.connection.host);
    } catch (err) {
        console.error("MongoDB connection error:", err.message);
        process.exit(1);
    }
};

module.exports = connectDB;

server.js

The entry point loads env vars, opens the database connection once, mounts the routes, and only then starts listening.

require("dotenv").config();
const express = require("express");
const connectDB = require("./config/db");

const app = express();
app.use(express.json());
connectDB();

app.use("/api/users", require("./routes/users"));

app.listen(process.env.PORT || 5000, () =>
    console.log("Server running on port " + (process.env.PORT || 5000))
);
Key point

Mongoose manages a connection pool internally. Call connect() once at startup and reuse it everywhere — never connect per request.

4. Mongoose — schema, model, methods, CRUD

models/User.js

The model is the single source of truth for a document's shape and rules: types, required fields, defaults, and relaxations such as trim/lowercase that run before saving.

const mongoose = require("mongoose");

const userSchema = new mongoose.Schema(
    {
        name:  { type: String, required: true, trim: true },
        email: { type: String, required: true, unique: true, lowercase: true }, // normalized + indexed
        age:   { type: Number, min: 0, max: 120 },
        role:  { type: String, enum: ["user", "admin"], default: "user" },
        posts: [{ type: mongoose.Schema.Types.ObjectId, ref: "Post" }]          // reference for populate()
    },
    { timestamps: true }   // adds createdAt / updatedAt automatically
);

userSchema.methods.isAdmin = function () {
    return this.role === "admin";
};

userSchema.statics.findByEmail = function (email) {
    return this.findOne({ email });
};

userSchema.virtual("displayName").get(function () {
    return this.name + " (" + this.role + ")";
});

module.exports = mongoose.model("User", userSchema);

CRUD cheat sheet

These promise-based calls mirror the shell operations. Note the extras that matter in an API: .select() hides fields, .lean() skips Mongoose wrapping on read-only queries, and the update options return the new document while still validating it.

const User = require("../models/User");

// CREATE
const user = await User.create({ name: "Alice", email: "alice@example.com" });

// READ
const all   = await User.find({ role: "admin" }).limit(10).sort("-createdAt");
const one   = await User.findById(id).populate("posts");        // replace post ids with documents
const found = await User.findOne({ email: "alice@example.com" }).lean(); // plain object, faster

// UPDATE
await User.findByIdAndUpdate(id, { name: "Alice B." }, { new: true, runValidators: true });

// DELETE
await User.findByIdAndDelete(id);

// AGGREGATION
const stats = await User.aggregate([
    { $group: { _id: "$role", count: { $sum: 1 } } },
    { $sort: { count: -1 } }
]);
Note

For a deeper treatment of Query vs Document, populate, authorization, methods/virtuals/statics, and controller patterns, see MongoDB & Mongoose Deep Dive. Basic shell CRUD and operators live on MongoDB Basics.

5. Express + Mongoose — full example

routes/users.js

A thin router maps each HTTP verb to a model call and translates errors into status codes. .select("-__v") keeps Mongoose's internal version key out of the response.

const express = require("express");
const User = require("../models/User");
const router = express.Router();

router.get("/", async (req, res) => {
    try {
        const users = await User.find().select("-__v").lean();
        res.json(users);
    } catch (err) {
        res.status(500).json({ error: err.message });
    }
});

router.get("/:id", async (req, res) => {
    try {
        const user = await User.findById(req.params.id);
        if (!user) return res.status(404).json({ error: "Not found" });
        res.json(user);
    } catch (err) {
        res.status(500).json({ error: err.message });
    }
});

router.post("/", async (req, res) => {
    try {
        const user = await User.create(req.body);
        res.status(201).json(user);
    } catch (err) {
        res.status(400).json({ error: err.message });
    }
});

router.put("/:id", async (req, res) => {
    try {
        const user = await User.findByIdAndUpdate(req.params.id, req.body, {
            new: true,
            runValidators: true
        });
        res.json(user);
    } catch (err) {
        res.status(400).json({ error: err.message });
    }
});

router.delete("/:id", async (req, res) => {
    try {
        await User.findByIdAndDelete(req.params.id);
        res.json({ success: true });
    } catch (err) {
        res.status(500).json({ error: err.message });
    }
});

module.exports = router;
Note

Route design, status codes, and REST conventions are owned by the REST API page; Express middleware patterns live on the Express page.

6. React — consuming the Express + Mongoose API

React fetches over HTTP and stores the JSON in state. It never imports Mongoose or knows what database is behind the API.

import { useEffect, useState } from "react";
import axios from "axios";

const API = "http://localhost:5000/api/users";

export default function Users() {
    const [users, setUsers] = useState([]);

    useEffect(() => {
        axios.get(API).then((r) => setUsers(r.data));
    }, []);

    const addUser = async () => {
        const { data } = await axios.post(API, {
            name: "Sara",
            email: "sara@example.com",
            role: "user"
        });
        setUsers((prev) => [...prev, data]);
    };

    const removeUser = async (id) => {
        await axios.delete(API + "/" + id);
        setUsers((prev) => prev.filter((u) => u._id !== id));
    };

    return (
        <div>
            <button onClick={addUser}>Add User</button>
            <ul>
                {users.map((u) => (
                    <li key={u._id}>
                        {u.name} — {u.email} ({u.role})
                        <button onClick={() => removeUser(u._id)}>x</button>
                    </li>
                ))}
            </ul>
        </div>
    );
}
Key point

React only touches HTTP. It does not know whether the backend is Mongo or SQL — that is the beauty of a REST API.

7. SQL — platform setup (PostgreSQL & MySQL)

Three realistic options:

Option A — Local via Docker (fastest for dev)

Docker starts a disposable database server in a single command — no installer, no system service, and no version conflicts with anything else on your machine. It is the fastest option for local development, but the data lives inside the container, so deleting it erases the database unless you add a volume.

# Postgres
# -e sets container env vars; -p maps host:container ports; -d runs it detached
docker run --name pg -e POSTGRES_PASSWORD=secret -e POSTGRES_DB=mydb -p 5432:5432 -d postgres

# MySQL
docker run --name mysql -e MYSQL_ROOT_PASSWORD=secret -e MYSQL_DATABASE=mydb -p 3306:3306 -d mysql:8

Option B — Managed cloud (like Atlas, but for SQL)

  • Neon — serverless Postgres, generous free tier.
  • Supabase — Postgres + Auth + Storage.
  • PlanetScale — serverless MySQL.
  • AWS RDS / Azure SQL — enterprise-grade. See the AWS RDS MySQL Guide.

Option C — Connection string

A connection string packs the driver, credentials, host, port and database name into one URL, so it is the single value you reuse in code, your .env, and GUI clients. The ?sslmode=require query parameter forces an encrypted connection, which most managed hosts expect.

postgresql://user:password@host:5432/mydb?sslmode=require
mysql://user:password@host:3306/mydb

Env

Keep the URL in an environment variable rather than hard-coding it, so the same codebase can point at a local, staging or production database without changes. DATABASE_URL is the conventional name that the pg driver and Prisma read automatically.

DATABASE_URL=postgresql://user:password@host:5432/mydb?sslmode=require
PORT=5000

Create the table

SQL needs its structure declared before you can insert anything. This is the same shape as the Mongoose schema above, expressed as a table with typed columns.

CREATE TABLE users (
    id         SERIAL PRIMARY KEY,          -- auto-incrementing primary key
    name       VARCHAR(100) NOT NULL,
    email      VARCHAR(150) UNIQUE NOT NULL,-- unique constraint enforces no duplicates
    age        INT,
    role       VARCHAR(20) DEFAULT 'user',
    created_at TIMESTAMP DEFAULT NOW()
);

8. MySQL command reference

This is the working vocabulary of MySQL: the statements you type into MySQL Workbench, a shell, or a migration file to create a database, shape a table, and read and write rows. The earlier sections run SQL from Node.js; this section is the raw command set itself, grouped by what each statement does, so you can look up the exact syntax when a driver call is not enough.

Database operations

A database (also called a schema) is the container that holds your tables. Create one, switch into it with USE, and confirm which one is active before creating tables — otherwise the table silently lands in the wrong database.

-- Create a new database (schema)
CREATE DATABASE appdb;

-- List every database on the server
SHOW DATABASES;

-- Select the active database for this session
USE appdb;

-- Print the database currently in use (NULL when none is selected)
SELECT DATABASE();

-- Delete a database and every table inside it (irreversible)
DROP DATABASE appdb;
Watch out

DROP DATABASE permanently deletes the schema and all its data in a single statement. There is no undo — verify the name and keep a backup.

Transactions — COMMIT, ROLLBACK, AUTOCOMMIT

A transaction groups several writes so they succeed or fail together — essential for money, inventory, or any multi-step change. MySQL runs in autocommit mode by default, meaning every statement is saved the moment you run it. Set AUTOCOMMIT = 0 when several statements must be atomic, then COMMIT to save them or ROLLBACK to discard them.

-- Autocommit ON (the default): each statement saves itself
SET AUTOCOMMIT = 1;

-- Turn autocommit OFF so you control when changes are saved
SET AUTOCOMMIT = 0;

-- Wrap several writes so they all land together
START TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;     -- persist both updates as one unit
-- ROLLBACK; -- instead, discard everything since the last commit
Key point

With AUTOCOMMIT = 0, forgetting to COMMIT loses your changes when the session ends, and the open transaction can hold row locks that block other clients.

Table operations

A table declares its columns, types, and rules before any row can be inserted — the opposite of MongoDB's flexible documents. DESCRIBE is the fastest way to inspect an existing table, and ALTER TABLE ... ADD CONSTRAINT adds a rule on top of data that is already there.

-- Define columns, a primary key, and defaults up front
CREATE TABLE users (
    id         INT AUTO_INCREMENT PRIMARY KEY,      -- auto-increments per insert
    name       VARCHAR(255) NOT NULL,
    email      VARCHAR(255) NOT NULL,
    age        INT,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP  -- filled automatically
);

-- List every table in the active database
SHOW TABLES;

-- Inspect columns, types, keys, and defaults
DESCRIBE users;

-- Enforce a rule on existing data: no duplicate emails
ALTER TABLE users
ADD CONSTRAINT unique_email UNIQUE (email);

-- Delete the table and all its rows (irreversible)
DROP TABLE users;
StatementRemovesUndo?
DELETE FROM usersRows matching WHEREYes, if inside a transaction
TRUNCATE TABLE usersAll rows, keeps the tableNo — DDL, cannot roll back
DROP TABLE usersThe table and its rowsNo — DDL, cannot roll back
DROP DATABASE appdbThe database and every tableNo — DDL, cannot roll back

Column operations

The shape of a table changes as an app grows, and MySQL handles all of it with ALTER TABLE: ADD a column, MODIFY its type, CHANGE to rename and retype it, and DROP to remove it. Each runs in place and rewrites existing data, so test on a copy first.

-- Add a new column
ALTER TABLE users
ADD COLUMN phone_number VARCHAR(15);

-- Change an existing column's data type (keeps the name)
ALTER TABLE users
MODIFY COLUMN phone_number INT;

-- Rename a column (repeat its full definition)
ALTER TABLE users
CHANGE COLUMN old_column_name new_column_name VARCHAR(255);

-- Remove a column and its data
ALTER TABLE users
DROP COLUMN phone_number;
Watch out

CHANGE COLUMN needs the old name, the new name, and the full type. Omit the type and MySQL errors out; supply the wrong type and you silently retype the column.

Data operations — INSERT, SELECT, UPDATE, DELETE

These four verbs are the core of daily work: INSERT adds rows, SELECT reads them, UPDATE changes them, and DELETE removes them. To run them from Node.js with safe placeholders instead of literals, see Express + SQL.

-- Insert one row (column order must match the value order)
INSERT INTO users (name, email, age)
VALUES ('John Doe', 'john.doe@example.com', 30);

-- Read every row
SELECT * FROM users;

-- Read only matching rows
SELECT * FROM users
WHERE age > 25;

-- Change matching rows; without WHERE this touches every row
UPDATE users
SET name = 'Jane Doe', age = 35
WHERE id = 1;

-- Remove matching rows; without WHERE this empties the table
DELETE FROM users
WHERE id = 1;
Common mistake

An UPDATE or DELETE with no WHERE applies to every row. Run the same condition as a SELECT first to preview exactly what you are about to change or remove.

Advanced queries — ORDER BY, COUNT, GROUP BY, JOIN

These turn raw rows into answers. ORDER BY sorts, COUNT and GROUP BY aggregate, and JOIN combines related tables on a matching key — the relational feature MongoDB reproduces with $lookup and populate() (see MongoDB vs SQL).

-- Sort rows by a column, descending
SELECT * FROM users
ORDER BY age DESC;

-- Count all rows in the table
SELECT COUNT(*) FROM users;

-- Count rows per age (GROUP BY collapses each distinct value into one row)
SELECT age, COUNT(*)
FROM users
GROUP BY age;

-- Combine two tables on the shared key
SELECT users.name, orders.order_date
FROM users
JOIN orders ON users.id = orders.user_id;
JoinReturns
INNER JOINOnly rows with a match in both tables
LEFT JOINAll left rows, plus matches (NULL when none)
RIGHT JOINAll right rows, plus matches
FULL JOINNot supported in MySQL — emulate with a LEFT JOIN and RIGHT JOIN joined by UNION
Note

To provision a managed MySQL instance and run these commands against it, see the AWS RDS MySQL Guide.

9. SQL in Node — raw drivers (pg & mysql2)

The driver is the lowest-level way to talk SQL from Node. No magic, just SQL strings.

# PostgreSQL
npm install pg dotenv

# MySQL
npm install mysql2 dotenv

config/db.js (Postgres)

Wrap a Pool in a tiny query() helper so every route uses the same pooled connection instead of opening its own.

const { Pool } = require("pg");

const pool = new Pool({
    connectionString: process.env.DATABASE_URL,
    ssl: { rejectUnauthorized: false }   // managed hosts often require TLS
});

module.exports = {
    query: (text, params) => pool.query(text, params), // params keep queries injection-safe
    pool
};

config/db.js (MySQL)

The MySQL version is identical in spirit: one pool, one query() wrapper.

const mysql = require("mysql2/promise");

const pool = mysql.createPool({
    uri: process.env.DATABASE_URL,
    waitForConnections: true,   // queue requests when all connections are busy
    connectionLimit: 10
});

module.exports = {
    query: (text, params) => pool.query(text, params),
    pool
};
Key point

A Pool is a set of reusable connections. Opening a new connection per request will kill your database under load — always use a pool.

10. SQL in Node — Prisma ORM (the Mongoose equivalent)

If Mongoose is to MongoDB, Prisma is to SQL.

npm install @prisma/client
npm install -D prisma
npx prisma init

prisma/schema.prisma

schema.prisma is Prisma's single source of truth: it declares the datasource, the generated client, and every model in one typed file. prisma migrate turns these models into real tables, so your schema lives in version control instead of hand-written SQL. This block uses Prisma's schema DSL, not JavaScript, so comments are written with //.

generator client {
  provider = "prisma-client-js"
}

datasource db {
  provider = "postgresql"
  url      = env("DATABASE_URL")
}

model User {
  id        Int      @id @default(autoincrement())
  name      String
  email     String   @unique
  age       Int?
  role      Role     @default(USER)
  posts     Post[]
  createdAt DateTime @default(now())
}

model Post {
  id       Int    @id @default(autoincrement())
  title    String
  body     String
  author   User   @relation(fields: [authorId], references: [id])  // foreign key link
  authorId Int
}

enum Role {
  USER
  ADMIN
}

Run first migration

A migration applies your schema to the database and records the change as a versioned file. Run it once after editing schema.prisma; the --name flag labels the migration so the history stays readable. Re-run it whenever the models change.

npx prisma migrate dev --name init

config/prisma.js

Create the client once and share it. Prisma manages its own connection pool, so a single instance is all you need.

const { PrismaClient } = require("@prisma/client");
const prisma = new PrismaClient();
module.exports = prisma;

CRUD cheat sheet

Prisma calls are typed and read almost like English: where filters, include eager-loads relations (a JOIN), and orderBy/take handle sorting and pagination.

const prisma = require("../config/prisma");

// CREATE
const user = await prisma.user.create({
    data: { name: "Alice", email: "alice@example.com" }
});

// READ
const all = await prisma.user.findMany({
    where: { role: "ADMIN" },
    include: { posts: true },        // eager-load the relation (JOIN)
    orderBy: { createdAt: "desc" },
    take: 10                         // LIMIT 10
});
const one = await prisma.user.findUnique({ where: { id: 1 } });

// UPDATE
await prisma.user.update({
    where: { id: 1 },
    data: { name: "Alice B." }
});

// DELETE
await prisma.user.delete({ where: { id: 1 } });

// TRANSACTION
await prisma.$transaction([
    prisma.user.update({ where: { id: 1 }, data: { role: "ADMIN" } }),
    prisma.post.create({ data: { title: "Hi", body: "...", authorId: 1 } })
]);

11. Express + SQL — full example

Same API shape as the Mongoose version — only the data layer changes.

routes/users.js (with raw pg driver)

This router uses the db.query() helper from config/db.js and returns rows from each result. Values are passed as $1, $2 placeholders matched positionally to an array; the driver escapes them, which is what prevents SQL injection.

const express = require("express");
const db = require("../config/db");
const router = express.Router();

router.get("/", async (req, res) => {
    try {
        const { rows } = await db.query(
            "SELECT id, name, email, age, role, created_at FROM users ORDER BY created_at DESC"
        );
        res.json(rows);
    } catch (err) {
        res.status(500).json({ error: err.message });
    }
});

router.get("/:id", async (req, res) => {
    try {
        const { rows } = await db.query("SELECT * FROM users WHERE id = $1", [req.params.id]);
        if (!rows[0]) return res.status(404).json({ error: "Not found" });
        res.json(rows[0]);
    } catch (err) {
        res.status(500).json({ error: err.message });
    }
});

router.post("/", async (req, res) => {
    const { name, email, age, role } = req.body;
    try {
        const { rows } = await db.query(
            "INSERT INTO users (name, email, age, role) VALUES ($1,$2,$3,$4) RETURNING *",  // RETURNING * gives back the new row
            [name, email, age, role || "user"]
        );
        res.status(201).json(rows[0]);
    } catch (err) {
        res.status(400).json({ error: err.message });
    }
});

router.put("/:id", async (req, res) => {
    const { name, email, age, role } = req.body;
    try {
        const { rows } = await db.query(
            "UPDATE users SET name=$1, email=$2, age=$3, role=$4 WHERE id=$5 RETURNING *",
            [name, email, age, role, req.params.id]
        );
        res.json(rows[0]);
    } catch (err) {
        res.status(400).json({ error: err.message });
    }
});

router.delete("/:id", async (req, res) => {
    try {
        await db.query("DELETE FROM users WHERE id = $1", [req.params.id]);
        res.json({ success: true });
    } catch (err) {
        res.status(500).json({ error: err.message });
    }
});

module.exports = router;
Warning

Never build SQL with template strings such as "WHERE id=" + id. Always use parameterized queries ($1, ?) — this is the single biggest SQL-injection defense.

With Prisma instead — same routes, cleaner code

The routes no longer contain SQL strings; Prisma builds the queries and parameterizes them for you, which removes the injection risk entirely.

const express = require("express");
const prisma = require("../config/prisma");
const router = express.Router();

router.get("/", async (req, res) => {
    const users = await prisma.user.findMany({ orderBy: { createdAt: "desc" } });
    res.json(users);
});

router.post("/", async (req, res) => {
    try {
        const user = await prisma.user.create({ data: req.body });
        res.status(201).json(user);
    } catch (err) {
        res.status(400).json({ error: err.message });
    }
});

router.put("/:id", async (req, res) => {
    const user = await prisma.user.update({
        where: { id: Number(req.params.id) },
        data: req.body
    });
    res.json(user);
});

router.delete("/:id", async (req, res) => {
    await prisma.user.delete({ where: { id: Number(req.params.id) } });
    res.json({ success: true });
});

module.exports = router;

12. React — consuming the Express + SQL API

Identical to the Mongoose example. That is the point of clean architecture.

import { useEffect, useState } from "react";
import axios from "axios";

const API = "http://localhost:5000/api/users";

export default function Users() {
    const [users, setUsers] = useState([]);

    useEffect(() => {
        axios.get(API).then((r) => setUsers(r.data));
    }, []);

    return (
        <ul>
            {users.map((u) => (
                <li key={u.id}>{u.name} — {u.email}</li>
            ))}
        </ul>
    );
}
Key point

Notice u._id (Mongo) vs u.id (SQL). That is the only visible difference to the frontend. Standardize your API responses so the UI never has to care.

15. When to use which

Choose MongoDB + Mongoose when

  • Your schema is still evolving (MVP, startup, discovery phase).
  • Data is naturally document-shaped — posts, comments, nested configs, catalogs.
  • You want speed of iteration — no migrations, add fields freely.
  • You need horizontal scale out of the box.
  • The workload is read-heavy with a flexible shape (CMS, feeds, product catalogs).
  • Your whole team is JS-only and you want one mental model.

Choose SQL (Postgres / MySQL) when

  • Data is highly relational — users ↔ orders ↔ items ↔ payments.
  • You need strict ACID transactions (banking, checkout, bookings).
  • Reporting and analytics are core — SQL wins.
  • Data integrity must be enforced by the DB (constraints, foreign keys).
  • Your team already knows SQL.
  • Compliance requires rigid schemas (finance, healthcare).
  • You need complex joins across many tables.

Choose BOTH (polyglot persistence) when

  • You have transactional and content needs in one app.
  • Example e-commerce: Postgres for users, orders, payments, inventory; Mongo for product descriptions, reviews, activity logs, and search indexes.

16. How to use BOTH in the same MERN app

A real production pattern: one Express API, each database abstracted behind its own module.

Folder structure

A polyglot app stays maintainable when each database is hidden behind its own module: config/ holds the connections, models/ holds Mongoose models, repositories/ holds SQL query functions, and routes/ stay unaware of which driver is underneath. The layout below keeps Mongo access (models) separate from SQL access (repositories).

server/
  config/
    mongo.js       (Mongoose connection)
    postgres.js    (pg Pool connection)
  models/          (Mongoose models)
    Product.js
  repositories/    (SQL access functions)
    orders.repo.js
  routes/
    products.js    (uses Mongo)
    orders.js      (uses SQL)
  server.js

config/mongo.js

Each database gets its own connection module, so nothing in the app hard-codes a driver detail.

const mongoose = require("mongoose");
module.exports = () => mongoose.connect(process.env.MONGO_URI);

config/postgres.js

The SQL pool exposes the same small query() surface used by the SQL routes.

const { Pool } = require("pg");
const pool = new Pool({ connectionString: process.env.DATABASE_URL });
module.exports = { query: (t, p) => pool.query(t, p), pool };

server.js

The entry point wires both databases together: it opens the Mongo connection once at boot, then mounts the product (Mongo) and order (SQL) route groups. The SQL pool connects lazily on its first query, so it is not started here; no route imports a driver directly.

require("dotenv").config();
const express = require("express");
const connectMongo = require("./config/mongo");

const app = express();
app.use(express.json());

connectMongo().then(() => console.log("Mongo ready"));  // open the Mongo pool once at startup

app.use("/api/products", require("./routes/products"));
app.use("/api/orders",   require("./routes/orders"));

app.listen(5000, () => console.log("Server on :5000"));

Route using Mongo (products)

This route reads from Mongoose and is unaware that SQL exists elsewhere in the app.

const router = require("express").Router();
const Product = require("../models/Product");

router.get("/", async (req, res) => {
    res.json(await Product.find().lean());
});

module.exports = router;

Route using SQL (orders)

This sister route talks SQL through the pool wrapper referenced across the app by id only.

const router = require("express").Router();
const db = require("../config/postgres");

router.get("/", async (req, res) => {
    const { rows } = await db.query("SELECT * FROM orders ORDER BY created_at DESC");
    res.json(rows);
});

module.exports = router;
Key point

Golden rules of polyglot persistence:

  • One database owns one domain. Never write the same entity to both.
  • Reference across databases by ID, not by join.
  • No cross-database transactions. Use the outbox pattern or an event bus (Kafka / RabbitMQ).
  • Abstract each database behind a module; routes should never know raw driver details.
  • Document clearly which domain lives where.

17. Best practices & security

MongoDB / Atlas

  1. Never commit MONGO_URI — use .env and a secret manager.
  2. Whitelist IPs in Atlas — avoid 0.0.0.0/0 in production.
  3. Least-privilege DB users — one user per service, scoped to one database.
  4. Enable backups (Atlas M10+ has continuous backup).
  5. Index the fields you query — email, userId, createdAt.
  6. Validate input with Mongoose + Joi / Zod.
  7. Always paginate — never return unbounded find() results.
  8. Use .lean() on read-only queries for a 2–5x speed boost.
  9. Rotate credentials regularly and enable audit logs.

SQL (Postgres / MySQL)

  1. Parameterized queries only — never concatenate SQL strings.
  2. Use migrations (Prisma Migrate / Knex / Flyway) — no manual ALTER in production.
  3. Index foreign keys and hot WHERE columns.
  4. Connection pooling always (pg Pool, mysql2 pool).
  5. Transactions for multi-step writes — BEGIN ... COMMIT.
  6. Read replicas for heavy read workloads.
  7. Backups + point-in-time recovery enabled.
  8. Principle of least privilege on DB roles.
  9. SSL/TLS enforced on all remote connections (sslmode=require).
  10. Never store plaintext passwords — bcrypt/argon2.

General MERN rules

  • Keep DB credentials server-side only.
  • Validate all input at the API boundary.
  • Rate-limit auth and mutation endpoints.
  • Log errors, not secrets.
  • Separate dev / staging / prod databases and credentials.

Key point

The 10-second decision: shape changes often and queries stay flexible → Mongo; money moves and rules are strict → SQL; both → split by domain, reference by ID, and never join across databases.

Quick recap

  • MongoDB is document-shaped; SQL is relational. Learn both and choose by data shape.
  • Atlas M0 is the free path to a hosted MongoDB; store the URI in .env.
  • Mongoose: connect once, then schema → model → CRUD, plus populate and aggregation.
  • SQL: pool connections; raw pg/mysql2 with parameterized queries, or Prisma.
  • MySQL command reference: DDL (CREATE/ALTER/DROP), transactions (COMMIT/ROLLBACK/AUTOCOMMIT), DML, and JOIN/GROUP BY queries.
  • The Express API looks identical whether the data layer is Mongo or SQL — only the driver changes.
  • Choose Mongo for evolving/JSON data; SQL for relational, transactional, analytics workloads.
  • Polyglot: one DB per domain, reference by ID, no cross-DB transactions.
  • Always pool connections, parameterize SQL, paginate, and keep secrets out of .git.
