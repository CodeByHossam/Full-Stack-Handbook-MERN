AWS RDS MySQL + Node.js

A complete lifecycle guide: create an AWS account, provision an RDS MySQL database, connect from MySQL Workbench and Node.js, and fix the ten problems that come up in practice.

Database AWS RDS MySQL + mysql2

1. Introduction

This guide walks through the full lifecycle of setting up a relational database (MySQL) on AWS using RDS (Relational Database Service), then connecting it to MySQL Workbench for administration and to Node.js using the mysql2 package.

Note

Every step explains why it matters, not just how to do it. No prior AWS experience is assumed.

2. AWS account creation

AWS hosts your managed MySQL database. RDS is a managed service: AWS handles backups, patching, and hardware, while you handle the schema and data.

Sign up

  1. Go to https://aws.amazon.com/ and click Create an AWS Account.
  2. Enter an email address (verification is required), a strong password, and an account name such as my-dev-account.
  3. Choose Personal or Business account type.
  4. Enter payment information — a card is required even for the free tier.
  5. Verify your identity via phone/SMS.
  6. Select the Basic Support Plan (Free).
  7. Sign in to the AWS Management Console at https://console.aws.amazon.com/.

IAM best practices

Do not use the root account for daily work. Instead:

  1. In the Console, search for IAM.
  2. Go to Users → Create user.
  3. Name it, for example dev-admin.
  4. Attach the policy AmazonRDSFullAccess.
  5. Enable console access and set a password.
  6. Optionally enable MFA.
  7. Use this user for all RDS-related work.
Key point

The root account is the master key to your entire AWS kingdom. Lock it away, enable MFA, and never use it for day-to-day tasks.

3. Choosing a region

Pick a region close to you (for example us-east-1, eu-west-1, or ap-south-1). This reduces latency and can affect free tier availability.

Warning

Stick to one region for all resources. Cross-region resources incur data transfer costs.

4. Creating an RDS MySQL database

Navigate to RDS

  1. In the AWS Console search bar, type RDS.
  2. Open the RDS Console at https://console.aws.amazon.com/rds/.
  3. Ensure you are in the correct region (top-right corner).

Choose a creation method

Create the database

Click Create database. Provisioning takes 5–10 minutes. Status goes from Creating to Available. Then copy the Endpoint, for example my-app-mysql.abc123.us-east-1.rds.amazonaws.com.

5. Configuring security groups

A security group is a virtual firewall. By default RDS blocks all inbound traffic, so you must explicitly allow your IP.

  1. On the RDS instance page, scroll to Connectivity & security.
  2. Click the VPC security group link (for example sg-0abc123...).
  3. In the Inbound rules tab, click Edit inbound rules.
  4. Add a rule:
TypeProtocolPortSourceDescription
MySQL/AuroraTCP3306My IPLocal dev access
Warning

Never use 0.0.0.0/0 (anywhere) in production — it exposes your database to the entire internet. Use My IP or a specific CIDR range.

Outbound rules are typically All traffic by default — leave them as-is.

7. Connecting with Node.js

Node connects to RDS through the mysql2 driver. Set up a small project, load credentials from .env, then verify the connection with a trivial query before writing real code.

mkdir aws-rds-node-demo
cd aws-rds-node-demo
npm init -y
npm install mysql2 dotenv
  • mysql2 — promise-based MySQL driver for Node.js, faster and more modern than mysql.
  • dotenv — loads environment variables from a .env file.

Create the .env file

Credentials go in the environment, never in source. Each variable matches a mysql2 connection option so the config stays a one-line mapping.

DB_HOST=my-app-mysql.abc123.us-east-1.rds.amazonaws.com
DB_PORT=3306
DB_USER=admin
DB_PASSWORD=Str0ngPass!2024
DB_NAME=appdb
Warning

Add .env to .gitignore immediately. Never commit credentials to Git.

Basic connection test

A sanity-check script connects, runs SELECT 1, prints the result, and closes the connection — the smallest possible proof that your credentials, security group, and endpoint are all correct.

require("dotenv").config();
const mysql = require("mysql2/promise");

async function main() {
    const connection = await mysql.createConnection({
        host: process.env.DB_HOST,
        port: Number(process.env.DB_PORT),  // env vars are strings — cast to number
        user: process.env.DB_USER,
        password: process.env.DB_PASSWORD,
        database: process.env.DB_NAME
    });

    try {
        const [rows] = await connection.query("SELECT 1 + 1 AS result");
        console.log("Connection OK. Result:", rows[0].result);
    } catch (err) {
        console.error("Connection failed:", err.message);
    } finally {
        await connection.end();
    }
}

main();

Using a connection pool (production pattern)

Export a single pool instead of opening a connection per request: connections are reused, so latency drops and concurrency scales under load.

require("dotenv").config();
const mysql = require("mysql2/promise");

const pool = mysql.createPool({
    host: process.env.DB_HOST,
    port: Number(process.env.DB_PORT),
    user: process.env.DB_USER,
    password: process.env.DB_PASSWORD,
    database: process.env.DB_NAME,
    waitForConnections: true,   // queue a request while all connections are busy
    connectionLimit: 10,
    queueLimit: 0               // unlimited queue size
});

module.exports = pool;
const pool = require("./db");

async function getUsers() {
    const [rows] = await pool.query("SELECT * FROM users");
    return rows;
}
Key point

Pools reuse connections, reduce latency, and handle concurrency gracefully. Never open a new connection per request in production.

8. Full working example: insertData.js

Project structure

The demo is deliberately flat: one small script per task, so you can run each step in isolation. test-connection.js proves connectivity, insertData.js writes rows, and readData.js reads them back. Only .env and node_modules/ must never be committed.

aws-rds-node-demo/
├── .env
├── .gitignore
├── package.json
├── test-connection.js
├── insertData.js
└── readData.js

insertData.js

Writes two rows in one statement using ? placeholders. The values array fills them in order — never concatenate them into the SQL string.

require("dotenv").config();
const mysql = require("mysql2/promise");

async function main() {
    const connection = await mysql.createConnection({
        host: process.env.DB_HOST,
        port: Number(process.env.DB_PORT),
        user: process.env.DB_USER,
        password: process.env.DB_PASSWORD,
        database: process.env.DB_NAME
    });

    try {
        await connection.query(
            `
            INSERT INTO users (name, email)
            VALUES (?, ?), (?, ?)
            `,
            [
                "John Smith",
                "john@example.com",
                "Sarah Johnson",
                "sarah@example.com"
            ]
        );

        console.log("2 users inserted successfully");
    } catch (error) {
        console.error("Database error:", error);
    } finally {
        await connection.end();
    }
}

main();

readData.js (verify)

This script mirrors insertData.js but runs a SELECT and prints the rows with console.table(), the quickest way to confirm the writes actually landed. Seeing the same rows later in Workbench proves both tools hit the same database.

require("dotenv").config();
const mysql = require("mysql2/promise");

async function main() {
    const connection = await mysql.createConnection({
        host: process.env.DB_HOST,
        port: Number(process.env.DB_PORT),
        user: process.env.DB_USER,
        password: process.env.DB_PASSWORD,
        database: process.env.DB_NAME
    });

    try {
        const [rows] = await connection.query("SELECT * FROM users");  // mysql2 returns [rows, fields]
        console.table(rows);   // destructure: first element is the result rows
    } catch (error) {
        console.error("Database error:", error);
    } finally {
        await connection.end();
    }
}

main();

Run both, then verify in Workbench with SELECT * FROM users;. The same two rows confirm Node.js and Workbench hit the same RDS database.

9. Troubleshooting & problems solved

These are real problems encountered during RDS + Node.js + Workbench setups, with their likely causes and fixes.

Problem 1 — ECONNREFUSED / connection timeout

Symptom: connect ETIMEDOUT or connect ECONNREFUSED <endpoint>:3306.

Cause: The RDS instance is not publicly accessible and/or the security group does not allow your IP.

Fix: Modify RDS → Connectivity → Publicly accessible: Yes, then add an inbound security group rule for MySQL/Aurora on port 3306 from My IP. Wait 1–2 minutes and retest with telnet <endpoint> 3306.

Problem 2 — Access denied for user 'admin'

Symptom: Access denied for user 'admin'@'<ip>' (using password: YES) even though the password looks correct.

Cause: Wrong password (typo or leftover whitespace in .env), username mismatch (the master user is not root), or special characters that broke parsing.

Fix: Remove trailing spaces and quotes in .env, use a password without shell-problematic characters (!, $, #) for CLI work, and re-verify the username from the RDS console.

Problem 3 — ER_NOT_SUPPORTED_AUTH_MODE

Symptom: Client does not support authentication protocol requested by server.

Cause: MySQL 8 defaults to caching_sha2_password, which the older mysql package does not support.

Fix: Use mysql2, which supports it natively. Alternatively: ALTER USER 'admin'@'%' IDENTIFIED WITH mysql_native_password BY 'YourPassword'; FLUSH PRIVILEGES;

Problem 4 — IAM authentication works in CLI but not Node.js

Symptom: The MySQL CLI connects with an IAM token, but mysql2 throws Access denied.

Cause: The mysql2 driver needs the cleartext plugin enabled when using IAM tokens as passwords.

Fix: Add enableCleartextPlugin: true to the connection config. Check the mysql2 docs for the exact option name in your version.

Problem 5 — ETIMEDOUT only from Node.js

Symptom: Workbench connects but Node.js times out.

Cause: A corporate VPN/firewall blocking Node's outbound traffic, or DB_PORT read as a string instead of a number.

Fix: Cast the port with port: Number(process.env.DB_PORT). Always cast environment variables to their expected types.

Problem 6 — Free tier instance not available

Symptom: The Free tier template is greyed out or missing.

Cause: You already have an active RDS instance, the account predates a Free Tier rule change, or the region does not support the free tier class.

Fix: Delete unused instances, switch to a supported region such as us-east-1, or use the Sandbox option.

Problem 7 — Node.js script hangs and never exits

Symptom: node insertData.js prints success but the terminal never returns to the prompt.

Cause: The MySQL connection was not closed, so the open socket keeps the event loop alive.

Fix: Always close the connection in a finally block with await connection.end(). In production, use a pool that manages lifecycle automatically.

Problem 8 — ER_NO_SUCH_TABLE

Symptom: Table 'appdb.users' doesn't exist.

Cause: RDS does not auto-create tables — the initial database exists but has no schema.

Fix: Run CREATE TABLE users (...) in Workbench before running insertData.js. Use a migration tool (knex, sequelize, prisma) to manage schema in code.

Problem 9 — ER_ACCESS_DENIED_ERROR after changing the password

Symptom: After rotating the master password, Node.js fails but Workbench works.

Cause: Node cached the old connection or .env was not updated.

Fix: Update .env, restart the Node process (env vars load at startup), and restart the app if using a pool. Use AWS Secrets Manager for automatic rotation.

Problem 10 — SSL/TLS required by RDS

Symptom: Connections using insecure transport are prohibited.

Cause: RDS enforces SSL for some MySQL versions (require_secure_transport = ON).

Fix: Add SSL config pointing at the RDS CA bundle, for example ssl: { ca: fs.readFileSync("./global-bundle.pem") }. Download it from the AWS RDS SSL documentation.

10. Cleanup & cost management

RDS is not free forever — even the free tier expires after 12 months.

  1. Go to the RDS Console and select your instance.
  2. Actions → Delete.
  3. Uncheck Create final snapshot (for dev) or check it (for prod).
  4. Type delete me to confirm.

Also check for manual snapshots, unused Elastic IPs, and accumulated CloudWatch Logs. Set a Billing Alarm for $1 to be notified early.

Quick recap

  • Create an AWS account, lock the root user away, and work through an IAM user with AmazonRDSFullAccess.
  • Pick one region and stay in it to avoid cross-region transfer costs.
  • Use Standard Create with the Free tier template, db.t4g.micro, 20 GB gp3, port 3306.
  • Make the instance publicly accessible and open inbound 3306 to My IP only.
  • Connect from Workbench, then from Node with mysql2/promise and a .env file ignored by Git.
  • Use a connection pool in production; always end() a single connection in finally.
  • Parameters are placeholders (?) — never string-concatenate SQL.
  • Most failures are network access, credentials, the wrong driver, a missing table, or SSL.
  • Delete the instance when finished and set a billing alarm.
