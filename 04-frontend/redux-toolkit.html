Redux Toolkit + RTK Query

Global client state with Redux Toolkit, and server data with RTK Query's built-in fetching, caching and cache invalidation.

Frontend State Management

When to use Redux

Good candidates for Redux: authentication, shopping cart, user preferences and global UI state.

State typeTool
Local component stateuseState
Server / API dataRTK Query
Global client stateRedux
Key point

Don't put everything in Redux. Reserve it for state that genuinely needs to be shared and global.

Install

Redux Toolkit (RTK) is the modern, batteries-included way to write Redux — far less boilerplate than hand-written action types and reducers. react-redux provides the useSelector and useDispatch hooks that connect components to the store.

npm install @reduxjs/toolkit react-redux

Store

The store is the single object that holds all global state. configureStore wires up your slice reducers, the dev tools and the default middleware. Register each slice under the key you will later read it by.

import { configureStore } from "@reduxjs/toolkit";
import authReducer from "./authSlice";
import cartReducer from "./cartSlice";

const store = configureStore({
    reducer: {
        auth: authReducer,   // exposed as state.auth
        cart: cartReducer    // exposed as state.cart
    }
});

export default store;

Provider

react-redux shares the store through React context, so the app must be wrapped once, at the root. Everything inside the provider can then call the Redux hooks.

// main.jsx
import { Provider } from "react-redux";
import store from "./store";

<Provider store={store}>
    <App />
</Provider>

Wrapping the app in Provider is what lets every component access the store.

Slice (actions & reducers)

A slice bundles one part of the state with the reducers that update it. createSlice generates the action creators and action types from each reducer name automatically, so you never write them by hand.

import { createSlice } from "@reduxjs/toolkit";

const initialState = {
    user: null,
    token: null,
    isAuthenticated: false
};

const authSlice = createSlice({
    name: "auth",              // prefix for generated action types
    initialState,
    reducers: {
        login: (state, action) => {          // reducer = how state changes
            state.user = action.payload.user;
            state.token = action.payload.token;
            state.isAuthenticated = true;
        },
        logout: (state) => {
            state.user = null;
            state.token = null;
            state.isAuthenticated = false;
        }
    }
});

export const { login, logout } = authSlice.actions;   // action creators
export default authSlice.reducer;                     // used in configureStore

Redux Toolkit uses Immer, so you can write "mutating" assignments inside reducers and it produces immutable updates.

useSelector & useDispatch

These two hooks are how components talk to the store. useSelector reads a piece of state and re-renders the component when that piece changes; useDispatch returns dispatch, which you call with an action to request a change. Notice the component never edits state directly — it dispatches and lets the reducer decide.

Read state with useSelector:

import { useSelector } from "react-redux";

const user = useSelector((state) => state.auth.user);   // select one field

Send actions with useDispatch:

import { useDispatch } from "react-redux";
import { login, logout } from "./authSlice";

const dispatch = useDispatch();

dispatch(login({ user, token }));   // action creator → { type, payload }
dispatch(logout());

Payload & nested state

action.payload contains the data sent with the action. Inside the reducer you read it as action.payload.user, action.payload.token.

const state = {
    auth: {
        user: { name: "Alice" },
        token: "abc"
    },
    cart: {
        items: []
    }
};

// Access
state.auth.user;
state.auth.token;
state.cart.items;

Async logic: createAsyncThunk

Reducers must stay pure, so you cannot fetch inside one. createAsyncThunk runs the async work outside the store and then dispatches a plain action for each phase: pending, fulfilled, and rejected. You handle those three in the slice's extraReducers, typically driving a status flag the UI can read.

This is the manual alternative to RTK Query (below): use it for one-off async actions that update client state; reach for RTK Query when you are talking to an API with caching.

import { createSlice, createAsyncThunk } from "@reduxjs/toolkit";

// The thunk returns a promise; RTK dispatches pending/fulfilled/rejected for it
export const fetchData = createAsyncThunk("counter/fetchData", async () => {
    const response = await fetch("/api/posts/1");
    return response.json();      // becomes action.payload on "fulfilled"
});

const counterSlice = createSlice({
    name: "counter",
    initialState: { value: 0, data: null, status: "idle" },  // status drives the UI
    reducers: {
        increment: (state) => { state.value += 1; }
    },
    extraReducers: (builder) => {
        builder
            .addCase(fetchData.pending, (state) => {
                state.status = "loading";
            })
            .addCase(fetchData.fulfilled, (state, action) => {
                state.status = "succeeded";
                state.data = action.payload;
            })
            .addCase(fetchData.rejected, (state) => {
                state.status = "failed";
            });
    }
});

export const { increment } = counterSlice.actions;
export default counterSlice.reducer;

In a component, dispatch the thunk once on mount and render each phase from status:

const { data, status } = useSelector((state) => state.counter);
const dispatch = useDispatch();

useEffect(() => {
    if (status === "idle") {      // guard so a re-render does not refetch forever
        dispatch(fetchData());
    }
}, [status, dispatch]);

if (status === "loading") return <p>Loading...</p>;
if (status === "failed") return <p>Failed to load data</p>;
return data ? <pre>{JSON.stringify(data, null, 2)}</pre> : null;
Key point

createAsyncThunk pairs with extraReducers, not reducers: reducers handle actions you define, while extraReducers listens for the thunk's lifecycle actions.

RTK Query: createApi & fetchBaseQuery

RTK Query handles GET, POST, PUT, PATCH and DELETE plus caching, loading and error state, refetching and cache invalidation.

import { createApi, fetchBaseQuery } from "@reduxjs/toolkit/query/react";

export const apiSlice = createApi({
    reducerPath: "api",                              // key RTK Query uses in the store
    baseQuery: fetchBaseQuery({ baseUrl: "/api" }),  // shared request config for every call
    endpoints: (builder) => ({
        getUsers: builder.query({
            query: () => "/users"                     // relative to baseUrl
        })
    })
});

// RTK Query generates a hook named use<Endpoint>Query for you
export const { useGetUsersQuery } = apiSlice;

Queries: generated hooks, loading/error, params

Each query endpoint becomes a hook that fetches and caches its data automatically. The hook returns data plus loading and error flags, and re-fetches when its argument changes — no manual useEffect needed.

const { data, isLoading, isError, error } = useGetUsersQuery();   // no params

if (isLoading) return <p>Loading...</p>;
if (isError) return <p>Error loading users</p>;

return (
    <div>
        {data?.map((user) => (
            <p key={user._id}>{user.name}</p>
        ))}
    </div>
);

Define a parameterized query and pass the argument to the hook:

getUser: builder.query({
    query: (id) => `/users/${id}`   // argument is injected into the URL
});

const { data: user } = useGetUserQuery(id);   // refetches whenever id changes

Mutations (POST / PUT / PATCH / DELETE)

Mutations model writes. Each one generates a use<Endpoint>Mutation hook that returns a trigger function plus status flags — you call the trigger to actually send the request (unlike queries, which fire on render).

createUser: builder.mutation({
    query: (userData) => ({
        url: "/users",
        method: "POST",       // writes always name their HTTP method
        body: userData
    })
});

// Component
const [createUser, { isLoading, isError }] = useCreateUserMutation();   // trigger + flags

const handleSubmit = async () => {
    await createUser({ name: "Alice", email: "test@email.com" });
};
updateUser: builder.mutation({
    query: ({ id, ...data }) => ({
        url: `/users/${id}`,
        method: "PATCH",   // partial update: only the fields in `data`
        body: data
    })
});

deleteUser: builder.mutation({
    query: (id) => ({
        url: `/users/${id}`,
        method: "DELETE"   // usually no body
    })
});

See Unwrapping results & handling errors for turning the trigger into a clean try/catch.

Unwrapping results & handling errors

A mutation trigger always resolves its promise — even on a failed request — because RTK Query reports errors as data. The returned object is "wrapped": it exposes data and error fields instead of rejecting. You can inspect it manually, or call .unwrap() to turn it into a normal promise that rejects on error.

ApproachOn failureHow you handle it
Wrapped resultresolves with { error }check result.error yourself
.unwrap()rejectsstandard try/catch
 
// Wrapped: you must check error manually
const result = await createNote({ title: "" });
if (result.error) {
    console.error("RTK error:", result.error);
} else {
    console.log("Created:", result.data);
}

// Unwrapped: catch it like any other promise rejection
try {
    const note = await createNote({ title: "" }).unwrap();
    console.log("Created:", note);      // note IS the data, not { data }
} catch (err) {
    console.error("Failed:", err);      // err is the serialized error
}
Key point

A query hook manages fetching for you — do not await it; read data/isLoading/isError from the returned object. Mutation triggers and lazy queries return promises, so those you await (optionally chained with .unwrap()).

Cache tags: providesTags & invalidatesTags

Tags tell RTK Query which cached data becomes stale after a mutation.

getProducts: builder.query({
    query: () => "/products",
    providesTags: ["Products"]   // this cached data IS the "Products" tag
});

deleteProduct: builder.mutation({
    query: (id) => ({
        url: `/products/${id}`,
        method: "DELETE"
    }),
    invalidatesTags: ["Products"]   // mark that cache stale → auto refetch
});

After a mutation invalidates the "Products" tag, RTK Query knows that cache is outdated and can refetch it automatically.

Adding the API slice to the store & base URL

Two extra steps make RTK Query work: register its reducer under its reducerPath, and append its middleware so caching, polling and invalidation actually run.

const store = configureStore({
    reducer: {
        auth: authReducer,
        cart: cartReducer,
        [apiSlice.reducerPath]: apiSlice.reducer   // "api" key from reducerPath
    },
    middleware: (getDefaultMiddleware) =>
        getDefaultMiddleware().concat(apiSlice.middleware)   // enable RTK Query
});

Use environment variables for the base URL so development and production differ cleanly:

baseQuery: fetchBaseQuery({
    baseUrl: import.meta.env.VITE_API_URL
})

For example http://localhost:5000/api in development and https://yourdomain.com/api in production.

Auth: Bearer token with prepareHeaders

prepareHeaders runs on every request, so it is the natural place to read the JWT from the store and attach it. No need to remember the header at each call site.

prepareHeaders: (headers, { getState }) => {
    const token = getState().auth.token;   // read directly from the store

    if (token) {
        headers.set("authorization", `Bearer ${token}`);   // standard Bearer scheme
    }

    return headers;
}

This automatically attaches the JWT from the auth slice to every request.

Complete apiSlice example

One createApi call can define the base URL, auth headers, tag types and every endpoint. The generated hooks are exported at the bottom for components to import.

export const apiSlice = createApi({
    reducerPath: "api",

    baseQuery: fetchBaseQuery({
        baseUrl: "/api",
        prepareHeaders: (headers, { getState }) => {      // runs on every call
            const token = getState().auth.token;
            if (token) {
                headers.set("authorization", `Bearer ${token}`);
            }
            return headers;
        }
    }),

    tagTypes: ["Users", "Products"],   // declare tags used for invalidation

    endpoints: (builder) => ({
        getProducts: builder.query({
            query: () => "/products",
            providesTags: ["Products"]
        }),

        createProduct: builder.mutation({
            query: (data) => ({
                url: "/products",
                method: "POST",
                body: data
            }),
            invalidatesTags: ["Products"]
        })
    })
});

export const {
    useGetProductsQuery,
    useCreateProductMutation
} = apiSlice;   // import these hooks in components

Persisting state with redux-persist

Redux state lives in memory, so a page reload resets it. redux-persist saves chosen slices to localStorage and rehydrates them on startup — handy for keeping a logged-in user or a cart across refreshes.

Install it:

npm install redux-persist

Wrap each reducer you want to keep in persistReducer, then create a persistor from the store:

import { configureStore } from "@reduxjs/toolkit";
import { persistStore, persistReducer } from "redux-persist";
import storage from "redux-persist/lib/storage";
import authReducer from "./authSlice";

const persistConfig = {
    key: "root",     // the localStorage key
    storage          // defaults to localStorage on the web
};

// The wrapped reducer reads saved state in and writes updates back out
const persistedAuth = persistReducer(persistConfig, authReducer);

export const store = configureStore({
    reducer: { auth: persistedAuth }
});

export const persistor = persistStore(store);   // controls save / rehydrate

Finally, wrap the app in PersistGate so React waits for the saved state to load before rendering the tree:

import { Provider } from "react-redux";
import { PersistGate } from "redux-persist/integration/react";
import { store, persistor } from "./store";

<Provider store={store}>
    <PersistGate loading={null} persistor={persistor}>
        <App />
    </PersistGate>
</Provider>
Watch out

Do not persist the RTK Query api slice — it already caches server data, and rehydrating a stale cache causes confusing bugs. Persist only the slices you choose (for example via a whitelist), and never persist secrets such as a raw JWT unless you accept the XSS risk.

Redux vs RTK Query vs useState

ToolBest forExample
useStateLocal component stateA search input

Note

Key terms: store holds global state, a slice controls one part, an action describes what happened, a reducer changes state, dispatch sends an action, a selector reads state, and middleware runs between dispatch and reducer.

Quick recap

  • Use Redux for global client state — not everything.
  • configureStore builds the store; createSlice holds state + reducers + actions.
  • Wrap the app in <Provider store={store}>.
  • Read with useSelector, write with useDispatch; data travels via action.payload.
  • RTK Query (createApi + fetchBaseQuery) handles queries and mutations with generated hooks.
  • Hooks expose data, isLoading, isError and accept parameters.
  • providesTags / invalidatesTags drive cache invalidation.
  • Attach the JWT with prepareHeaders and register apiSlice.middleware.
  • createAsyncThunk + extraReducers handle async lifecycle (pending/fulfilled/rejected).
  • .unwrap() on a mutation trigger routes failures to try/catch; query hooks are not awaited.
  • redux-persist + PersistGate keep chosen slices across reloads — never the api slice.
