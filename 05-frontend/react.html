Frontend Components & Hooks

The React core idea

A React app is a tree of components. Each component receives props (data in) and owns state (data it manages). When state or props change, React re-renders that part of the UI.

Component
   ↓
Props (parent → child)
   ↓
State (owned locally)
   ↓
Render (JSX)
   ↓
User event
   ↓
State update → re-render

The mechanics of state and effects (snapshots, why setState isn't immediate, when to use useEffect) are owned by React State & useEffect. This page covers everyday component patterns.

Components & JSX

A component is a reusable function that returns JSX — markup that looks like HTML but compiles to React.createElement(...) calls, so structure and logic live together in one file. Split the UI into small, single-purpose components and compose them; a component re-renders only when its props or state change.

function UserCard({ name, age }) {   // props destructured by name
    // A component must return ONE root element, so wrap siblings in a fragment
    return (
        <div>
            {/* braces embed any JavaScript expression — here, the props */}
            <h2>{name}</h2>
            <p>{age}</p>
        </div>
    );
}

JSX uses className instead of class and htmlFor instead of for — see HTML in React.

Props

Props are data passed from a parent to a child. They are read-only inside the child.

Data flows one way (down the tree), so a child can never silently change what its parent passed — that keeps ownership of the data clear. To let a child change parent data, the parent passes a callback prop (for example onSelect) that the child calls.

function UserCard({ name, age }) {   // receive props as one object
    return (
        <div>
            <h2>{name}</h2>
            <p>{age}</p>
        </div>
    );
}

// Parent — strings use quotes; numbers, arrays and variables use braces
<UserCard name="Alice" age={42} />

Props use array/object destructuring — covered in JavaScript Basics.

State with arrays & objects

Never mutate state directly — always create a new value. This is where the spread operator earns its keep.

const [items, setItems] = useState([]);

// Add — spread copies the old array, then append the new item
setItems((prev) => [...prev, newItem]);

// Remove — filter returns a new array without the matching item
setItems((prev) => prev.filter((item) => item.id !== id));

// Update one item — map builds a new array, replacing only the match
setItems((prev) =>
    prev.map((item) =>
        item.id === id ? { ...item, name: "New Name" } : item
    )
);

// Update one property of an object — spread keeps the untouched fields
const [user, setUser] = useState({ name: "", age: 0 });
setUser((prev) => ({ ...prev, name: "Alice" }));
Key point

Using the updater form setItems(prev => ...) is safer when the new value depends on the previous one. The full state model is in React State & useEffect.

Events

React attaches event handlers as props, using camelCase names (onClick, onChange, onSubmit). You pass a function and React calls it later with a synthetic event that wraps the native one, so the same handler behaves the same across browsers.

<button onClick={handleClick}>Click</button>

React event handlers are rules you must internalize:

FormMeaning
onClick={handleClick}Correct: passes the function, React calls it on click
onClick={handleClick()}Wrong: calls the function immediately during render
onClick={() => handleClick(id)}Correct: wraps in a new function to pass an argument later

See React State & useEffect for the full explanation of why.

Forms & controlled inputs

A controlled input has its value driven by state and its updates handled by onChange.

Because the field's value comes from state, React is the single source of truth: you can validate, reset, or pre-fill it at any time. An uncontrolled input keeps its own value internally — fine for simple cases, but harder to read or clear.

const [name, setName] = useState("");

<input
    value={name}                                 // state drives the text shown
    onChange={(e) => setName(e.target.value)}    // typing writes back to state
/>

e.target.value is the text the user typed. For a full form:

function Form() {
    const [email, setEmail] = useState("");

    const handleSubmit = (e) => {
        e.preventDefault();   // stop the browser's full-page form reload
        console.log(email);
    };

    return (
        <form onSubmit={handleSubmit}>
            <label htmlFor="email">Email</label>
            <input
                id="email"
                type="email"
                value={email}
                onChange={(e) => setEmail(e.target.value)}
            />
                <button type="submit">Submit</button>
            </form>
        );
}

Submitting a form to an API

A controlled form is the front half; sending its data to your Express API is the back half. Track three things in state — the field values, a loading flag, and an error message — so the UI reflects exactly what is happening while the request is in flight.

e.preventDefault() stops the browser's native full-page submit, JSON.stringify turns the object into a JSON body, and response.ok is false for 4xx/5xx responses. Note that a network failure rejects and lands in catch, but a 400/500 does not — you must check the status yourself.

function MyForm() {
    const [inputValue, setInputValue] = useState("");
    const [loading, setLoading] = useState(false);
    const [error, setError] = useState("");

    const handleSubmit = async (e) => {
        e.preventDefault();        // stop the browser's full-page reload
        setLoading(true);          // disable the button and show feedback
        setError("");

        try {
            const response = await fetch("/api/submit", {
                method: "POST",
                headers: { "Content-Type": "application/json" },
                body: JSON.stringify({ name: inputValue })   // send JSON, not a form body
            });

            if (!response.ok) {
                // a 4xx/5xx response does NOT throw — check it yourself
                throw new Error("Request failed with status " + response.status);
            }

            setInputValue("");     // clear the field on success
        } catch (err) {
            setError(err.message);  // store the message and render it below
        } finally {
            setLoading(false);     // always re-enable the button
        }
    };

    return (
        <form onSubmit={handleSubmit}>
            <label htmlFor="name">Name</label>
            <input
                id="name"
                value={inputValue}
                onChange={(e) => setInputValue(e.target.value)}
            />
            <button type="submit" disabled={loading}>
                {loading ? "Submitting..." : "Submit"}
            </button>
            {error && <p className="error">{error}</p>}
        </form>
    );
}
Watch out

fetch only rejects on network errors. A 400 or 500 still resolves, so check response.ok (or the status) before treating the call as successful.

With axios the same request is shorter, and axios does reject on non-2xx status codes:

import axios from "axios";

await axios.post("/api/submit", { name: inputValue });   // throws on 4xx/5xx
Note

For repeated or cached server calls, prefer RTK Query mutations over hand-written fetch. Data fetching on mount lives in useEffect.

Conditional rendering

JSX has no if statement — you place ordinary JavaScript expressions inside braces to decide what appears. Use a ternary (? :) when you need one thing or another, and && when you only want to render something in one case. Returning null renders nothing.

{isLoggedIn ? <Dashboard /> : <Login />}   // either / or

{isAdmin && <AdminPanel />}            // only when true

Use a ternary for either/or and && to render only when true. Both are plain JavaScript operators (see JavaScript Basics).

Common mistake

{count && <Badge />} renders a literal 0 when count is 0 (because 0 is falsy but still rendered). Guard with a boolean: {count > 0 && <Badge />}.

Rendering lists

Turn an array into an array of elements with map(). Each element needs a stable, unique key so React can match items between renders — without it React re-creates DOM nodes and loses input focus and component state. Use a database _id, not the array index, so keys stay stable when order changes.

{products.map((product) => (
    <ProductCard
        key={product._id}      // stable identity for this row
        product={product}
    />
))}
Warning

Always give each list item a stable, unique key (usually a database _id) so React can track items efficiently.

The common CRUD pattern on a product list:

// Filter
const available = products.filter((p) => p.stock > 0);

// Find one
const product = products.find((p) => p._id === id);

// Update one
setProducts((prev) =>
    prev.map((p) =>
        p._id === id ? { ...p, stock: p.stock - 1 } : p
    )
);

// Delete one
setProducts((prev) => prev.filter((p) => p._id !== id));

useEffect & fetching data

useEffect runs side effects after render — API calls being the most common.

useEffect(() => {
    fetch("/api/users")
        .then((res) => res.json())
        .then((data) => setUsers(data));
}, []);   // empty dependency array: run once, after the first render
async function getData() {
    try {
        const response = await fetch("/api/data");
        const data = await response.json();
        return data;
    } catch (error) {
        console.error(error);   // network or JSON parsing failed
    }
}
Note

When effects run, how dependencies work, and why you often don't need an effect are covered in React State & useEffect. For server state at scale, see Redux Toolkit + RTK Query.

React Router

React Router maps URLs to components. The three things you always need are the router, the Routes/Route definitions, and navigation.

npm install react-router-dom
import {
    BrowserRouter,
    Routes,
    Route
} from "react-router-dom";

function App() {
    return (
        <BrowserRouter>
            <Routes>
                <Route path="/" element={<Home />} />
                <Route path="/products" element={<Products />} />
                {/* :id is a URL parameter, read with useParams() below */}
                <Route path="/products/:id" element={<ProductDetail />} />
                {/* "*" catches any unmatched URL (a 404 page) */}
                <Route path="*" element={<NotFound />} />
            </Routes>
        </BrowserRouter>
    );
}

Navigate between pages with Link and read route parameters with useParams. Use Link instead of a plain anchor so the router swaps components without a full-page reload:

import { Link, useParams } from "react-router-dom";

<Link to="/products">Products</Link>

function ProductDetail() {
    const { id } = useParams();   // matches the :id segment in the route path
    // fetch the product using id
}
See official docs

For nested routes, layouts, loaders and protected routes, see the official React Router documentation.

Context

Context shares a value with a subtree without passing props through every level. It is ideal for theme, locale, or the currently authenticated user.

import { createContext, useContext, useState } from "react";

const AuthContext = createContext(null);   // null = value before a Provider mounts

export function AuthProvider({ children }) {   // wrap the tree once, near the root
    const [user, setUser] = useState(null);

    return (
        // value is what every descendant reads through useContext
        <AuthContext.Provider value={{ user, setUser }}>
            {children}
        </AuthContext.Provider>
    );
}

export function useAuth() {   // custom hook hides the context object from callers
    return useContext(AuthContext);
}
function Profile() {
    const { user } = useAuth();
    return user ? <p>{user.name}</p> : <p>Guest</p>;
}
Key point

Use Context for low-frequency, app-wide values. For large global state (cart, auth with complex updates) prefer Redux Toolkit.

Performance: memo, useMemo, useCallback, lazy

Reach for these after you have measured a real problem — not by default.

ToolPurpose
React.memoSkip re-rendering a component when props are unchanged
useMemoCache an expensive computed value between renders
useCallbackCache a function identity so memoized children don't re-render
React.lazy + SuspenseCode-split routes/components so they load on demand
 
import { useMemo, useCallback, memo, lazy, Suspense } from "react";

const total = useMemo(
    () => items.reduce((sum, i) => sum + i.price, 0),
    [items]   // recompute only when items changes
);

const handleClick = useCallback(
    (id) => setSelected(id),
    []        // stable identity so memoized children don't re-render
);

const Chart = lazy(() => import("./Chart"));   // fetched only when first rendered

<Suspense fallback={<p>Loading…</p>}>
    <Chart />
</Suspense>
Common mistake

Wrapping everything in memo/useMemo adds complexity and can be slower. Measure first, optimize second.

Quick recap

  • Components receive props (read-only) and own state.
  • Update state immutably with the spread operator and updater functions.
  • Event handlers follow one rule: pass a function, don't call it.
  • Controlled inputs bind value + onChange to state.
  • Submit forms with fetch/axios and track loading + error state.
  • Conditional rendering uses ? : and &&.
  • Lists use map() with a stable key.
  • Router maps URLs to components; Context shares app-wide values.
  • Optimize with memo, useMemo, useCallback and lazy only when measured.
