React State & useEffect

The mental model behind React state: snapshots, why setState isn't immediate, the onClick function-execution rule, and when (and when not) to use useEffect.

Frontend React mechanics owner

State is a snapshot per render

React state is a snapshot for each render.

const [activeIndex, setActiveIndex] = useState(-1);

On render #1, activeIndex is -1. When you call:

setActiveIndex(2);

you are not changing the current activeIndex variable. You are telling React: "render this component again using 2 as the new state." React then produces render #2 where activeIndex is 2.

Key point

Each render gets its own snapshot of state. The variable activeIndex is a constant for that render.

setState does not update immediately

A state setter schedules work; it does not change the variable in the render that is currently running. This catches almost everyone once: a console.log placed right after setState still prints the old value.

function Counter() {
    const [count, setCount] = useState(0);

    const handleClick = () => {
        setCount(1);           // schedules a re-render; does not change `count` now
        console.log(count);    // still this render's value (0)
    };

    return (
        <button onClick={handleClick}>{count}</button>
    );
}

When you click, the console shows 0, not 1. The handler is still working with the snapshot from the current render.

    ↓

Calling setState does not change the current render's state variable; it requests a new render that receives the updated state.

handleClick(index) runs immediately vs () => handleClick(index)

This is the classic "why does my handler fire on every render?" bug. Adding () invokes the function right away; wrapping it in an arrow function hands React a function to call later, when the event actually happens.

Consider:

onClick={handleClick(index)}

The () means "call the function". JavaScript evaluates handleClick(index) while React is rendering, so it does not wait for the click.

function Card() {
    const handleClick = (index) => {
        console.log("clicked", index);
    };

    // Wrong: runs during render
    return (
        <button onClick={handleClick(2)}>Apple</button>
    );
}

Now wrap it:

onClick={() => handleClick(index)}

Here () => handleClick(index) is a function definition. You give React a function without executing it, and React calls it when the user clicks.

React renders
    ↓
Creates the function
    ↓
Gives the function to onClick
    ↓
User clicks
    ↓
React calls the function
    ↓
handleClick(2) executes
    ↓
"clicked 2"

The valid form when you don't need arguments

If you don't need to pass arguments, you can hand React the function directly:

function Button() {
    const handleClick = () => {
        console.log("clicked");
    };

    return (
        <button onClick={handleClick}>Click Me</button>
    );
}
Key point

onClick expects a function, not the result of calling a function. onClick={handleClick} is valid.

useEffect runs after the render

useEffect runs after React renders, so it sees the new state value.

function Counter() {
    const [count, setCount] = useState(0);

    useEffect(() => {
        console.log("New count:", count);   // runs after render, with the NEW count
    }, [count]);   // re-run whenever count changes

    const handleClick = () => {
        setCount(count + 1);
    };

    return (
        <button onClick={handleClick}>{count}</button>
    );
}

The dependency array controls when the effect re-runs: [] runs once after mount; [count] re-runs whenever count changes.

You don't need useEffect just to read state

You do not need useEffect to use updated state. React automatically provides the new state during the next render.

function Counter() {
    const [count, setCount] = useState(0);

    return (
        <div>
            <h2>{count}</h2>
            <button onClick={() => setCount(count + 1)}>Increase</button>
        </div>
    );
}

    ↓

    ↓

Common mistake

Syncing state with an effect just to display it is unnecessary. If a value can be computed during render, compute it during render.

When to use useEffect

Use useEffect to perform a side effect after rendering:

useEffect(() => {
    console.log("Count changed:", count);   // side effect after render
}, [count]);   // only when count changes
  • Fetching data
  • Updating the document title
  • Starting a timer
  • Subscribing to something
  • Working with external APIs
Warning

Effects that set state can cause extra renders. Include every value the effect reads in its dependency array to avoid stale values.

Common mistake

Forgetting to clean up an interval, listener or subscription leaks it. Return a cleanup function from the effect — React calls it before the next run and on unmount, for example return () => clearInterval(id);.

For data fetching at scale, prefer RTK Query. Everyday component patterns are on the React page.

Navigate after a state update (not during render)

State updates and side effects belong inside an useEffect or behind an if guard — never called bare during render. Rendering must stay pure, so calling navigate(...) (or setting another component's state) while React is computing JSX fights the render flow and can produce warnings or loops.

A common case is a login form: after a successful request you update the token and want to redirect to the dashboard. Do not call navigate("/tasks") directly in the render or the handler — the token you just scheduled is not available in this render, and navigating mid-render is unsafe. Let the render finish, then react to the token change in an effect.

import { useEffect, useState } from "react";
import { useNavigate } from "react-router-dom";

function LoginForm() {
    const navigate = useNavigate();
    const [token, setToken] = useState(null);
    const [userData, setUserData] = useState({ email: "", password: "" });

    const handleSubmit = async (e) => {
        e.preventDefault();
        const result = await fetch("/api/login", {
            method: "POST",
            headers: { "Content-Type": "application/json" },
            body: JSON.stringify(userData)
        }).then((res) => res.json());
        setToken(result.accessToken);   // schedule the state update
    };

    // Runs AFTER render, once the new token value is available
    useEffect(() => {
        if (token) {
            navigate("/tasks");         // guard: only when we actually have a token
        }
    }, [token, navigate]);              // re-run whenever token changes

    return (
        <form onSubmit={handleSubmit}>
            <input
                type="text"
                value={userData.email}
                onChange={(e) =>
                    setUserData((prev) => ({ ...prev, email: e.target.value }))
                }
            />
            <input
                type="password"
                value={userData.password}
                onChange={(e) =>
                    setUserData((prev) => ({ ...prev, password: e.target.value }))
                }
            />
            <button type="submit">Login</button>
        </form>
    );
}
Key point

The effect runs after render, so token already holds the new value. The if (token) guard prevents an unnecessary redirect on the first render, when token is still null.

Common mistake

Calling navigate() directly inside the render body navigates on every render, and calling it in the handler may navigate before the state settles. Move the navigation into an effect that depends on the value you are waiting for.

Lifting state up

Siblings cannot see each other's local state, so when two components must stay in sync you move the state to their closest common parent. The parent becomes the single source of truth and passes the value down plus a setter (or callback) back up.

function Panel() {
    // Parent owns the one shared value
    const [query, setQuery] = useState("");

    return (
        <>
            <SearchInput value={query} onChange={setQuery} />   {/* data down */}
            <Results query={query} />                          {/* data down */}
        </>
    );
}
Key point

Pass the value down and the setter down. The child never edits the value directly — it calls the parent's setter, which triggers a re-render. Reach for Context only when many levels are involved.

Custom hooks

A custom hook is any function whose name starts with use that calls other hooks — it extracts reusable logic without extra components. Each component that calls it gets its own isolated copy of the state.

function useLocalStorage(key, initial) {
    const [value, setValue] = useState(() => {
        // lazy initializer: runs once, reads any saved value
        return JSON.parse(localStorage.getItem(key)) ?? initial;
    });

    useEffect(() => {
        localStorage.setItem(key, JSON.stringify(value));
    }, [key, value]);   // persist whenever value changes

    return [value, setValue];   // works like a normal hook
}

// Each component gets its own independent value
const [theme, setTheme] = useLocalStorage("theme", "light");
Common mistake

Rules of Hooks: call hooks only at the top level of a component or another hook — never inside loops, conditions or nested functions, or the call order breaks between renders.

Quick recap

  • State is a snapshot belonging to a specific render.
  • setState does not change the current snapshot — it schedules a new render.
  • A stale console.log after setState is expected behavior.
  • handleClick(index) means execute now; () => handleClick(index) means execute on click.
  • onClick={handleClick} is valid — React expects a function.
  • useEffect runs after render and sees the new state when its dependencies change.
  • You don't need an effect just to read state — the next render has it.
  • Side effects such as navigation belong in useEffect (or behind an if), not during render.
