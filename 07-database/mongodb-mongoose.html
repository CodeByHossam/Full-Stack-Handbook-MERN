MongoDB & Mongoose Deep Dive

The advanced Mongoose layer: Query vs Document, populate, controller patterns, resource authorization, methods/virtuals/statics, and model-level security.

Database Mongoose Controllers · Authorization

Query vs Document

The single most important distinction in Mongoose is the difference between a Query and a Document.

const query = User.findOne({ email });       // Query — not executed yet
const user = await User.findOne({ email });  // Document — the actual record

A Query is an instruction that describes a database operation. It can be modified and chained before it runs. A Document is the real MongoDB record represented by Mongoose, which you can modify, save, populate, or delete.

findById()
    ↓
  Query
    ↓
  await
    ↓
Document
Key point

In practice, await is what executes the operation and turns a Query into its result. Conceptually though, a Query is the instruction and a Document is the record.

Building a query before awaiting

When you need the result, await the operation. When you want to build the query first, delay the await.

// await immediately
const user = await User.findOne({ email });
const notes = await Note.find();

// build the query, then execute it
const query = Note.find();
query.populate("creator", "name");
const result = await query;

// more commonly, chain and await inline
const notes = await Note.find().populate("creator", "name");

Query chaining

Because a Query is an object, methods like populate(), sort(), and limit() can be chained before it executes.

const note = await Note.findById(id)
    .populate("assignedTo", "name")
    .populate("creator", "name");

Populate — replacing references

Suppose the Note schema references User:

assignedTo: {
    type: mongoose.Schema.Types.ObjectId,
    ref: "User"
},
creator: {
    type: mongoose.Schema.Types.ObjectId,
    ref: "User"
}

Without populate a Note contains only ObjectIds:

{
    title: "Fix login API",
    creator: "68a123...",
    assignedTo: "68b456..."
}

With populate the ids are replaced by the referenced documents:

const note = await Note.findById(id)
    .populate("assignedTo", "name")
    .populate("creator", "name");

// result
{
    title: "Fix login API",
    creator: { _id: "68a123...", name: "Alice Ali" },
    assignedTo: { _id: "68b456...", name: "Bob Hassan" }
}

Why select only some fields

The second argument to populate() is a field selection. .populate("creator", "name") means "populate the creator User but return only its name". The User document may contain sensitive fields such as password, and the frontend rarely needs them.

Separate populate calls for separate references

This is a common mistake:

.populate("assignedTo", "name creator")  // WRONG

The creator there refers to a field on the User document referenced by assignedTo — it does not populate the Note's creator. The Note has two independent references, so use two calls:

.populate("assignedTo", "name")
.populate("creator", "name")

Populate on a query vs a document

Both styles are valid. findById() returns a Query, so you can populate before awaiting.

// on a Query
const note = await Note.findById(id)
    .populate("assignedTo", "name")
    .populate("creator", "name");

If you already awaited, you have a Document and can populate it directly:

const note = await Note.findById(id);

await note.populate([
    { path: "assignedTo", select: "name" },
    { path: "creator", select: "name" }
]);

Populate after create

Note.create() returns a Document, so populate it afterward:

const note = await Note.create({
    title,
    description,
    assignedTo,
    creator: req.user._id
});

await note.populate([
    { path: "assignedTo", select: "name" },
    { path: "creator", select: "name" }
]);

res.status(201).json({
    isSuccess: true,
    data: note,
    message: "Note created successfully"
});

Controller pattern — GET all notes

When a custom static returns a Query, you can keep chaining populate() before awaiting.

const notes = await Note.getAccessibleByUser(req.user)
    .populate("assignedTo", "name")
    .populate("creator", "name");
getAccessibleByUser(req.user)
    ↓
  Query
    ↓

The whole req.user object is passed because accessibility depends on both req.user._id and req.user.role.

Controller pattern — GET one note

findById() returns a Query; chaining populate() and awaiting gives the Document. A missing id is a real 404, so return early before any authorization check can run.

const note = await Note.findById(req.params.id)
    .populate("assignedTo", "name")
    .populate("creator", "name");

if (!note) {
    return res.status(404).json({
        isSuccess: false,
        message: "Note not found"
    });
}

// authorization happens here, after we have the document

Authentication vs authorization in queries

These are different concepts, and mixing them up causes security bugs.

  req.user

Role authorization middleware

A role middleware factory accepts a single array of allowed roles.

const authorize = (allowedRoles) => {
    return (req, res, next) => {
        if (!req.user) {
            // 401 → we do not know who you are yet
            return res.status(401).json({
                isSuccess: false,
                message: "Not authenticated"
            });
        }

        if (!allowedRoles.includes(req.user.role)) {
            // 403 → we know you, but your role is not allowed
            return res.status(403).json({
                isSuccess: false,
                message: "You are not authorized to perform this action"
            });
        }

        next();
    };
};

module.exports = authorize;
const allowedRoles = {
    admin: ["admin"],
    user: ["user"],
    adminAndUser: ["admin", "user"]
};

// usage
router.delete("/:id", protect, authorize(allowedRoles.adminAndUser), deleteNote);
Common mistake

Do not pass multiple arguments — authorize(allowedRoles.admin, allowedRoles.user) — because the middleware only reads its first argument. Do not pass an array of arrays either, because allowedRoles.includes("admin") would then fail. Combine roles first: authorize(allowedRoles.adminAndUser).

Resource-specific authorization

Role checks are not enough for per-resource rules. For a note, a user may access it if they are the creator, the assignee, or an admin. Access is denied only when all three are false.

if (
    !note.isOwner(req.user._id) &&
    !note.isAssignedTo(req.user._id) &&
    req.user.role !== "admin"
) {
    return res.status(403).json({
        isSuccess: false,
        message: "You are not authorized to access this note"
    });
}

The && is correct here because denial requires every condition to be true: not the creator AND not assigned AND not admin. If any single one is satisfied, access is allowed.

Common mistake

Never write !req.user.role === "admin". JavaScript applies ! first, so this evaluates false === "admin". Use req.user.role !== "admin".

Controller pattern — UPDATE a note

The clear, maintainable flow uses two database operations: find the note, check authorization, then update.

Find note
    ↓
Check authorization
    ↓
Update
    ↓
Populate updated document
    ↓
Return response
const updateNote = asyncHandler(async (req, res) => {
    const note = await Note.findById(req.params.id);

    if (!note) {
        return res.status(404).json({
            isSuccess: false,
            message: "Note not found"
        });
    }

    // Only the creator or an admin can update
    if (!note.isOwner(req.user._id) && req.user.role !== "admin") {
        return res.status(403).json({
            isSuccess: false,
            message: "You are not authorized to update this note"
        });
    }

    const { title, description, assignedTo, state, completed } = req.body;

    const updatedNote = await Note.findByIdAndUpdate(
        req.params.id,
        {
            title: title ?? note.title,
            description: description ?? note.description,
            assignedTo: assignedTo ?? note.assignedTo,
            state: state ?? note.state,
            completed: completed ?? note.completed
        },
        {
            new: true,
            runValidators: true
        }
    )
        .populate("assignedTo", "name")
        .populate("creator", "name");

    res.status(200).json({
        isSuccess: true,
        data: updatedNote,
        message: "Note updated successfully"
    });
});

new: true and runValidators: true

  • new: true — return the updated document instead of the pre-update version.
  • runValidators: true — apply schema validation (for example an enum on state) during the update.

Partial updates with ??

The nullish coalescing operator ?? means: use the new value when it is not null or undefined, otherwise keep the existing one. So a request that only sends { "title": "New title" } leaves every other field unchanged.

Document-based update

Instead of findByIdAndUpdate() you can modify a document and call save():

const note = await Note.findById(id);
note.title = "New title";
await note.save();
Key point

Populate the document you actually return. If you update with findByIdAndUpdate() into updatedNote, populate updatedNote — not the earlier note.

Controller pattern — DELETE a note

note.deleteOne() returns a delete result, not the deleted document:

const result = await note.deleteOne();
// { acknowledged: true, deletedCount: 1 }

Because findById() loaded the document into memory, you can populate and return it even after the database row is gone.

const deleteNote = asyncHandler(async (req, res) => {
    const note = await Note.findById(req.params.id);

    if (!note) {
        return res.status(404).json({
            isSuccess: false,
            message: "Note not found"
        });
    }

    // Only the creator or an admin can delete
    if (!note.isOwner(req.user._id) && req.user.role !== "admin") {
        return res.status(403).json({
            isSuccess: false,
            message: "You are not authorized to delete this note"
        });
    }

    // Populate before deleting because deleteOne() returns a delete result
    await note.populate([
        { path: "creator", select: "name" },
        { path: "assignedTo", select: "name" }
    ]);

    await note.deleteOne();

    res.status(200).json({
        isSuccess: true,
        data: note,
        message: "Note deleted successfully"
    });
});
MongoDB
   ↓
findById()
   ↓
Document in memory
   ↓
populate()
   ↓
deleteOne()
   ↓
MongoDB record deleted
   ↓
note still exists in JS memory
   ↓
return note

deleteOne() vs findByIdAndDelete()

ApproachUse when
note.deleteOne() (document)You already fetched the document for authorization, or you want to return it. Returns a delete result.
Note.findByIdAndDelete(id) (query)You do not need authorization beyond the id. Returns the deleted document.

If the frontend only needs a success message, skip populate and return no data.

Built-in vs custom methods

Mongoose ships with methods such as find(), findOne(), findById(), findByIdAndUpdate(), findByIdAndDelete(), save(), deleteOne(), and populate(). You can also define your own for business logic.

TypeProvided byExamples
Built-inMongoose / JavaScriptnote.save(), note.toJSON(), note.validate()
CustomYou, for the applicationnote.isOwner(), user.comparePassword()
Customized built-inYou override an existing hookdefining Schema.methods.toJSON

Schema.methods — behavior of one document

Use a method when an action naturally belongs to a single document. Inside a method, this is the document.

UserSchema.methods.checkPassword = function (password) {
    return password === this.password;
};

// usage
const user = await User.findOne({ email });
user.checkPassword("123456");

Realistic method examples: user.comparePassword(), user.isAdmin(), note.isOwner(userId), note.markAsCompleted().

NoteSchema.methods.isOwner = function (userId) {
    return this.creator.toString() === userId.toString();
};

Customizing toJSON

toJSON() is a standard serialization hook; defining it on Schema.methods customizes how the document is serialized.

NoteSchema.methods.toJSON = function () {
    const { __v, ...object } = this.toObject();
    return object;
};

Now res.json(note) no longer leaks the internal __v field.

Schema.virtual — calculated properties

A virtual is a derived property that is not stored in MongoDB.

UserSchema.virtual("fullName").get(function () {
    return `${this.firstName} ${this.lastName}`;
});

// usage — notice there are no parentheses
const user = await User.findOne();
console.log(user.fullName);
Warning

A virtual is a value, not a function. Access user.fullName, not user.fullName(). Good uses: fullName, displayName, product.finalPrice.

Schema.statics — behavior of the model

Use a static for behavior that belongs to the model/collection rather than one document.

UserSchema.statics.findByEmail = function (email) {
    return this.findOne({ email });
};

// usage
const user = await User.findByEmail(email);

A static searches across many documents. A useful use case is a reusable access query that returns a Query which can then be chained:

NoteSchema.statics.getAccessibleByUser = function (user) {
    if (user.role === "admin") {
        return this.find();
    }
    return this.find({
        $or: [{ creator: user._id }, { assignedTo: user._id }]
    });
};

// controller
const notes = await Note.getAccessibleByUser(req.user)
    .populate("assignedTo", "name")
    .populate("creator", "name");
Method  → ONE document       user.comparePassword()
Static  → MODEL / collection User.findByEmail()

Controller responsibilities and anti-patterns

The controller handles the API request, CRUD, application flow, and the HTTP response.

Request
   ↓
Controller
   ↓
Model / Service
   ↓
Database
   ↓
Controller
   ↓
Response

Typical controller functions: createNote(), getNotes(), getNote(), updateNote(), deleteNote(), register(), login().

const createNote = async (req, res) => {
    const note = await Note.create({
        title: req.body.title,
        content: req.body.content,
        creator: req.user._id
    });

    res.status(201).json(note);
};

Do not create a document method just because an operation touches a document. These are anti-patterns:

note.create()      // WRONG — creating belongs to the Model
note.getAllNotes() // WRONG — collection operation, use Note.find()
note.sendResponse()// WRONG — HTTP behavior belongs in the controller
Key point

Methods describe what a single document knows how to do. CRUD, collection queries, and HTTP responses stay in the controller.

Services — for larger applications

When business logic grows complex or is reused in several places, move it into a service layer. The controller stays thin and focused on the API.

Request
   ↓
Controller
   ↓
Service
   ↓
Model
   ↓
Database
// controller
const createNote = async (req, res) => {
    const note = await noteService.createNote(req.body, req.user);
    res.status(201).json(note);
};

Introduce a service only when the controller becomes too large or the same logic is needed in multiple controllers.

Collation and unique case-sensitivity

Collation can make a query case-insensitive:

const existedUser = await User.findOne({ email })
    .collation({ locale: "en", strength: 2 })
    .exec();

But if the schema already normalizes the field, a simpler approach is to normalize the input yourself:

const existedUser = await User.findOne({
    email: email.toLowerCase()
}).exec();
Common mistake

unique: true creates a unique index but does not make comparison case-insensitive. Add lowercase: true to normalize stored values, so Alice@example.com is saved as alice@example.com.

ObjectId validation

A field typed as mongoose.Schema.Types.ObjectId must receive a valid MongoDB ObjectId — 24 hexadecimal characters.

assignedTo: Joi.string().hex().length(24).required()
Warning

Do not invent an id for testing. Copy the real _id of an existing user, or the request will fail validation.

Password hashing in the model

Centralize password hashing in the User model with a pre-save hook so the controller never handles plaintext logic.

UserSchema.pre("save", async function () {
    if (!this.isModified("password")) return;
    this.password = await bcrypt.hash(this.password, 10);
});

The controller then simply creates the user; the model hashes before saving:

const user = await User.create({ name, email, password, role });
Common mistake

Do not call next() inside an async hook — that causes TypeError: next is not a function. When the middleware is async, return or await the Promise instead. The guard if (!this.isModified("password")) return; also stops an already-hashed password from being re-hashed on every save.

Hashing and verification are separate operations. Registration uses bcrypt.hash(); login uses bcrypt.compare() against the stored hash.

// registration
const hashedPassword = await bcrypt.hash(password, 10);

// login
const isMatch = await bcrypt.compare(password, user.password);
if (!isMatch) {
    return res.status(401).json({ message: "Invalid credentials" });
}

JWT expiry vs cookie security

A JWT payload contains iat (issued at) and exp (expiration), both Unix timestamps in seconds.

{
    "iat": 1788332006,
    "exp": 1788332906
}

The difference, 1788332906 - 1788332006 = 900 seconds, so expiresIn: "900s" produces a token valid for 15 minutes.

SettingControls
expiresIn: "900s"How long the token is valid
Cookie secure: trueWhether the browser sends the cookie only over HTTPS

Use secure: false for local HTTP development and secure: true in production. The full auth flow lives on Authentication & JWT.

Recommended architecture and final rules

This is the layered architecture these pages recommend, followed by the rules distilled from every earlier section. Use it as the checklist when you structure a new Mongoose feature.

Request
   ↓
Middleware   → authentication, authorization, validation
   ↓
Controller   → CRUD, API request/response, application flow
   ↓
Service      → complex/reusable business logic (when needed)
   ↓
Model        → methods (one document), statics (collection), virtuals (computed)
   ↓
MongoDB      → stores the data
  • findById() returns a Query until you await it; await executes it and returns a Document.
  • Populate on a Query before await, or on a Document after await; populate what you return.
  • findByIdAndUpdate() returns a Query — use new: true and runValidators: true.
  • deleteOne() returns a delete result; populate before deleting if you must return the document.
  • Keep authentication and authorization separate; never write !req.user.role === "admin".
  • Prefer clear authorization logic over cramming it into one query.
  • Use methods for one document, statics for the model, virtuals for computed values, services for complex logic.

Quick recap

  • Query is the instruction; Document is the record you get after await.
  • Chain populate(), sort(), limit() on a Query, or populate a Document after awaiting.
  • Select only needed fields in populate to avoid leaking sensitive data; use one call per reference.
  • Controllers own CRUD and HTTP; models own document behavior and collection queries.
  • Resource authorization uses AND of negatives (creator/assignee/admin) — and !==, never !.
  • Updates use new: true, runValidators: true, and ?? for partial updates; populate the returned document.
  • deleteOne() returns a result, not the document; populate before delete if returning it.
  • Methods act on one document, statics on the Model, virtuals are computed, services handle complex logic.
  • Centralize password hashing in a pre-save hook; bcrypt.compare() at login; keep JWT expiry and cookie secure separate.
