Clean Code & Best Practices

The 55 everyday rules that make code easy to read, understand, debug, change, test, and maintain — with a practical refactor example.

Practices 55 rules Everyday habits

What clean code means

The goal is code that is easy to read, understand, debug, change, and test, and easy for another developer to maintain.

Key point

Good code is not the shortest code. Good code is code another developer can understand without asking you what it does. The underlying concepts live in Programming Principles.

Naming: make names carry meaning

A name should explain what the value represents. Functions are actions, variables are things, and booleans read like yes/no questions. 

// bad
const x = 10;
const u = getUser();
const p = 100;

// good
const maxRetries = 10;
const user = getUser();
const productPrice = 100;
// functions are verbs
function getUser() {}
function createProduct() {}
function calculateTotal() {}
function deleteUser() {}

// variables are nouns
const user = {};
const totalPrice = 100;

// booleans sound like questions
const isActive = true;
const isAdmin = false;
const hasPermission = true;
const canEdit = false;

Case conventions by identifier type

The convention depends on what the identifier is. Pick one style per category and keep it consistent across the whole codebase.

Identifier Convention Example
Variables camelCase userName
Functions camelCase getUserById()
Classes PascalCase ShoppingCart
Constants SCREAMING_SNAKE_CASE MAX_RETRY_COUNT
Private fields _ prefix _internalState
Booleans is/has/can prefix isActive, hasPermission
React components PascalCase UserProfile
Interfaces / types (TS) PascalCase UserData
Enums (TS) PascalCase Color

PascalCase, explained

What: every word starts with an uppercase letter, including the first, with no separators. Why: it visually signals "this is a type, class, or component", not a value or action. When: classes, React components, TypeScript interfaces/types/enums. 

// PascalCase — types, components, classes
class UserAccount {}
function UserProfile() { return <div>...</div>; }
interface UserData {}
type ResponseStatus = "success" | "error";

// camelCase — values and actions
const userName = "Alice";
function getUser() {}
Note

Also called UpperCamelCase, because it looks like camelCase with the first letter capitalized — like a camel's humps.

Enforce conventions with ESLint

ESLint's built-in camelcase rule cannot tell a function apart from a class. For per-type rules, use @typescript-eslint/naming-convention — it works in plain .js files too. 

npm install -D @typescript-eslint/eslint-plugin @typescript-eslint/parser
// eslint.config.js
import tseslint from "@typescript-eslint/eslint-plugin";
import tsparser from "@typescript-eslint/parser";

export default [
  {
    files: ["**/*.js", "**/*.ts", "**/*.jsx", "**/*.tsx"],
    languageOptions: { parser: tsparser },
    plugins: { "@typescript-eslint": tseslint },
    rules: {
      "@typescript-eslint/naming-convention": [
        "error",
        { selector: "variable",   format: ["camelCase", "UPPER_CASE"], leadingUnderscore: "allow" },
        { selector: "function",   format: ["camelCase"] },
        { selector: "parameter",  format: ["camelCase"], leadingUnderscore: "allow" },
        { selector: "class",      format: ["PascalCase"] },
        { selector: "interface",  format: ["PascalCase"] },
        { selector: "typeAlias",  format: ["PascalCase"] },
        { selector: "enum",       format: ["PascalCase"] },
        { selector: "enumMember", format: ["UPPER_CASE", "PascalCase"] },
        { selector: "objectLiteralProperty", format: ["camelCase", "UPPER_CASE", "snake_case"], leadingUnderscore: "allow" },
        { selector: "variable", types: ["boolean"], format: ["PascalCase"], prefix: ["is", "has", "can", "should"] }
      ]
    }
  }
];
Watch out

React components are functions but PascalCase — allow both formats for functions if your project uses JSX, or use the TypeScript filter option to scope the PascalCase rule to capitalized names.

Functions: small, focused, early-return

Don't make functions too long, and give each one a single responsibility. A function that validates, calculates, charges, saves, emails, and updates inventory is impossible to test. 

// bad: one function doing everything
function createOrder() {
    // validate user
    // check products
    // calculate prices
    // process payment
    // save order
    // send email
    // update inventory
}

// better: each step has its own function
function createOrder() {
    validateOrder();
    const total = calculateOrderTotal();
    const payment = processPayment(total);
    const order = saveOrder(payment);
    sendConfirmationEmail(order);
}

Avoid deep nesting with early return

What: Guard clauses — checking each precondition and returning early — flatten nested if blocks into a linear sequence. Why: Deep nesting hides the happy path inside indentation and makes edge cases hard to spot. When: Use at the top of a function for validation and permission checks, exactly like protect middleware in Express. 

// bad
if (user) {
    if (user.isActive) {
        if (user.isAdmin) {
            if (user.hasPermission) {
                // code
            }
        }
    }
}

// better — guard clauses: each check exits early,
// so the real logic stays at the top level
if (!user) return;
if (!user.isActive) return;
if (!user.isAdmin) return;
if (!user.hasPermission) return;
// code

Don't use else unnecessarily

What: When a branch always returns, a trailing else is dead weight. Why: Removing it drops a nesting level and makes the default case explicit — the reader sees "return early, otherwise fall through". When: Any if/else where both sides end in return, throw, or break. 

// bad
if (isAdmin) {
    return "Admin";
} else {
    return "User";
}

// better — no else needed: "User" is simply the default
if (isAdmin) {
    return "Admin";
}
return "User";

DRY — but don't over-abstract

Don't repeat yourself: extract repeated logic into a function. But don't create a function for everything — abstract repeated or meaningful logic, not every single line. 

// repeated
const total1 = price1 + price1 * 0.05;
const total2 = price2 + price2 * 0.05;

// extracted
function calculateWithTax(price) {
    return price + price * 0.05;
}
const total = calculateWithTax(price1);
// over-abstracted
function addNumbers(a, b) {
    return a + b;
}
const result = addNumbers(2, 3);

// simple is better here
const result = 2 + 3;

Also keep related code together rather than scattering pieces hundreds of lines apart.

Magic numbers & constants

A bare number or string with no explanation is a magic value. Name it. 

// bad
if (age > 18) {}
setTimeout(function () {}, 86400000);

// good
const MINIMUM_AGE = 18;
const ONE_DAY = 24 * 60 * 60 * 1000;

if (age > MINIMUM_AGE) {}
setTimeout(function () {}, ONE_DAY);

// named role constants
const ADMIN_ROLE = "admin";
if (role === ADMIN_ROLE) {}

React component discipline

One component, one clear responsibility. Split big pages into focused pieces: 

ProductPage.jsx          ProductPage.jsx
  (1000 lines)     ->    ProductHeader.jsx
                         ProductList.jsx
                         ProductCard.jsx
                         ProductFilters.jsx
                         ProductPagination.jsx

The division of labour inside the frontend:

  • Component — UI responsibility
  • Hook — logic responsibility
  • Service — API responsibility
ProductPage -> useProducts() -> RTK Query -> API

Don't scatter raw fetch("/api/products") across components. Centralize API logic in one place such as RTK Query. 

// centralized
const { data, isLoading } = useGetProductsQuery();
Note

Component design and hooks are detailed in MERN Architecture; server-state caching in Redux Toolkit + RTK Query.

Modern JavaScript syntax

Modern JS (ES6+) is shorter, safer, and more predictable than older idioms. Why: Manual loops, mutation, and fragile conditional chains are more verbose and hide bugs. When: Everywhere in MERN — this is the everyday vocabulary of React components and Node/Express code. 

// destructuring
const { name, email } = user;

// optional chaining: returns undefined instead of throwing
// when any link in the chain is null/undefined
console.log(user?.profile?.address?.city);

// nullish coalescing: fallback only for null / undefined
const displayName = user.name ?? "Guest";

// immutable updates
setUser({ ...user, name: "Alice" });

// prefer array methods over manual loops
const expensive = products.filter(product => product.price > 100);

// use map when you need a new array, not forEach + push
const names = users.map(user => user.name);

// strict equality
if (userId === id) {}

// const by default, let only when it changes
const label = "Alice";
let count = 0;
count++;
Common mistake

Don't create pointless variables just to return them, but do keep a variable when it improves readability: const fullName = `${firstName} ${lastName}`;.

Operator Returns fallback when... Common use
?? left is null/undefined safe default values (keeps 0, "", false)
|| left is any falsy value broad fallbacks
?. left is null/undefined safe property access down a chain
=> always (it is a function) compact functions and callbacks
Watch out

?? cannot be mixed with || or && without parentheses — a ?? b || c throws a SyntaxError; write (a ?? b) || c.

Comments & dead code

Comments explain WHY, not obvious WHAT. And unused functions, variables, imports, files, and comments should be removed. 

// bad: increment index
index++;

// good: Reset to the first item after
// reaching the end of the array.
index = (index + 1) % items.length;
// clean imports only
import { useEffect, useState } from "react";

Formatting & linting

Let tools enforce consistency so reviews focus on logic. Use Prettier to format (VS Code: Shift + Alt + F) and ESLint to catch unused variables, bad patterns, potential bugs, and style problems. 

npm install -D eslint
# ESLint finds problems, Prettier fixes formatting — use both together

Error handling & validate early

Let centralized middleware handle API errors instead of logging and swallowing them in every controller. And validate at the top of a function — fail fast. 

// bad: swallowed error
try {
    await saveUser();
} catch (error) {
    console.log(error);
}

// better: forward to centralized middleware
try {
    await saveUser();
} catch (error) {
    next(error);
}
function createUser(data) {
    if (!data.email) {
        throw new Error("Email is required");
    }
    // continue...
}
Note

The centralized error middleware and custom error objects are built in MERN Architecture; Express-level error handling in Express.

Decoupling: keep each layer in its lane

Separate business logic from routes, and keep database logic out of React entirely. 

// bad: 200 lines of logic inside the route
router.post("/orders", async (req, res) => { /* ... */ });

// better: delegate
router.post("/orders", createOrder);
// Route -> Controller -> Service -> Model
  • React should know the API (e.g. GET /api/products), never MongoDB or Mongoose.
  • The backend owns the database, fields, security, and business rules.
  • Don't expose database structure — return a useful, deliberate API response.

Security

Never trust req.body, req.params, req.query, or any value the frontend claims (role, price, payment status). Always validate on the backend. 

// never store passwords directly
// bad
password: "123456";

// good
password: await bcrypt.hash(password, 10);

Never commit secrets such as MONGO_URI, JWT_SECRET, or STRIPE_SECRET_KEY. Put them in .env and list .env in .gitignore.

Warning

Secrets and environment variables are owned by Node.js; hashing and tokens by Authentication & JWT.

Logging

Use console.log() in development, and a real logger (Pino or Winston) in production. Log errors, requests, and important events.

Never log passwords, JWTs, credit card data, or API secrets.

Database, API & frontend UX best practices

Three surfaces of a MERN app where small habits prevent large problems later: keep queries cheap, URLs meaningful, and every view honest about its four states.

Database — keep queries cheap

MongoDB makes it effortless to write expensive queries. Small habits at the query layer stop the database becoming the bottleneck at scale. 

// project only what you need
const users = await User.find({}, { name: 1, email: 1 });

// index what you filter and sort on — before you need it
userSchema.index({ email: 1 }, { unique: true });
orderSchema.index({ userId: 1, createdAt: -1 });

// paginate by default
const posts = await Post.find({ _id: { $lt: cursor } })
    .sort({ _id: -1 })
    .limit(20);

// avoid N+1: one query, not one per document
const posts = await Post.find().populate("authorId", "name avatar");

// .lean() for read-only responses — 3–5× faster hydration
const items = await Item.find().lean();
Key point

An unindexed query works fine with 100 documents in development and does a collection scan on every request at 100k documents in production. The habit costs seconds today; retrofitting costs days later.

API — keep URLs meaningful

Your URLs are a public contract. Once clients depend on them, changing them is a breaking change. Use nouns for resources, verbs only for actions, and let HTTP status codes speak. 

GET    /api/v1/users
POST   /api/v1/posts
DELETE /api/v1/users/42
GET    /api/v1/users/42/orders
GET    /api/v1/products?category=shoes&sort=-price&page=2
  • Pluralise consistently — /users, not /user in one place and /orders in another.
  • Version from the start — /api/v1 costs nothing now and saves everything later.
  • Nest only when the relationship is truly hierarchical; flatten otherwise with query params.
  • Return real status codes — 201 on create, 204 on delete, 404 not found, 422 invalid input.
Note

HTTP methods, status codes, and REST naming are owned by REST API.

Frontend UX — every view honest about its four states

Every API-driven component has four states, not one. A view that only handles success lies to the user on slow connections, when the API is down, and when a new user has zero items. 

Loading: "Loading products..."
Error:   "Unable to load products." + Retry
Empty:   "No products found." + action
Success: show the products.
function ProductList() {
    const { status, data, error, refetch } = useGetProductsQuery();

    if (status === "loading") return <Skeleton rows={5} />;
    if (status === "error")   return <ErrorState message={error} onRetry={refetch} />;
    if (data.length === 0)    return <EmptyState message="No products found" />;

    return <ul>{data.map(p => <ProductCard key={p._id} product={p} />)}</ul>;
}
Watch out

Empty and loading are different states. A blank panel while loading looks broken; a blank panel when empty looks broken too. Handle both explicitly.

Accessibility & responsiveness

  • Use <button>, not a clickable <div>.
  • Use <label> for inputs.
  • Give images descriptive alt text.
  • Make buttons keyboard accessible.

Don't design only for desktop — consider mobile, tablet, desktop, and large screens, and test real screen sizes.

Note

Layout mechanics and responsive CSS are owned by CSS and HTML.

Performance

Don't optimize everything immediately: make it work, then measure, then optimize.

  • Lazy loading
  • Memoization
  • Pagination
  • Caching
  • Image optimization
  • Code splitting
Note

Reason about growth before optimizing with Big O / Time Complexity.

The "make it clean" process

Clean code is a sequence, not a single act. Why: code that only "works" still costs time on the next change. When: run these steps in order on every feature or bug fix, always after your solution already works. 

1  Make it work           7  Validate inputs
2  Make it readable       8  Test
3  Remove duplication     9  Format with Prettier
4  Split large functions  10 Check with ESLint
5  Separate responsibilities 11 Review security
6  Handle errors          12 Commit
Key point

The most important rule: good code is not the shortest code — it is code another developer can understand without asking you what it does.

Worked example: the getProducts refactor

A controller with bad names, no explicit status, database logic inline, and poor error handling: 

// bad
const f = async (r, s) => {
    try {
        const x = await Product.find();
        s.json(x);
    } catch (e) {
        s.status(500).json({ message: e.message });
    }
};

// Problems:
// - Bad names
// - No explicit status code
// - Database logic in the controller
// - Poor error handling
// - Hard to maintain

The same endpoint, cleaned up:

const getProducts = async (req, res, next) => {
    try {
        const products = await productService.getAllProducts();

        res.status(200).json({
            success: true,
            data: products
        });
    } catch (error) {
        next(error);   // forward to the centralized error middleware
    }
};

Clear names, an explicit status, logic delegated to a service, and errors forwarded to centralized middleware.

Professional mental model

The questions a senior developer silently asks for every block they write or review. Working through them in order turns "it works" into "it will keep working". 

WHAT does this code do?
  -> WHY does it do it?
    -> WHO is responsible for it?
      -> CAN I reuse it?
        -> WHAT happens if it fails?
          -> CAN another developer understand it?

Quick recap

  • Meaningful names; verbs for functions, nouns for variables, questions for booleans
  • Small, single-responsibility functions; early return; no unnecessary else
  • DRY, but don't over-abstract; name magic values as constants
  • Keep components small; logic in hooks, API calls centralized
  • Use destructuring, optional chaining, nullish coalescing, immutability, ===, const
  • Comment WHY; remove dead code and unused imports
  • Format with Prettier, enforce with ESLint
  • Centralize errors, validate early, fail fast
  • Keep business logic out of routes and DB logic out of React
  • Never trust input, never store plain passwords, never commit secrets
  • Log properly and never log sensitive data
  • Handle loading, error, success, and empty states; be accessible and responsive
  • Clean folders, meaningful commits, self-review before pushing
