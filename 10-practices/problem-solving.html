Problem Solving

A repeatable playbook for turning any problem into a clear sequence of steps — the process, the data-structure patterns, the diagnostic questions, and worked examples.

Practices Algorithm playbook Patterns & templates

What problem solving is

Problem solving is turning a problem into a clear sequence of steps that a computer can execute. The answer is almost never "stare at it until code appears" — it is a process you can run every time.

Key point

The coding part is the last step. Most of the work happens before you type in JavaScript.

The basic process

Every problem — algorithm, bug, or feature — follows the same loop. Why: jumping straight to code skips the steps where most mistakes actually happen. When: run this sequence for any non-trivial task, and return to the loop whenever you get stuck.

UNDERSTAND -> BREAK DOWN -> PLAN -> PSEUDOCODE
 -> CODE -> TEST -> DEBUG -> IMPROVE

Each step below expands one stage of this loop.

Step 1 — Understand the problem

Before coding, identify input, output, and rules.

Problem: "Find the largest number in an array."
Input:   [4, 8, 2, 10, 5]
Output:  10

Step 2 — Solve it manually

Before writing code, solve the problem yourself, out loud. You cannot explain an algorithm you do not understand.

[4, 8, 2, 10, 5]
max = 4
8 > 4   -> max = 8
2 < 8   -> max = 8
10 > 8  -> max = 10
5 < 10  -> max = 10
Answer: 10

Step 3 — Break the problem down

Break a large problem into parts, then break each part further.

"Build an online-store"
  -> Users / Products / Categories / Cart
  -> Orders / Payments / Authentication / Admin

Products:
  -> get, get one, create, update, delete,
     search, filter, paginate

Step 4 — Identify the data

Ask "What data do I need?" The answer often points at the right data structure.

Problem: find duplicate numbers.
Input:   [1, 2, 3, 2, 4, 1]

We must remember which numbers we have seen.
-> Use a Set.

Step 5 — Write pseudocode

Don't start with JavaScript. Write the logic in plain steps first.

START
Create an empty Set
Create an empty duplicates list
For every number:
    If number already exists in Set:
        Add number to duplicates
    Otherwise:
        Add number to Set
Return duplicates
END

Step 6 — Implement

Now translate the pseudocode into code.

function findDuplicates(numbers) {
    const seen = new Set();
    const duplicates = new Set();

    for (const number of numbers) {
        if (seen.has(number)) {
            duplicates.add(number);
        }
        seen.add(number);
    }

    return [...duplicates];
}

Step 7 — Test

Don't test only one example. Cover normal, empty, single-item, all-duplicates, no-duplicates, and negative cases.

Normal:        [1, 2, 3, 2]
Empty:         []
One item:      [5]
All duplicates:[1, 1, 1]
No duplicates: [1, 2, 3, 4]
Negative:      [-1, -2, -1]

Edge cases

Always ask: "What could make my solution fail?"

  • Empty array
  • null / undefined
  • Zero
  • Negative numbers
  • Very large numbers
  • Duplicate values
  • One item / no items

Start with the simple solution

Don't immediately hunt for the cleverest solution. First find one that works, then improve it: correct first, efficient second.

Version 1: O(n²)
Version 2: O(n)
Note

Complexity classes and how to measure growth are owned by Big O / Time Complexity.

Brute force

Brute force means trying the straightforward solution — for example, comparing every item with every other item. It may be O(n²), but it helps you understand the problem before optimizing.

Optimize after you understand

Once it works, ask the optimization questions:

  • Can I avoid repeated work?
  • Can I use a Set or a Map?
  • Can I sort first?
  • Can I stop early?
  • Can I reduce nested loops?
Array search:  O(n)
Map lookup:    O(1) average

Choosing the right data structure can improve the algorithm more than micro-tuning the code.

Recognize patterns

Many problems repeat the same shapes. Learn the patterns, not individual answers:

  • Two Pointers
  • Sliding Window
  • Hash Map / Hash Set
  • Binary Search
  • Stack
  • Queue
  • Recursion
  • Divide and Conquer
  • Sorting
  • Dynamic Programming
  • Graph Traversal

Pattern: two pointers

Useful for arrays and strings. Move a left and a right pointer toward each other.

[1, 2, 3, 4, 5]
 left ->     <- right

Common problems: pair sum, palindrome, sorted arrays.

Pattern: sliding window

Useful for consecutive elements — maintain a window and slide it.

[1, 2, 3, 4, 5, 6]
[1, 2, 3]
   [2, 3, 4]
      [3, 4, 5]

Useful for maximum sum, longest substring, and subarray problems.

Pattern: hash map / set

Use when you need fast lookup, counting, detecting duplicates, or tracking values.

const count = new Map();

for (const item of array) {
    count.set(item, (count.get(item) || 0) + 1);   // || 0 -> first occurrence counts from 1
}

Ideal for frequency counting, duplicates, and fast lookup.

Pattern: binary search

Use when the data is sorted. Instead of checking every element, check the middle and eliminate half each time.

[1, 3, 5, 7, 9, 11, 13]
          ^ check middle, keep one half

Complexity: O(log n).

Pattern: recursion

A function that calls itself. Always identify the base case and the recursive case.

function countdown(n) {
    if (n === 0) {
        return;
    }

    console.log(n);
    countdown(n - 1);
}

Pattern: stack (LIFO)

Last In, First Out. Push adds on top; pop removes from the top.

[ A ][ B ][ C ]
push D  ->  [ A ][ B ][ C ][ D ]
pop     ->  D

Common uses: undo, browser history, function calls, parentheses matching.

Pattern: queue (FIFO)

First In, First Out. The first item added leaves first.

A -> B -> C
A leaves first.

Common uses: task processing, print queues, message queues.

Pattern: divide and conquer

Break a large problem into smaller problems, solve them, then combine. Merge sort is the classic example.

Large array -> split -> smaller arrays -> sort -> merge

Often produces efficient algorithms.

Recurring diagnostic questions

Four questions solve a surprising majority of problems.

"What changes?"

Identify the value that changes to find which variables you need: the max, the count, or the left/right pointers.

"What do I need to remember?"

Finding duplicates means remembering numbers already seen → Set. Counting names means remembering name → count → Map.

"Can I stop early?"

The moment a condition is satisfied, the remaining iterations are wasted work. Why: an early return or break can turn a full scan into a short one — the simplest optimization there is. When: any search, existence check, or first-match lookup.

for (const number of numbers) {
    if (number === target) {
        return true;   // found — skip the rest of the array
    }
}

Don't keep searching after you have found it.

"Am I doing the same work?"

If yes: can I store the result, use a Map or Set, or calculate it once? This is the beginning of optimization.

Debugging as problem solving

When code fails, don't immediately rewrite everything. Ask:

  1. What did I expect?
  2. What actually happened?
  3. Where did they become different?
  4. What value caused the difference?
  5. Why does that value have that value?
  6. What is the smallest fix?

Debug with examples

Run the function on the smallest case that shows the behavior, then compare the actual result with the expected one. Why: a single tiny example makes the discrepancy visible, so the bug stops hiding. When: whenever a function returns the wrong thing.

function add(a, b) {
    return a - b;
}

add(5, 2);
// Expected: 7
// Actual:   3   -> the bug is obvious

Testing simple examples helps isolate bugs.

Trace the code

Walk through the code line by line, updating each variable by hand. Why: tracing exposes where the value diverges from your mental model — usually at the very first wrong step. When: loops, recursion, or any sequence where you cannot see the mistake.

let total = 0;
for (const number of [2, 4, 6]) {
    total += number;
}
// start total = 0
// 1st   total = 2
// 2nd   total = 6
// 3rd   total = 12

Tracing is one of the best ways to understand code.

Draw it

Sketch the data and the flow as boxes and arrows. Why: diagrams make structure — nesting, ordering, pointer movement — visible in ways that prose hides. When: arrays, graphs, request flows, or any problem where you cannot yet "see" the answer.

User -> Order -> Products -> Payment
[ 4 ][ 8 ][ 2 ][ 10 ]

Visualizing the problem can make the solution obvious.

Don't code too early

The single most common beginner mistake is typing code before understanding the problem. Why: code written from confusion gets changed at random and still fails. When: always — read and understand first, then plan, then code.

Bad:    Read -> immediately write code -> get confused -> change random lines
Better: Read -> Understand -> Example -> Break down -> Pseudocode -> Code

Explain your solution

After solving, explain it in simple language. If you can explain it clearly, you probably understand it.

"I use a Set to remember numbers I have already seen. If I see a number again, it is a duplicate."

Complexity check

After solving, ask: what is the time complexity, and what is the space complexity?

ShapeComplexity
One loopO(n)
Nested loopsO(n²)
Map lookupO(1) average
New array of n itemsO(n) space
Note

Full complexity reference: Big O / Time Complexity.

Ask "can this scale?"

Code that works for 100 records may be unusable for 1,000,000. A solution that works on small data may break on large data.

General problem-solving template

A fill-in-the-blank version of the whole process — run it top to bottom and you have both a plan and a self-review. Why: the template forces you to answer the questions that expose design flaws before they are buried in code. When: any problem larger than a one-liner; keep it in your head until it becomes habit.

PROBLEM:       What am I asked to solve?
INPUT:         What data do I receive?
OUTPUT:        What should I return?
EXAMPLES:      What happens with simple input?
EDGE CASES:    What unusual input can occur?
DATA STRUCTURE: What should I use to store information?
ALGORITHM:     What steps solve the problem?
IMPLEMENT:     Write the code.
TEST:          Try normal + edge cases.
COMPLEXITY:    Time? Space?
IMPROVE:       Can it be simpler or faster?

Worked examples

The full process applied end-to-end, showing how the same skeleton handles different problems.

Example 1 — find the maximum

What: scan the array once, remembering the largest value seen so far. Why: each item is compared exactly once, so this is optimal for an unsorted array. When: any "largest / smallest / best so far" problem — this is a reusable pattern, not just a function.

PROBLEM: Find the largest number.
INPUT:   [4, 7, 2, 9, 1]
OUTPUT:  9
PLAN:    Start with the first number; compare each; keep the largest.
function findMax(numbers) {
    let max = numbers[0];              // seed with the first item

    for (const number of numbers) {
        if (number > max) {            // compare once per item -> O(n)
            max = number;
        }
    }

    return max;
}

// TIME:  O(n)   one full pass
// SPACE: O(1)   only one extra variable

Example 2 — count frequency

What: count occurrences by treating each value as a Map key. Why: Map lookup is O(1) average, so the whole job is one O(n) pass instead of nested loops. When: frequency counting, grouping, or any "how many of each" question.

PROBLEM: Count how many times each number appears.
INPUT:   [1, 2, 2, 3, 3, 3]
OUTPUT:  1 -> 1, 2 -> 2, 3 -> 3
PLAN:    Use a Map.
function countNumbers(numbers) {
    const count = new Map();               // Map gives O(1) average lookup

    for (const number of numbers) {
        count.set(number, (count.get(number) || 0) + 1);   // start at 0 if unseen
    }

    return count;
}

// TIME:  O(n)   one pass, O(1) work per item
// SPACE: O(n)   one key per unique number

The habit & how to practice

Every time you face a problem, train yourself to ask:

"What exactly is the problem?" · "What do I know?" · "What do I need?" · "What changes?" · "What should I remember?" · "Can I solve it manually?" · "Can I break it down?" · "Which data structure fits?" · "Can I make it simpler?" · "What's the complexity?"

Don't memorize solutions — learn which pattern a problem uses:

ProblemPattern
Duplicate valuesSet
FrequencyMap
Sorted searchBinary Search
Pair in a sorted arrayTwo Pointers
Consecutive rangeSliding Window
Nested decisionsRecursion / Backtracking

Practice by level:

LevelFocus
1Simple loops, arrays, strings, conditions
2Objects, Map, Set, functions
3Two Pointers, Sliding Window, Stack, Queue
4Binary Search, Recursion, Sorting
5Trees, Graphs, Dynamic Programming
Key point

When you don't know how to solve something: don't panic and don't immediately look for the answer. Understand it, create a small example, solve it manually, break it into steps, write pseudocode, code it, test it, find edge cases, analyze Big O, and improve it.

Quick recap

  • Run the process: understand → break down → plan → pseudocode → code → test → debug → improve
  • Understand input, output, and rules before writing anything
  • Solve a small example manually, then break the problem down
  • Identify the data you must remember to pick a data structure
  • Write pseudocode to separate logic from syntax
  • Start simple, brute force if needed, then optimize
  • Learn patterns: two pointers, sliding window, hash map/set, binary search, recursion, stack, queue, divide & conquer
  • Ask: what changes, what to remember, can I stop early, am I repeating work?
  • Debug by comparing expected vs actual and tracing values
  • Always check edge cases and complexity, and ask if it scales
  • Explain your solution; if you can't, you don't understand it yet
  • Practice by level and learn patterns, not memorized answers
