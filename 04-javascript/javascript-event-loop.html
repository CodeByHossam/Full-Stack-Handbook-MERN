JavaScript Event Loop

Single-threaded model, call stack, Web APIs, task queue, microtasks/macrotasks, ordering, async/await, and pitfalls.

JavaScript Async

Single-threaded model

JavaScript runs one piece of code at a time on a single thread. It can still handle async work (fetch, timers, events, I/O) via the runtime + Event Loop.

Event Loop diagram

The Event Loop is what keeps JavaScript single-threaded yet non-blocking. Synchronous code runs on the stack; async work is handed to the runtime, and its callbacks wait in queues until the stack is free.

Core components

  • Call Stack – Executes JS functions (LIFO). Pushes frames on call, pops on return.
  • Web APIs / Runtime APIs – Browser/Node APIs (timers, fetch, DOM events, I/O) run outside the JS call stack.
  • Task Queue (Macrotasks) – Holds callbacks from setTimeout, setInterval, DOM events, etc. Processed one per iteration.
  • Microtask Queue – Holds Promise.then/catch/finally, queueMicrotask. Drained completely before next macrotask.
  • Event Loop – Continuously checks: if call stack empty → take next eligible task (microtasks first, then macrotasks) and push to stack.

Call Stack

The call stack tracks which function is currently running: each call pushes a frame and each return pops it. Because it is LIFO, the most recent call finishes first — a call that never returns freezes everything.

function one() { console.log("One"); }
function two() { one(); console.log("Two"); }
two();
// Order: two() → one() → console.log("One") → "One" → console.log("Two") → "Two"

Works on LIFO: Last In, First Out.

Synchronous vs Asynchronous

Synchronous code runs top-to-bottom and blocks until it finishes. Asynchronous calls (timers, fetch, events) are handed to the runtime, so the rest of the script keeps running while their callbacks wait to run later.

console.log("A");
setTimeout(() => console.log("B"), 0);
console.log("C");

// Expected: A, C, B
// setTimeout(0) does NOT run immediately; it schedules macrotask.
Key point

setTimeout(fn, 0) means “run after the timer is ready and event loop gets to it”, not immediately.

Microtasks vs Macrotasks

Both queues hold callbacks, but microtasks get priority: after the current synchronous script, the microtask queue is fully drained before a single macrotask runs.

  • Microtasks: Promise.then/catch/finally, queueMicrotask. Higher priority; drained until empty after current sync script completes.
  • Macrotasks: setTimeout/setInterval, I/O, UI events. One per event loop iteration (after microtask queue cleared).
console.log("A");
setTimeout(() => console.log("B"), 0);
Promise.resolve().then(() => console.log("C"));
console.log("D");

// Order: A, D, C, B
// Sync: A,D → Microtasks: C → Macrotasks: B

Worked ordering example

This example mixes all three phases in one script, so it is the canonical ordering test. To predict the output, separate the synchronous lines from the microtasks and the macrotasks, then apply the priority order.

console.log("1");   // sync — runs first

setTimeout(() => {
    console.log("2");   // macrotask — runs after all microtasks
}, 0);

Promise.resolve().then(() => {
    console.log("3");   // microtask — queued now, runs after sync
});

Promise.resolve().then(() => {
    console.log("4");   // microtask — FIFO, runs after 3
});

console.log("5");   // sync — runs before any queued callback

Expected output order:

1
5
3
4
2
Explanation
  • Run all synchronous code first: 1, 5.
  • Draining microtask queue (all Promises): 3, then 4 (chained microtasks stay in microtask phase until queue empty).
  • Then next macrotask: 2 from setTimeout.

Microtask draining (nested)

A microtask can enqueue another microtask. The queue keeps draining until it is completely empty before any macrotask runs.

Promise.resolve().then(() => {
    console.log("A");
    Promise.resolve().then(() => {
        console.log("B");
    });
});
setTimeout(() => console.log("C"), 0);

// Order: A, B, C
// New microtask created inside microtask runs before moving to macrotask.

How async/await fits

async/await is built on Promises. await pauses execution of the current async function (its continuation is scheduled as a microtask) without blocking the entire JS runtime.

console.log("1");
async function test() {
    console.log("2");
    await Promise.resolve();
    console.log("3"); // continuation
}
test();
console.log("4");

// Order: 1, 2, 4, 3
Note

await pauses the current async function, not the entire runtime. Other synchronous code continues to run.

Fetch

fetch is a Web API; network request happens off-thread. When response arrives, its .then continuations go to microtask queue (Promise-based).

console.log("Start");
fetch("/api/users")
  .then(r => r.json())
  .then(data => console.log(data));
console.log("End");

// Order: Start, End, [data]

Blocking JavaScript

Long-running synchronous loops block the call stack → Event Loop cannot process callbacks until finished → UI may feel frozen.

function heavyWork() {
  for (let i = 0; i < 10_000_000_000; i++) { /* busy */ }
}
heavyWork(); // blocks
Warning

Avoid large synchronous blocks in UI code. Offload heavy work or chunk it.

Non-blocking I/O (Node.js)

Node uses event-driven model: start async I/O (fs, DB), don’t wait synchronously, continue handling other work; callback/Promise runs when I/O completes.

const fs = require("fs");
console.log("Start");
setTimeout(() => console.log("Timer"), 0);
fs.readFile("file.txt", () => console.log("File"));
console.log("End");

Exact ordering between different async operations depends on runtime/timing (don’t memorize a fixed universal order).

Callbacks, Promises, and readability

Callbacks are simple but can lead to nesting; Promises + async/await improve readability and error handling.

async function safeFetch() {
  try {
    const res = await fetch("/api");
    return await res.json();
  } catch (e) {
    console.error(e);
  }
}

Common pitfalls

  • Calling a function instead of passing reference: onClick={fn()} runs immediately.
  • Assuming setTimeout(0) is synchronous.
  • Expecting microtasks to wait for macrotasks or vice versa in wrong order.
  • Blocking event loop with heavy sync loops (freezes UI).
  • Confusing “pauses JS” with “pauses runtime” – await only pauses current async function.

Quick recap

  • JS is single-threaded; Event Loop coordinates async via runtime.
  • Call Stack (LIFO) runs sync code first.
  • Microtasks (Promises, queueMicrotask) drain completely before macrotasks (setTimeout, events).
  • await pauses the current async function, not the whole runtime.
  • Network I/O is off-thread; completions schedule Promises/microtasks.
  • Avoid long sync blocks – they block the Event Loop.
  • Memorize the canonical order: sync → microtasks → macrotasks.
