Design Patterns

All 22 Gang of Four patterns plus the MERN-specific ones — what each pattern is, why it exists, how to implement it, and when to reach for it (and when not to).

Practices 22 GoF patterns MERN examples

What a design pattern actually is

What: A design pattern is a named, reusable solution to a recurring design problem. It is not code you copy — it is a description of a solution plus the trade-offs behind it. Why: Patterns give you a battle-tested answer for a problem someone has already solved dozens of times, and they give the whole team a shared vocabulary instead of an argument. When: Use a pattern when you recognize the problem it solves — never because "it sounds professional".

The Gang of Four (Erich Gamma, Richard Helm, Ralph Johnson, John Vlissides, 1994) described every pattern with the same four-part anatomy. Learn this anatomy — it applies to every pattern on this page:

PartQuestion it answersExample (Observer)
ProblemWhat recurring situation forces this design?"I need to notify many parts of the app when one thing changes."
ContextWhen does the pattern apply?"The subject must notify an unknown number of dependents."
SolutionWhat is the structure of the fix?"Register listeners, then broadcast events to them."
ConsequencesWhat do you gain and what do you pay?Gains: loose coupling. Pays: subscribers can drift out of sync.

What a pattern is not:

  • Not a library. You do not install a pattern; you write it (or use a library that implements it).
  • Not an algorithm. An algorithm solves a computational problem; a pattern solves a design problem.
  • Not a framework. Frameworks call your code; patterns are structures you arrange.
  • Not a silver bullet. Every pattern has costs — that is why the Consequences part exists.
Key point

A pattern is a trade-off packaged with a name. If you cannot name the problem a pattern solves, you are not using it — you are decorating.

Two ideas from the original book are worth remembering for every pattern that follows:

  • Composition over inheritance — prefer composing objects over deep class hierarchies. In JavaScript, this mostly means favoring mixins, factory functions, and plain delegation over class A extends B extends C.
  • Program to the interface, not the implementation — in JS that means depend on the shape of an object (duck typing) rather than on the concrete class behind it.

The three families (and the full catalog)

Patterns are grouped by what kind of pressure they relieve:

  • Creational — pressure on object creation. "Which object should I make, and how do I hide the making?"
  • Structural — pressure on object composition. "How do objects fit together so that change in one doesn't break another?"
  • Behavioral — pressure on object interaction. "Who calls whom, and how is responsibility split?"

Creational patterns

Singleton — one instance, one access point

What: A pattern that guarantees a class has exactly one instance and provides a global access point to it. Why: Some resources are expensive or must be shared and consistent — a database connection pool, a logger, a feature-flag client. Creating them repeatedly wastes resources or breaks state. When: Use it when one instance is genuinely required and the resource is process-wide, stateless-ish, and cheap to access.

// ---- The classic (and safest in JS): module singleton ----
// ES modules are cached by the runtime, so the module body runs once.
class Database {
  constructor() {
    this.connected = false;
  }

  connect() {
    this.connected = true;
    return this;
  }
}

let instance = null;

export function getDatabase() {
  if (!instance) {
    instance = new Database().connect();
  }
  return instance;
}

How — the mechanics are always the same three moves: private constructor (so nobody calls new directly), a static instance holder, and a single public getter. The factory-function version below is the most idiomatic JavaScript because a closure gives you a truly private constructor for free:

function createLogger() {
  let instance = null;

  class Logger {
    constructor() {
      this.entries = [];
    }
    log(message) {
      this.entries.push(message);
      console.log(message);
    }
  }

  return {
    getInstance() {
      if (!instance) instance = new Logger();
      return instance;
    }
  };
}

export const logger = createLogger();

When to use it in a MERN app:

  • The MongoDB / Mongoose connection (normally handled by Mongoose's own caching — do not reinvent it).
  • Application-wide configuration and feature flags.
  • A logger or metrics collector that must aggregate across the whole process.
  • An in-process cache when Redis is overkill (single-server apps only).

When NOT to use it — the honest warning. Singleton is the most misused pattern in JavaScript:

  • Hidden dependencies. A function that reaches for a global logger can no longer be tested with a fake logger — you have to mutate the real one.
  • Global mutable state. Shared state leaks between tests and creates race conditions.
  • One instance per process, not per system. Under cluster / PM2 / Docker scaling, you get N singletons, N connection pools, and inconsistent caches.
  • Tight coupling. Everything depends on the same object, so it cannot be swapped.
// BAD: hard-wired global, impossible to fake in tests
function sendWelcomeEmail(user) {
  logger.log("sending email");
  mailer.send(user.email);
}

// GOOD: dependencies passed in (dependency injection).
// The singleton still exists — it is just created and injected at the edge.
function sendWelcomeEmail({ mailer, logger }, user) {
  logger.log("sending email");
  mailer.send(user.email);
}

// tests can pass a fake mailer; production passes the real singleton
const fake = { send: () => {}, log: () => {} };
sendWelcomeEmail(fake, { email: "a@b.c" });
Warning

In a horizontally scaled Node app, a singleton cache is per container. Use Redis (or a Mongo collection) for shared state, and treat the singleton as a thin wrapper around it.

Testing a singleton: expose a reset() (or setInstance()) hook used only by tests, or reset module state with vi.resetModules() / jest.resetModules(). Otherwise the first test pollutes every test after it.

Factory Method

What: A method (or function) that decides which concrete object to create, instead of the caller calling new directly. Why: The caller depends on an interface rather than a class, so you can swap implementations without touching the caller. When: Use it when the type of object depends on runtime data (a config value, a request parameter, a channel name) and the list of types is open to extension.

class EmailChannel {
  constructor() { this.type = "email"; }
  send(to, message) { console.log("email ->", to, message); }
}

class SmsChannel {
  constructor() { this.type = "sms"; }
  send(to, message) { console.log("sms ->", to, message); }
}

class PushChannel {
  constructor() { this.type = "push"; }
  send(to, message) { console.log("push ->", to, message); }
}

const channels = { email: EmailChannel, sms: SmsChannel, push: PushChannel };

// The factory: one place that knows every concrete class.
function createChannel(type) {
  const Channel = channels[type];
  if (!Channel) throw new Error(`Unknown channel: ${type}`);
  return new Channel();
}

// The caller never imports EmailChannel.
function notifyUser(user, message) {
  return createChannel(user.preferredChannel).send(user.contact, message);
}

In MERN: choosing a Mongoose model by name, picking a payment provider (stripe vs paypal), or mapping a route verb to a handler set. A switch inside a factory is often simpler than a class hierarchy — JS does not need the ceremony.

Abstract Factory

What: A factory that produces a family of related objects and guarantees they work together. Why: You need a whole consistent set (Mongo repositories + Mongo models), and you want to switch the entire set at once without mixing incompatible parts. When: Use it when the product family is known but the concrete family is chosen at runtime — for example, a MONGO vs SQL persistence layer, or stripe vs paypal vs manual payment providers.

// Both factories expose the same interface.
function createMongoProductRepository() {
  return {
    async findById(id) {
      return { id, name: "Mongo Product", price: 10 };
    },
    async save(product) {
      return { ...product, savedIn: "mongo" };
    }
  };
}

function createSqlProductRepository() {
  return {
    async findById(id) {
      return { id, name: "SQL Product", price: 10 };
    },
    async save(product) {
      return { ...product, savedIn: "sql" };
    }
  };
}

function createRepositoryFactory(driver) {
  const factories = {
    mongo: createMongoProductRepository,
    sql: createSqlProductRepository
  };
  const factory = factories[driver];
  if (!factory) throw new Error(`Unsupported driver: ${driver}`);
  return factory();
}

// The service depends only on the interface, not on MongoDB or SQL.
const repo = createRepositoryFactory(process.env.DB_DRIVER);
const product = await repo.findById("123");
Note

The real-world MERN version of this is a database abstraction layer: the service layer talks to an interface, and mongo-repository.js or sql-repository.js implements it. See MERN Architecture.

Builder

What: A pattern that assembles a complex object through a series of explicit steps, then produces the finished object. Why: Constructor parameter lists with 8 optional arguments are unreadable and easy to get wrong. When: Use it when an object has many optional fields, when a step-by-step process must be readable, or when the construction process itself is complex.

class ProductQuery {
  constructor() {
    this.filters = {};
    this.options = { limit: 20, sort: "-createdAt", page: 1 };
  }

  where(field, value) {
    this.filters[field] = value;
    return this;                       // fluent: return this
  }

  category(category) {
    return this.where("category", category);
  }

  pricedBetween(min, max) {
    this.filters.price = { $gte: min, $lte: max };
    return this;
  }

  limit(count) {
    this.options.limit = count;
    return this;
  }

  page(number) {
    this.options.page = number;
    return this;
  }

  build() {
    return {
      filter: { ...this.filters },
      options: { ...this.options }
    };
  }
}

// Usage reads like a sentence
const query = new ProductQuery()
  .category("laptops")
  .pricedBetween(500, 2000)
  .limit(10)
  .page(2)
  .build();

const products = await Product.find(query.filter)
  .sort(query.options.sort)
  .skip((query.options.page - 1) * query.options.limit)
  .limit(query.options.limit);

In MERN: Mongoose's own query builder (Model.find().where().sort().limit().select()) is exactly this pattern; so are filter builders for your REST API and report builders in an admin panel.

Prototype

What: Create new objects by copying a prototype instance. Why: Cheaper and safer than re-running complex construction, and it lets you pre-load defaults. When: Use it when objects of the same kind are expensive to build, when you need many similar records, or when you want a "template object" with defaults.

// Copy an existing instance (shallow copy)
const baseProduct = {
  name: "Generic product",
  price: 0,
  category: "misc",
  tags: []
};

function createProduct(overrides = {}) {
  const product = Object.create(baseProduct);   // prototype = template
  return Object.assign(product, overrides);     // own properties override
}

const laptop = createProduct({ name: "Laptop", price: 1200, category: "tech" });
const phone = createProduct({ name: "Phone", price: 800 });

console.log(laptop.name);      // "Laptop"  (own property)
console.log(laptop.category);  // "tech"    (own property)
console.log(phone.category);   // "misc"   (inherited from prototype)

Watch out: shallow copies share nested references. Object.create + Object.assign copies references, so two products can end up sharing the same tags array. Deep-clone the nested parts (or use structuredClone) when they must be independent.

Object Pool

What: Reuse a fixed set of pre-created objects instead of allocating new ones. Why: Allocation and garbage collection cost time and memory under load. When: Use it for objects that are expensive to create (DB connections, buffers, workers) and are used in bursts.

class ObjectPool {
  #factory;
  #available = [];
  #inUse = new Set();

  constructor(factory, size) {
    this.#factory = factory;
    for (let i = 0; i < size; i++) {
      this.#available.push(factory());
    }
  }

  acquire() {
    const obj = this.#available.pop() ?? this.#factory();
    this.#inUse.add(obj);
    return obj;
  }

  release(obj) {
    if (!this.#inUse.delete(obj)) return;
    obj.reset?.();                 // object should reset itself
    this.#available.push(obj);
  }
}

// usage
const pool = new ObjectPool(() => ({ reset() {} }), 5);
const session = pool.acquire();
try {
  await session.run();
} finally {
  pool.release(session);
}

Structural patterns

Adapter

What: A wrapper that converts one interface into the interface your code expects. Why: Third-party libraries rarely match your domain model exactly. Adapters isolate that mismatch in one small file instead of leaking it through your whole codebase. When: Use it at integration boundaries — a payment SDK, an SMS provider, a legacy API, a different database driver.

// Your app speaks this interface
class PaymentGateway {
  async charge({ amount, currency, token }) {
    throw new Error("not implemented");
  }
}

// The Stripe SDK speaks a different one
class StripeSDK {
  async createPaymentIntent({ amount, currency, payment_method }) {
    return { id: "pi_123", status: "succeeded" };
  }
}

// The adapter translates between them
class StripePaymentAdapter extends PaymentGateway {
  constructor(stripe) {
    super();
    this.stripe = stripe;
  }

  async charge({ amount, currency, token }) {
    const intent = await this.stripe.createPaymentIntent({
      amount: Math.round(amount * 100),   // dollars -> cents
      currency,
      payment_method: token
    });
    return { id: intent.id, status: intent.status };
  }
}

// The service only ever sees PaymentGateway
const gateway = new StripePaymentAdapter(stripe);
await gateway.charge({ amount: 49.99, currency: "usd", token: "tok_abc" });

In MERN: an adapter is the right place to put every vendor quirk — currency conversion, webhook signature checks, error translation into your own AppError types. See File Storage: S3 & Cloudinary for a real adapter example.

Decorator

What: Wrap an object to add behavior, keeping the original object untouched. Why: It gives you composable, stackable features without touching (or subclassing) the original code. When: Use it when you want optional cross-cutting behavior — logging, caching, retries, timing, authorization — that applies to many classes.

function withLogging(fn) {
  return function (...args) {
    console.log(`[call] ${fn.name}`);
    const result = fn(...args);
    console.log(`[done] ${fn.name}`);
    return result;
  };
}

function withCache(fn, ttlMs = 60_000) {
  const store = new Map();
  return async function (...args) {
    const key = JSON.stringify(args);
    if (store.has(key)) return store.get(key);

    const value = await fn(...args);
    store.set(key, value);
    setTimeout(() => store.delete(key), ttlMs).unref?.();
    return value;
  };
}

async function getProduct(id) {
  return { id, name: "Laptop" };
}

// Stack decorators: the last one applied runs first
const getProductCached = withLogging(withCache(getProduct));

const product = await getProductCached("123");

Class-based version (same idea, explicit):

class LoggingProductService {
  constructor(service) {
    this.service = service;
  }
  async getProduct(id) {
    console.log("getProduct", id);
    return this.service.getProduct(id);
  }
}

In MERN: Express error-handling middleware, a retry wrapper around an HTTP client, or a validate() wrapper around route handlers are all decorators. Decorators keep features optional — nothing forces you to extends a base class.

Facade

What: A single simplified interface in front of a complex subsystem. Why: Callers should not need to know the order, the error handling, or the five services involved to complete one business operation. When: Use it when a workflow spans several subsystems and you want one obvious entry point.

class CheckoutFacade {
  constructor({ cart, inventory, payments, orders, email }) {
    this.cart = cart;
    this.inventory = inventory;
    this.payments = payments;
    this.orders = orders;
    this.email = email;
  }

  // One call, five coordinated steps
  async placeOrder(userId) {
    const cart = await this.cart.get(userId);
    if (!cart.items.length) throw new Error("Cart is empty");

    const reserved = await this.inventory.reserve(cart.items);
    const payment = await this.payments.charge(userId, reserved.total);
    const order = await this.orders.create({ userId, items: reserved.items, payment });
    await this.email.sendReceipt(userId, order);
    return order;
  }
}

// The controller stays thin
router.post("/checkout", asyncHandler(async (req, res) => {
  const order = await checkoutFacade.placeOrder(req.user.id);
  res.status(201).json(order);
}));
Note

A facade is exactly the Service Layer pattern in a MERN app — and it is also the practical difference between a fat controller and a thin one. See MERN Architecture.

Composite

What: Treat individual objects and compositions of those objects uniformly — the client code cannot tell a leaf from a branch. Why: Recursive structures become easy to work with: one method call handles "one node" and "a tree of nodes" the same way. When: Use it for trees: category trees, folder trees, permission trees, menus, comments with replies.

class FileNode {
  constructor(name) {
    this.name = name;
  }
  getSize() {
    return 0;
  }
  print(indent = "") {
    console.log(indent + this.name);
  }
}

class File extends FileNode {
  constructor(name, size) {
    super(name);
    this.size = size;
  }
  getSize() {
    return this.size;
  }
  print(indent = "") {
    console.log(`${indent}${this.name} (${this.size}kb)`);
  }
}

class Directory extends FileNode {
  constructor(name) {
    super(name);
    this.children = [];
  }
  add(node) {
    this.children.push(node);
    return this;
  }
  getSize() {
    return this.children.reduce((total, child) => total + child.getSize(), 0);
  }
  print(indent = "") {
    console.log(indent + this.name + "/");
    this.children.forEach((child) => child.print(indent + "  "));
  }
}

// The client treats both the same way
const tree = new Directory("src")
  .add(new Directory("models").add(new File("user.js", 4)))
  .add(new File("app.js", 12));

tree.print();
console.log(tree.getSize());   // 16 — no special-casing anywhere

Proxy

What: A stand-in object that forwards calls to a real object while adding control: lazy creation, caching, access checks, remote calls. Why: It lets you add a behavior (like "load only when needed") without changing the real object. When: Use it for lazy loading, caching, access control, remote/virtual objects, and rate limiting.

class ProductProxy {
  constructor(id, repository) {
    this.id = id;
    this.repository = repository;
    this._promise = null;      // no query has run yet
  }

  // The first call loads; later calls reuse the same promise.
  async load() {
    if (!this._promise) {
      this._promise = this.repository.findById(this.id);
    }
    return this._promise;
  }
}

const product = new ProductProxy("123", repository);

// Only this line triggers the database query — and only once.
const { name, price } = await product.load();

Proxy vs Decorator: a proxy imitates the real object and controls access to it; a decorator wraps an existing object to add behavior while keeping the same interface. The code looks similar, the intent is different.

Bridge

What: Split an abstraction from its implementation with a separate hierarchy, connected by a bridge. Why: Without it, adding a new implementation means editing the abstraction and every subclass — the classic "diamond" explosion. When: Use it when two dimensions vary independently (notification type × channel, document type × renderer, UI component × platform).

// Implementation hierarchy
class EmailChannel {
  send(message) { console.log("email:", message); }
}
class SmsChannel {
  send(message) { console.log("sms:", message); }
}

// Abstraction hierarchy
class Notification {
  constructor(channel) {
    this.channel = channel;      // the "bridge"
  }
  notify(message) {
    this.channel.send(`[app] ${message}`);
  }
}

class Alert extends Notification {}
class Digest extends Notification {}

// 2 abstractions x 2 implementations = 4 combinations, no subclass explosion
new Alert(new EmailChannel()).notify("Disk almost full");
new Digest(new SmsChannel()).notify("Weekly report");
new Alert(new SmsChannel()).notify("Login from new device");

Flyweight

What: Share many identical heavy objects instead of creating one per place that needs them. Why: Memory. If 10,000 table cells use the same icon object, one shared instance is enough. When: Use it when many objects are identical, cheap to create but expensive in memory, and mostly immutable.

// Shared, immutable icon metadata
const iconCache = new Map();

function getIcon(name) {
  if (!iconCache.has(name)) {
    iconCache.set(name, { name, svg: `<svg><use href="#${name}"></use></svg>` });
  }
  return iconCache.get(name);
}

// 10,000 rows reference the same 5 icon objects
const rows = Array.from({ length: 10_000 }, (_, i) => getIcon("star"));
console.log(new Set(rows).size);   // 1 — not 10,000

In a MERN app the same idea appears as a shared map of style objects, a sprite sheet, an in-memory cache of reference data (countries, currencies), or a Map-backed memoization helper.

Behavioral patterns

Strategy

What: A family of interchangeable algorithms behind a common interface; the caller picks one at runtime. Why: A chain of if/else that grows with every new rule is a classic smell. Strategy turns that chain into independent, testable objects. When: Use it when the algorithm varies but the surrounding code doesn't.

// Each strategy is a standalone function with the same shape
const pricingStrategies = {
  regular: (price) => price,
  premium: (price) => price * 0.9,
  seasonal: (price, { season }) => (season === "winter" ? price * 0.8 : price),
  coupon: (price, { code }) => (code === "SAVE10" ? price * 0.9 : price)
};

function calculateTotal(price, strategyName, context = {}) {
  const strategy = pricingStrategies[strategyName];
  if (!strategy) throw new Error(`Unknown strategy: ${strategyName}`);
  return strategy(price, context);
}

calculateTotal(100, "regular");
calculateTotal(100, "coupon", { code: "SAVE10" });

// Adding a strategy = adding one entry, no edits to calculateTotal
pricingStrategies.loyal = (price) => price * 0.95;

In MERN: pricing and discount rules, sorting and filtering options, pluggable export formats, or swapping a password hasher (bcrypt → argon2) without touching the auth service. In JavaScript, plain functions are usually enough — you rarely need a class per strategy.

Observer

What: Define a one-to-many dependency: when the subject changes, all registered dependents are notified automatically. Why: Without it, the subject must know every listener and call them one by one — tight coupling and a growing if chain. When: Use it when the number of listeners is unknown or changes at runtime, and listeners should be able to subscribe and unsubscribe.

class EventEmitter {
  #listeners = new Map();

  on(event, listener) {
    if (!this.#listeners.has(event)) this.#listeners.set(event, new Set());
    this.#listeners.get(event).add(listener);
    return () => this.off(event, listener);   // returns an unsubscribe fn
  }

  off(event, listener) {
    this.#listeners.get(event)?.delete(listener);
  }

  emit(event, payload) {
    this.#listeners.get(event)?.forEach((listener) => {
      try {
        listener(payload);
      } catch (error) {
        console.error(`listener for "${event}" failed`, error);  // one bad listener must not break the rest
      }
    });
  }
}

const bus = new EventEmitter();

const unsubscribe = bus.on("order:created", (order) => {
  console.log("send email for", order.id);
});

bus.on("order:created", (order) => {
  console.log("clear cart for", order.id);
});

bus.emit("order:created", { id: "1" });
unsubscribe();   // stop listening

In MERN: the events module in Node is exactly this. Use it for domain events inside one service, but remember: an in-process event bus is not durable. If the event must not be lost (send an email, charge a card), use a real queue (BullMQ, SQS) or an outbox table instead.

Template Method

What: Define the skeleton of an algorithm in a base function, and let steps be overridden by subclasses or options. Why: It guarantees the order of operations while allowing individual steps to vary — the algorithm stays correct even as parts change. When: Use it when several classes share the same overall process but differ in one or two steps.

class ReportGenerator {
  // The template: fixed order, overridable steps
  generate() {
    const raw = this.collectData();
    const processed = this.process(raw);
    const output = this.format(processed);
    this.deliver(output);
    return output;
  }

  collectData() { throw new Error("collectData() must be implemented"); }
  process(data) { return data; }
  format(data) { return JSON.stringify(data, null, 2); }
  deliver(output) { console.log("delivered", output.length, "bytes"); }
}

class SalesReport extends ReportGenerator {
  collectData() { return [{ month: "Jan", total: 1200 }]; }
  process(data) { return data.map((row) => ({ ...row, tax: row.total * 0.14 })); }
  format(data) { return data.map((row) => `${row.month}: ${row.total}`).join("\n"); }
}

new SalesReport().generate();

In MERN: a shared base controller that always sets headers, parses the body, and calls a handler; or a seed script that always connects → clears → inserts → logs but lets you swap the data source.

Note

Template Method uses inheritance; the composition-friendly alternative is the Strategy pattern (pass the varying steps in as functions). In JavaScript, prefer composition.

Command

What: Encapsulate a request as an object that can be stored, queued, logged, or undone. Why: Turning an action into data lets you schedule it, retry it, serialize it, or reverse it. When: Use it for job queues, background tasks, undo/redo, and audit logging of actions.

class SendEmailCommand {
  constructor({ to, subject, body }) {
    this.to = to;
    this.subject = subject;
    this.body = body;
  }

  execute(mailer) {
    return mailer.send({ to: this.to, subject: this.subject, body: this.body });
  }
}

class DeleteUserCommand {
  constructor(userId) {
    this.userId = userId;
  }

  execute(userService) {
    return userService.remove(this.userId);
  }
}

// Commands are plain data: they can be queued, retried, or logged
const queue = [new SendEmailCommand({ to: "a@b.c", subject: "Hi", body: "…" })];

for (const command of queue) {
  await command.execute(mailer);
}

In MERN: BullMQ jobs are commands in production form — a job payload plus a handler function. This is also the shape of an outbox record: write the intent to the database in the same transaction as the data change, then a worker picks it up.

Iterator

What: Provide a way to walk through a collection without exposing its internal structure. Why: The client code stops depending on arrays vs Maps vs database cursors; you can change the underlying storage without changing the traversal code. When: Use it for paginated data, lazy loading, infinite scroll, and custom collection types.

// Async generator-based iterator: no class needed
async function* paginate(fetchPage, pageSize = 20) {
  let page = 0;
  let hasMore = true;

  while (hasMore) {
    const { items, nextCursor } = await fetchPage(page, pageSize);
    for (const item of items) {
      yield item;
    }
    hasMore = Boolean(nextCursor);
    page += 1;
  }
}

// usage
const iterator = paginate(async (page, size) => {
  const res = await fetch(`/api/products?page=${page}&limit=${size}`);
  const data = await res.json();
  return { items: data.items, nextCursor: data.nextCursor };
});

for await (const product of iterator) {
  console.log(product.name);
}

In MERN: cursor-based pagination on the server, and infinite scroll on the client. A generator keeps memory flat: you never load 10,000 rows into an array.

State

What: Let an object's behavior change based on its internal state, by swapping the implementation object. Why: A status field plus a wall of if (status === …) branches spreads the rules across the class. The State pattern makes each state a first-class object that owns its own transitions. When: Use it for workflows with clear states: orders, subscriptions, invoices, deployment pipelines.

const orderStates = {
  pending: {
    next: ["paid", "cancelled"],
    pay(order) { order.status = "paid"; return order; },
    cancel(order) { order.status = "cancelled"; return order; }
  },
  paid: {
    next: ["shipped", "refunded"],
    ship(order) { order.status = "shipped"; return order; },
    refund(order) { order.status = "refunded"; return order; }
  },
  shipped: { next: ["delivered"] },
  delivered: { next: [] },
  cancelled: { next: [] },
  refunded: { next: [] }
};

function transition(order, action) {
  const state = orderStates[order.status];
  if (!state) throw new Error(`Unknown state: ${order.status}`);

  const handler = state[action];
  if (!handler) {
    throw new Error(`Cannot "${action}" an order that is "${order.status}"`);
  }
  return handler(order);
}

const order = { id: "1", status: "pending" };
transition(order, "pay");      // status -> "paid"
transition(order, "ship");     // status -> "shipped"
transition(order, "cancel");   // throws: cannot cancel a shipped order
Key point

Every state object declares its own next states. That single list is usually the best place to document and test your workflow — and it makes illegal transitions impossible to express.

Chain of Responsibility

What: Pass a request along a chain of handlers; each handler either handles it, passes it on, or stops the chain. Why: Each concern stays in its own small function instead of one giant function that validates everything. When: Use it for request pipelines: middleware, validation, authorization, logging, retries.

// A chain of small, focused handlers
function requestLogger(req, res, next) {
  console.log(`${req.method} ${req.url}`);
  next();
}

function authenticate(req, res, next) {
  if (!req.headers.authorization) {
    return res.status(401).json({ message: "Unauthorized" });
  }
  next();
}

function requireRole(role) {
  return function (req, res, next) {
    if (req.user.role !== role) {
      return res.status(403).json({ message: "Forbidden" });
    }
    next();
  };
}

function rateLimit(req, res, next) {
  if (isRateLimited(req.ip)) {
    return res.status(429).json({ message: "Too many requests" });
  }
  next();
}

// Compose the chain
const chain = [requestLogger, authenticate, rateLimit, requireRole("admin")];

function runChain(index = 0) {
  const handler = chain[index];
  if (!handler) return;
  handler(req, res, () => runChain(index + 1));
}

In MERN: this is literally how Express works — app.use(mw1); app.use(mw2); and the next() callback moves to the next link. Error-handling middleware (4 arguments) is the same pattern with an extra branch.

Mediator

What: Define an object that coordinates communication between a set of objects, so they don't talk to each other directly. Why: With many objects calling each other, you get a web of dependencies that is hard to follow and change. When: Use it for multi-step workflows where the order of interactions matters (checkout, sign-up) or a chat-style system.

class SignupMediator {
  constructor({ userService, emailService, analytics }) {
    this.userService = userService;
    this.emailService = emailService;
    this.analytics = analytics;
  }

  async signup(data) {
    const user = await this.userService.create(data);
    await this.emailService.sendWelcome(user);
    this.analytics.track("signup", { userId: user.id });
    return user;
  }
}

// Participants talk to the mediator, not to each other
const mediator = new SignupMediator({ userService, emailService, analytics });
await mediator.signup({ email: "a@b.c", password: "…" });

In MERN: a "checkout coordinator" that sequences cart → inventory → payment → order → email, while the individual services stay unaware of each other. The mediator is a natural place to hold the workflow transaction.

Visitor

What: Define a new operation over a set of objects without changing their classes; the operation lives in a separate visitor that is applied to each object. Why: Adding "export to CSV" to 10 entity classes means editing 10 files; with Visitor you write one visitor and call it. When: Use it when the object structure is stable but you frequently add operations over it (export, reporting, serialization).

// Entities expose an accept() method, but know nothing about the operations
class Order {
  constructor(total) { this.total = total; }
  accept(visitor) { return visitor.visitOrder(this); }
}
class Product {
  constructor(price) { this.price = price; }
  accept(visitor) { return visitor.visitProduct(this); }
}

// The operations live in the visitor
class CsvExporter {
  visitOrder(order) { return `order,${order.total}`; }
  visitProduct(product) { return `product,${product.price}`; }
}

const exporter = new CsvExporter();
const rows = [new Order(99), new Product(19.99)].map((entity) => entity.accept(exporter));
Warning

Visitor is the most complex pattern in the book: every new entity type forces a change in every visitor, and a new operation forces a change in every entity. In JavaScript you usually get the same benefit with a plain switch on entity.type — reach for Visitor only when the operation set genuinely grows.

Interpreter

What: Define a small language and a way to evaluate sentences in it. Why: It turns a user-defined expression into first-class data that you can parse and run. When: Use it for rule engines, formula evaluators, filter expressions, or DSLs (e.g. an email template language, a query language).

// A tiny expression language:  price > 100 && category == "laptop"
const rules = {
  ">": (a, b) => a > b,
  "<": (a, b) => a < b,
  "==": (a, b) => a === b
};

function evaluate(expression, context) {
  // split on the operator, then resolve both sides from the context
  const [left, operator, right] = expression.split(/\s+/);
  const rule = rules[operator];
  if (!rule) throw new Error(`Unsupported operator: ${operator}`);

  const resolve = (token) => {
    const key = token.replace(/^"|"$/g, "");   // strip surrounding quotes
    return key in context ? context[key] : Number(token);
  };

  return rule(resolve(left), resolve(right));
}

evaluate('price > 100', { price: 250 });                 // true
evaluate('category == "laptop"', { category: "laptop" }); // true

In MERN: analytics dashboards where the user types a filter expression, permission rules like role:admin AND org:42, or pricing rules stored in the database.

Patterns that are specific to a MERN app

The GoF catalog is about objects. Real web apps have a second layer: architectural patterns that decide where code lives and how requests flow. These are the ones you will use every single day.

Repository pattern

What: A dedicated layer that owns all data access for an entity, hiding the database behind a collection-like interface. Why: Controllers and services stop knowing about Mongoose, queries, and connection details — so you can swap MongoDB for SQL, add caching, or unit-test a service without a database. When: Use it when more than one consumer needs the same data access, or when you want to test business logic without a live DB.

// repositories/product.repository.js
class ProductRepository {
  constructor(model) {
    this.model = model;          // Mongoose model — an implementation detail
  }

  async findById(id) {
    return this.model.findById(id).lean();
  }

  async findMany(filter, options) {
    const query = this.model.find(filter);
    if (options?.sort) query.sort(options.sort);
    if (options?.limit) query.limit(options.limit);
    if (options?.page) query.skip((options.page - 1) * options.limit);
    return query.lean();
  }

  async create(data) {
    return this.model.create(data);
  }
}

module.exports = { ProductRepository };
// services/product.service.js — depends on the interface, not on Mongoose
class ProductService {
  constructor(products) {
    this.products = products;    // injected, so tests pass a fake
  }

  async list({ category, page = 1, limit = 20 }) {
    const filter = category ? { category } : {};
    const items = await this.products.findMany(filter, { page, limit });
    const total = await this.products.count?.(filter) ?? items.length;
    return { items, total, page, limit };
  }
}

// wiring (composition root)
const productService = new ProductService(new ProductRepository(ProductModel));

The payoff: a unit test for the service needs no MongoDB at all.

const fakeProducts = {
  findMany: async () => [{ id: "1", name: "Laptop", price: 1200 }],
  count: async () => 1
};

const service = new ProductService(fakeProducts);
const result = await service.list({ category: "tech" });
assert.equal(result.items.length, 1);

Service layer

What: A layer of plain classes/functions that holds the business rules of the domain, sitting between HTTP and the database. Why: HTTP handlers are about status codes and parsing; business rules ("an order can only be cancelled before shipping") belong somewhere reusable, testable, and independent of Express. When: Use it in every non-trivial app — even in a small project it becomes the layer you will definitely need later.

Request
   |
   v
Route (path, method)        — HTTP concerns
   |
   v
Controller (req/res)        — HTTP concerns
   |
   v
Service (business rules)    — domain concerns
   |
   v
Repository (data access)    — persistence concerns
   |
   v
Database
// controllers/order.controller.js
const orderService = require("../services/order.service");

exports.create = asyncHandler(async (req, res) => {
  const order = await orderService.create({
    userId: req.user.id,
    items: req.body.items
  });
  res.status(201).json(order);
});

Rule of thumb: if you can delete the HTTP layer and the service still makes sense, the separation is correct. A service should never touch req or res.

Middleware (Chain of Responsibility in Express)

What: Functions that run before (or after) a route handler, with the ability to end the request or call next(). Why: Cross-cutting concerns — logging, auth, validation, rate limiting — would otherwise be copy-pasted into every route. When: Use it for anything that applies to many or all routes.

// middleware/auth.js
exports.protect = (req, res, next) => {
  const token = req.headers.authorization?.split(" ")[1];
  if (!token) return res.status(401).json({ message: "Not authenticated" });

  try {
    req.user = jwt.verify(token, process.env.JWT_SECRET);
    next();
  } catch {
    return res.status(401).json({ message: "Invalid token" });
  }
};

// middleware/validate.js — a reusable schema validator
exports.validate = (schema) => (req, res, next) => {
  const { error, value } = schema.validate(req.body);
  if (error) return res.status(422).json({ message: error.details[0].message });
  req.body = value;
  next();
};
// routes/product.routes.js
router.post(
  "/",
  protect,                                  // chain of responsibility
  validate(productSchema),
  createProduct
);

router.delete(
  "/:id",
  protect,
  requireRole("admin"),
  deleteProduct
);

Order matters: authentication before authorization, validation before business logic, error-handling middleware last. Full details in Express.

Dependency injection & the container

What: Objects receive their collaborators from outside instead of creating them with new inside. Why: It removes hidden dependencies, makes code testable, and enables a container that knows how to build the whole object graph. When: Use it whenever a class has more than one dependency, and always in code you intend to test.

// Bad: the class reaches for its own dependency — impossible to fake
class OrderService {
  async create(data) {
    const user = await UserModel.findById(data.userId);
    await mailer.send(user.email);          // hidden global
  }
}

// Good: the dependency arrives from outside
class OrderService {
  constructor({ orders, users, mailer, events }) {
    this.orders = orders;
    this.users = users;
    this.mailer = mailer;
    this.events = events;
  }

  async create(data) {
    const user = await this.users.findById(data.userId);
    const order = await this.orders.create({ ...data, userId: user.id });
    await this.mailer.send(user.email, "Order confirmed");
    this.events.emit("order:created", order);
    return order;
  }
}

A tiny container removes the wiring boilerplate:

class Container {
  #registry = new Map();
  #singletons = new Map();

  register(name, factory) {
    this.#registry.set(name, factory);
    return this;
  }

  resolve(name) {
    if (!this.#registry.has(name)) throw new Error(`Unknown service: ${name}`);
    if (!this.#singletons.has(name)) {
      const deps = this.#registry.get(name).dependencies ?? [];
      const args = deps.map((dep) => this.resolve(dep));
      this.#singletons.set(name, this.#registry.get(name).build(...args));
    }
    return this.#singletons.get(name);
  }
}

// registration
const container = new Container();

container.register("mailer", {
  dependencies: [],
  build: () => new NodemailerMailer(process.env.SMTP_URL)
});
container.register("users", {
  dependencies: [],
  build: () => new UserRepository(UserModel)
});
container.register("orders", {
  dependencies: [],
  build: () => new OrderRepository(OrderModel)
});
container.register("events", {
  dependencies: [],
  build: () => new EventEmitter()
});
container.register("orderService", {
  dependencies: ["orders", "users", "mailer", "events"],
  build: (orders, users, mailer, events) =>
    new OrderService({ orders, users, mailer, events })
});

const orderService = container.resolve("orderService");
Note

The container's singletons are the only place singletons belong: created once, injected everywhere, replaceable in tests. See MERN Architecture for folder-level wiring.

Module pattern

What: Encapsulate related code behind a single exported interface, hiding internals. Why: It is the JavaScript answer to "private members", it gives every file a clear public API, and it prevents accidental cross-file coupling. When: Use it for every file — it is the default way to structure JS/TS code.

// IIFE version (classic)
const Cart = (function () {
  const items = [];

  function add(product) {
    items.push(product);
    return items.length;
  }
  function clear() {
    items.length = 0;
  }

  return { add, clear, get size() { return items.length; } };
})();

// ES module version (modern default) — the file itself is the encapsulation
// cart.js
const items = [];
export function add(product) { items.push(product); }
export function clear() { items.length = 0; }
export function get size() { return items.length; }

Note that the ES module version also gives you a singleton for free: the module is evaluated once per process, so items is a single shared array. That is the cleanest singleton in JavaScript — no class, no getInstance().

Redux as Observer + a state machine

What: A single store holds the state; every dispatch notifies the reducers and the subscribers. Why: Predictable state updates, one source of truth, and a dev-tools time machine — all consequences of the Observer pattern done carefully. When: Use Redux Toolkit for genuinely global client state (auth, cart, preferences); use local state or RTK Query for everything else.

// A slice is a mini state machine for one domain
import { createSlice } from "@reduxjs/toolkit";

const cartSlice = createSlice({
  name: "cart",
  initialState: { items: [], status: "idle" },   // status = the state machine
  reducers: {
    itemAdded(state, action) {
      state.items.push(action.payload);
    },
    itemRemoved(state, action) {
      state.items = state.items.filter((item) => item.id !== action.payload);
    },
    checkoutStarted(state) {
      state.status = "loading";
    },
    checkoutSucceeded(state) {
      state.status = "idle";
      state.items = [];
    }
  }
});

export const { itemAdded, itemRemoved, checkoutStarted } = cartSlice.actions;
export const selectItemCount = (state) => state.cart.items.length;
export default cartSlice.reducer;

See Redux Toolkit + RTK Query for the full setup.

Pub/Sub & event-driven services

What: Publishers emit named events; any number of subscribers react, without knowing who each other are. Why: New features can subscribe to an existing event without editing the publisher — the publisher never changes. When: Use it for cross-cutting reactions (email on signup, analytics on purchase, cache invalidation on update).

// events/order.events.js
const bus = new EventEmitter();

function publishOrderCreated(order) {
  bus.emit("order.created", order);
}

function subscribeToOrderCreated(handler) {
  bus.on("order.created", handler);
  return () => bus.off("order.created", handler);
}

module.exports = { publishOrderCreated, subscribeToOrderCreated };
// subscribers/order-notification.subscriber.js
const { subscribeToOrderCreated } = require("../events/order.events");
const { mailer } = require("../config/mailer");

subscribeToOrderCreated(async (order) => {
  await mailer.send(order.email, "Your order is confirmed");
});
Warning

In-process events are lost if the process crashes and invisible to other services. For anything that must happen reliably, use a durable queue (BullMQ + Redis, SQS, or RabbitMQ) and treat the subscriber as a worker.

Cache as a Proxy / Decorator

What: Wrap a data-access call with a cache that stores results for a short time. Why: Caching is a cross-cutting concern — it should be applied to the repository, not sprinkled through controllers. Why as a pattern: the wrapper keeps the "where does the data come from" question separate from "do we have it already?". When: Use it for expensive, read-mostly queries. Always set a TTL and an invalidation rule.

function withCache(repository, { ttl = 60_000, store = new Map() } = {}) {
  return {
    async findById(id) {
      const key = `product:${id}`;

      if (store.has(key)) {
        const { value, expiresAt } = store.get(key);
        if (expiresAt > Date.now()) return value;
      }

      const value = await repository.findById(id);
      store.set(key, { value, expiresAt: Date.now() + ttl });
      return value;
    },

    findMany: (...args) => repository.findMany(...args)
  };
}

// Use it
const cachedProducts = withCache(new ProductRepository(ProductModel));
const productService = new ProductService(cachedProducts);
Warning

Cache invalidation is where caching goes wrong. A stale cache serving old prices or deleted users is a real bug. Always define: TTL, invalidation on write, and what happens when Redis is down (fail open, usually).

Saga / process manager

What: Break a long business transaction into a sequence of local steps, each with a compensating action if a later step fails. Why: You cannot run a distributed ACID transaction across the database, an email provider, and a payment gateway. When: Use it when one user action triggers several services and partial failure must be recoverable (place order → charge card → reserve stock → ship).

async function placeOrderSaga({ cart, payments, inventory, orders }) {
  // Step 1: reserve stock (compensate: release)
  const reservation = await inventory.reserve(cart.items);

  try {
    // Step 2: charge the card (compensate: refund)
    const payment = await payments.charge(cart.total, cart.paymentToken);

    try {
      // Step 3: create the order (no compensation needed — it's the goal)
      return await orders.create({ cart, payment, reservation });
    } catch (error) {
      await payments.refund(payment.id);   // compensate step 2
      throw error;
    }
  } catch (error) {
    await inventory.release(reservation.id); // compensate step 1
    throw error;
  }
}

In MERN: the same idea appears as a State machine stored in the database (order.status + pendingActions[]), where a worker retries the failed step until it succeeds. This is more practical than a pure in-memory saga, because it survives restarts.

Feature-based modular structure

What: Organize code by feature (users, products, orders), not by technical layer (routes/, controllers/, services/ everywhere). Why: A change to one feature touches one folder, not five folders across the tree. When: Use it from the start of any project with more than one feature — it is the structural expression of the Open/Closed Principle and it makes the patterns above easier to apply.

src/
├── modules/
│   ├── products/
│   │   ├── product.model.js        # data
│   │   ├── product.repository.js   # data access
│   │   ├── product.service.js      # business rules
│   │   ├── product.controller.js   # HTTP
│   │   ├── product.routes.js       # routing
│   │   ├── product.validation.js   # validation
│   │   ├── product.events.js       # pub/sub
│   │   └── index.js                # public API of the module
│   └── orders/
│       └── ...
├── shared/
│   ├── middleware/
│   ├── utils/
│   └── config/
└── app.js

Each module exports one public surface, so other modules never reach into your internals:

// modules/products/index.js
module.exports = {
  routes: require("./product.routes"),
  service: require("./product.service"),
  repository: require("./product.repository"),
  events: require("./product.events")
};

// app.js — the composition root
const productModule = require("./modules/products");
app.use("/api/products", productModule.routes);

How to choose the right pattern

Never start with "which pattern do I want to use?". Start with the pressure you feel:

"Creating the right object is hard"
   -> Creational (Factory, Builder, Prototype, Singleton)

"Objects do not fit together"
   -> Structural (Adapter, Facade, Decorator, Proxy, Composite)

"Who calls whom, and who decides?"
   -> Behavioral (Strategy, Observer, State, Chain of Responsibility)

"My code is a mess of responsibilities"
   -> Architectural (Repository, Service Layer, Module, DI container)
If the symptom is…Look at…Because…
A giant if/else picking the algorithmStrategyEach rule becomes an independent, testable function
One object must call five others after a changeObserver / Pub-SubListeners subscribe instead of being called by hand
The same 4 steps repeat in 6 servicesFacade / Service layerOne entry point owns the sequence
Status fields scattered across the classStateEach state owns its own transitions
Validation/auth copied into every routeChain of ResponsibilityMiddleware handles it once
A vendor SDK leaks through your whole appAdapterTranslation happens at one boundary
A query is unreadable with 6 optional argsBuilderNamed steps instead of positional booleans
Business logic is tangled with req/resService layer + RepositoryDomain rules become testable in isolation
Tests need a real databaseRepository + Dependency injectionYou inject a fake instead
Key point

The honest answer to "which pattern should I use?" is usually none yet. Patterns are for problems you already have. Write the straightforward version first; when the pain appears (a third if branch, a second implementation, an untestable dependency), then extract the pattern.

Anti-patterns and pattern smells

A pattern applied where it does not belong is an anti-pattern. These are the ones you will actually meet in a MERN codebase:

Anti-patternWhat it looks likeFix
God objectOne class with 40 methods handling auth, orders, and emailSplit by responsibility — Service layer, feature modules
Spaghetti codeControl flow jumps between files; nobody can say what runs whenReintroduce separation of concerns and one direction of dependencies
Singleton abuseGlobal state nobody can reset or fakeKeep the singleton at the edge, inject it inward
Shotgun surgeryAdding a field to "User" requires editing 12 filesGroup by feature; give entities one owner
Utility bagutils.js with 90 unrelated functionsSplit by domain; name files after what they do
Magic strings"admin", "pending" typed everywhereConstants / enums / shared state machine
Premature abstractionA "BaseController" with one subclass, built for a hypothetical futureYAGNI — delete it; abstract on the third real case
Distributed monolithTwo "services" that must deploy together and share a databaseMerge into one module until a real boundary appears
Leaky abstractionMongoose documents leaking into React components and API responsesMap at the boundary: .lean(), DTOs, serializers
Callback hellNested callbacks 6 levels deepasync/await + a thin error boundary

Warning signs that you over-engineered:

  • You cannot explain the pattern in one sentence without using the word "flexible".
  • You added a base class or interface with exactly one implementation.
  • A new developer cannot guess where to add a new endpoint.
  • The pattern exists "for future flexibility" but there is no second use case yet.
  • The file is more about plumbing than about the business problem.
Warning

Patterns are a vocabulary, not a quality score. A codebase with three well-chosen patterns beats one with fifteen textbook ones. Always prefer the simplest design that solves the problem — see Programming Principles (KISS, YAGNI) and Clean Code.

Applying patterns in real work

A repeatable process for introducing a pattern without wrecking a working codebase:

  1. Name the pain, not the pattern. "I have to change the payment provider in 9 files" — not "we need the Adapter pattern".
  2. Check the simple fix first. A shared function, a constant, or a moved file often solves it faster than a pattern.
  3. Refactor green. Make the existing tests pass before you start, so you always know the code works.
  4. Introduce the pattern behind the existing API. Change the internals first, keep the callers working — the pattern is an implementation detail of the module.
  5. Write the test that proves the value. For a repository: a test that runs without a database. For a strategy: a test per strategy. For a state machine: a test per illegal transition.
  6. Delete the old path. Never keep both the old and the new implementation "just in case".
  7. Review the trade-off. Write down what the pattern costs you — that is the part the next developer will need.
# A practical order of adoption for a MERN codebase
1. modules/            feature-based folders        (structure)
2. validation schemas  validate at the boundary     (safety)
3. error middleware    one error shape for the API   (consistency)
4. service layer       business rules out of controllers
5. repository layer    data access behind an interface
6. dependency injection  services get their deps injected
7. events / pub-sub    decouple reactions from commands
8. state machines      explicit lifecycle rules
9. caching (proxy)     only where measurement shows a need
Key point

Notice the order: structure first, then boundaries, then patterns. Each step makes the next one easier, and each step is independently valuable. Adding "Factory + Observer + Command" on day one of a new project is how projects become unreadable.

Quick recap

  • A pattern is a named solution to a recurring design problem: Problem, Context, Solution, Consequences
  • Three families: Creational (creation), Structural (composition), Behavioral (interaction)
  • Singleton = one instance, one access point — use it for connections, config, loggers; never for business state
  • Factory / Abstract Factory = decide (or switch) which concrete class to build at runtime
  • Builder = assemble complex objects with readable named steps
  • Prototype = copy a template instead of rebuilding; watch shared references
  • Adapter = translate a foreign interface at the boundary
  • Decorator = add behavior by wrapping, composably
  • Facade / Service layer = one simple entry point for a complex workflow
  • Composite = treat one node and a tree of nodes identically
  • Proxy = stand in for a real object to control loading, caching, or access
  • Bridge = decouple abstraction from implementation when two dimensions vary
  • Flyweight = share heavy immutable objects to save memory
  • Strategy = interchangeable algorithms; kills the growing if/else
  • Observer = notify subscribers when the subject changes
  • Template Method = fixed skeleton, overridable steps
  • Command = a request as an object: queue it, log it, undo it
  • Iterator = traverse a collection without exposing its internals
  • State = behavior changes with state; each state owns its transitions
  • Chain of Responsibility = handlers in a pipeline until one handles it — that is Express middleware
  • Mediator = a coordinator that owns multi-step workflows
  • Visitor = new operations without changing the classes; use sparingly in JS
  • Interpreter = evaluate a small user-defined language
  • MERN essentials: Repository, Service layer, middleware, DI container, module pattern, Redux store, pub/sub, cache-as-proxy, saga
  • Match the pattern to the pressure you feel, and never to a fashion
  • Guardrails: no god objects, no spaghetti, no premature abstraction, no singleton abuse
  • Adopt in order: structure → boundaries → service → repository → DI → events → states → caching
