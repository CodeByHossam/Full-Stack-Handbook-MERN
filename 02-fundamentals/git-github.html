Git & GitHub

The complete workflow: initialize, stage, commit, branch, merge, push, and open pull requests — plus the rules that keep a repository clean and secret-free.

Fundamentals Version control Workflow

Git vs GitHub

Git is a version control system that tracks changes to your code. GitHub is an online platform for hosting Git repositories and collaborating.

git --version   # verify Git is installed and see which version
Key point

Git runs entirely on your machine and works offline; GitHub is just one remote place to store and share a Git repository. Other hosts such as GitLab and Bitbucket work the same way.

Create a Git repository

Running git init in a folder creates a hidden .git folder — the repository that tracks all history.

git init   # create .git/ in the current folder and start tracking history

Check status

git status shows modified files, new files, deleted files, and staged files.

git status   # your most-used command: see what is staged vs unstaged

Add files

Stage everything, or stage a single file:

git add .        # stage all changes in the current directory tree
git add app.js   # stage just one file
Watch out

git add . stages everything that is not ignored — including secrets. Add a .gitignore with .env and node_modules/ before your first commit.

Commit

A commit records the staged changes with a message. Write messages that describe the change.

git commit -m "Initial commit"        # -m supplies the message inline
git commit -m "Add login functionality"  # describe WHAT changed, not "fix stuff"
git commit -m "Fix product API"
git commit -m "Update navbar"

Amend the last commit's message if you made a mistake:

git commit --amend -m "Updated commit message"  # rewrites the most recent commit only

Already-tracked files can be staged and committed in one step with -a (it does not include brand-new untracked files):

git commit -a -m "Update all modified tracked files"

View history and changes

log shows the commits that were made; diff shows edits that are not committed yet. Together they answer "what happened?" and "what am I about to commit?".

git log             # full commit history
git log --oneline   # one line per commit — much easier to scan

git diff            # unstaged changes (working tree vs the last commit)
git diff --staged   # staged changes (staging area vs the last commit)

Configuration

Set your identity once (globally) so commits are attributed to you:

git config --global user.name "Alice Doe"          # name attached to every commit
git config --global user.email "alice@example.com" # must match your GitHub email

Make Git output easier to read by enabling colors, and review everything you have set:

git config --global color.ui auto   # colorize status/diff/log output for readability
git config --list                   # show all current Git settings

Connect to GitHub

A remote is a named link from your local repository to a copy hosted elsewhere. origin is the conventional name for the main remote. Create an empty repository on GitHub first, then link it.

git remote add origin https://github.com/USERNAME/REPOSITORY.git  # link local repo to GitHub
git remote -v                                                      # list remotes and their URLs

Push for the first time, then push normally afterwards:

git push -u origin main   # -u sets origin/main as the default upstream
git push                  # afterwards a plain push goes to that upstream

Renamed the repository on GitHub, or want to switch between HTTPS and SSH? Update the remote's URL:

git remote set-url origin https://github.com/USERNAME/NEW-REPOSITORY.git  # point origin at a new URL

SSH keys (passwordless auth)

An SSH key pair lets you push and pull without typing a password. The public key goes to GitHub; the private key stays on your machine and must never be shared.

ssh-keygen -t rsa -b 4096 -C "alice@example.com"   # generate a key pair (press Enter to accept defaults)
eval "$(ssh-agent -s)"                             # start the SSH agent in the current shell
ssh-add ~/.ssh/id_rsa                              # load the private key into the agent
cat ~/.ssh/id_rsa.pub                              # print the PUBLIC key so you can copy it

Paste the printed public key into Settings → SSH and GPG keys on GitHub, then verify the connection:

ssh -T git@github.com   # should reply "successfully authenticated" (use git@gitlab.com for GitLab)
Key point

Add the public key (id_rsa.pub or id_ed25519.pub), never the private one. A modern, shorter option is ssh-keygen -t ed25519 -C "alice@example.com".

Clone, pull, and fetch

These get code from GitHub to your machine. Clone is for the first time; pull and fetch update a repository you already have.

git clone https://github.com/USERNAME/REPOSITORY.git   # first-time full copy
git pull                                               # fetch + merge into current branch
git fetch                                              # download new commits but do not merge yet

clone gets a repository for the first time. pull gets the latest changes in an existing repository. fetch downloads information without merging (pull = fetch + merge).

CommandWhen to useMerges automatically?
cloneYou have no local copy yetn/a (creates the repo)
fetchYou want to inspect changes firstNo — remote-tracking only
pullYou want the latest changes nowYes (fetch + merge)

Branches

A branch is a movable pointer to a line of commits. You create one to work on a feature in isolation so main stays stable until the work is reviewed and merged. switch is the modern replacement for checkout.

git branch                 # list branches (* marks the current one)
git branch feature-login   # create a branch (does NOT switch to it)
git checkout feature-login # switch (classic, older command)
git switch feature-login   # switch (modern)
git switch -c feature-login # create + switch in one step

Rename a branch (including the default one) and delete finished branches — locally and on the remote:

git branch -m old-name new-name          # rename any local branch
git branch -M main                       # force-rename the current branch to main
git branch -d feature-login              # delete a merged local branch (-D to force)
git push origin --delete feature-login   # delete the branch on the remote

Merge

Switch to the target branch first, then merge:

git switch main          # you merge INTO the branch you are on
git merge feature-login  # bring feature-login's commits into main

Merge conflicts

When both branches changed the same lines, Git marks the conflict:

<<<<<<< HEAD
your code
=======
other code
>>>>>>> feature-login

Choose the correct code manually, then:

git add .
git commit -m "Resolve merge conflict"

Stash

Temporarily save uncommitted changes and bring them back later:

git stash        # save changes
git stash pop    # restore them
git stash list   # see stashes

Tags

Tags mark releases:

git tag v1.0.0            # mark the current commit as release 1.0.0
git push origin v1.0.0    # tags are NOT pushed by a normal git push

Reset and restore

Unstage a file, or discard local changes to it:

git restore --staged app.js   # unstage
git restore app.js            # discard local changes (destructive)

Undo a commit while keeping or discarding the changes:

git reset --soft HEAD~1   # undo commit, keep changes
git reset --hard HEAD~1   # undo commit AND changes (destructive)
Warning

git reset --hard can permanently remove uncommitted work. Use it only when you are certain.

Simple daily workflow

The loop most teams repeat: start from an up-to-date main, branch off, commit your work, push the branch, then open a pull request.

git switch main           # go to the main branch
git pull                  # get everyone's latest commits first
git switch -c feature-login   # branch off so main stays clean

# Write code...

git status                # review what changed
git add .                 # stage it
git commit -m "Add login" # record it with a clear message
git push -u origin feature-login   # publish the branch to GitHub

# Then open a Pull Request on GitHub.

Quick version for a personal branch:

git pull

# Write code...

git status
git add .
git commit -m "Describe what you changed"
git push

Never commit secrets

Common mistake

Committing secret files. Once a secret is pushed, treat it as compromised and rotate it — removing the file later does not erase it from history.

Never push any of these:

  • .env
  • MongoDB password
  • JWT_SECRET
  • Stripe secret key
  • PayPal secret
  • API keys

Environment variables and secrets are handled by the backend — see Node.js and MERN Architecture.

Quick recap

  • Git tracks code history; GitHub hosts it online.
  • git init creates a repo; git status shows the state.
  • Changes flow: working area → add → staging → commit → repo → push → GitHub.
  • clone gets a repo once; pull gets new changes; fetch downloads without merging.
  • Branches isolate work; merge (and resolve conflicts) brings it back.
  • Stash shelves work; tags mark releases; restore/reset undo changes.
  • Use .gitignore and never commit secrets.
  • SSH keys give passwordless auth: generate with ssh-keygen and add the public key to GitHub.
  • git remote set-url changes the remote; git branch -m renames and git push origin --delete removes a branch.
  • Professional flow: branch → commit → push → pull request → review → merge.
