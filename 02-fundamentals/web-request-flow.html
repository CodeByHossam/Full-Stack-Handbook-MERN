Complete Web Request Flow

From the browser to the server and back — all 14 phases and 25 steps that happen between typing a URL and seeing a rendered page.

Fundamentals End-to-end Layers in action

The overall flow at a glance

Every page load — from typing https://www.example.com/index.html to seeing the rendered page — passes through these 14 phases. The sections below explain each group in detail.

Phase 1–2: Browser URL processing and DNS

Step 1 — User action: the user types https://www.example.com/index.html and the browser receives the URL input.

Step 2 — URL parsing: the browser breaks the URL into components — protocol https, host www.example.com, path /index.html, and the default port 443.

Step 3 — DNS query: the browser checks its own DNS cache, then the OS cache, then the router cache. If the name is not found, it queries a DNS server.

Browser DNS cache → OS DNS cache → Router DNS cache → DNS server

Step 4 — DNS resolution: the DNS server answers:

Domain: www.example.com
IP:     93.184.216.34
Key point

This is a data transformation: a human-readable domain name becomes a machine-readable IP address.

Phase 3: TCP three-way handshake

Step 5 — TCP handshake: before any HTTP data flows, the client and server establish a reliable connection with a three-way handshake.

Client → Server: SYN
  Seq: 1000

Server → Client: SYN-ACK
  Seq: 5000
  Ack: 1001

Client → Server: ACK
  Ack: 5001

After this exchange the transport connection is established. See Networking Layers for how TCP provides ordering, acknowledgements, and retransmission.

Watch out

The order is fixed: DNS resolves the name before TCP connects, TCP connects before the TLS handshake, and only then is the HTTP request sent. If an HTTPS request fails, checking them in this order isolates the cause quickly.

Phase 4–5: HTTP request and TLS encryption

Step 6 — HTTP request creation: the browser builds an HTTP request message.

GET /index.html HTTP/1.1
Host: www.example.com
User-Agent: Mozilla/5.0 ...
Accept: text/html
Accept-Encoding: gzip, deflate
Connection: keep-alive

Step 7 — TLS handshake: for HTTPS, the client and server negotiate an encrypted channel.

ClientHello:  TLS version, cipher suites, random number
ServerHello:  chosen cipher, certificate, random number
Key Exchange: pre-master secret → session keys generated

Step 8 — Data encryption: the HTTP request is encrypted (for example with AES-256-GCM) and becomes unreadable ciphertext.

Original:  GET /index.html HTTP/1.1
Encrypted: 7E 3A 1F 9C B2 4D 8E A1 ...
Note

TLS is a security layer that sits between the application data and the transport. The HTTP message is the same, it is just protected on the wire.

Phase 6–7: Encoding, compression, and packetization

Step 9 — Character encoding: the text request is encoded into bytes (UTF-8).

"GET / HTTP/1.1"
        ↓
47 45 54 20 2F 20 48 54 54 50 ...

Step 10 — Data compression (optional): the payload may be compressed to reduce size — for example 1,024 bytes down to 342 bytes via GZIP/DEFLATE.

Step 11 — IP packet creation: TCP segmentation and IP wrap the payload in an IP packet.

Source IP:      192.168.1.20
Destination IP: 93.184.216.34
TTL:            64
Protocol:       TCP (6)
Payload:        encrypted TCP segment

Encoding, compression, and packetization are three different problems — see Data Representation & Encoding.

Phase 8: ARP and MAC frame creation

Step 12 — MAC frame creation: because the destination IP is not on the local network, the frame is addressed to the router. The host first resolves the router's MAC via ARP.

ARP Request: "Who has 192.168.1.1?"
ARP Reply:   "192.168.1.1 is at BB:BB:BB:BB:BB:BB"

Source MAC:      AA:AA:AA:AA:AA:AA
Destination MAC: BB:BB:BB:BB:BB:BB

The IP packet from step 11 becomes the payload of the Ethernet/Wi-Fi frame. Note that the destination IP is the final server while the destination MAC is the local router — exactly the distinction covered in Networking Layers.

Phase 9: Physical transmission

Step 13 — Binary conversion: frame bytes are converted to bits.

Frame bytes: AA BB CC DD EE FF ...
        ↓
Bits: 10101010 10111011 11001100 ...

Step 14 — Physical signal transmission: bits become physical signals depending on the medium.

MediumSignalDetails
Wi-FiRadio waves2.4 GHz / 5 GHz, OFDM modulation
EthernetElectrical signalsVoltage variations, Manchester/PAM5
FiberLight pulses850 nm / 1310 nm / 1550 nm

Phase 10: Routers and multiple hops

Step 15 — Router reception and processing: the router converts the signal back to bits and a frame, checks the destination MAC, extracts the IP packet, and makes a routing decision.

1. Signal → bits
2. Bits → frame
3. Check destination MAC (matches router)
4. Extract IP packet
5. Check destination IP: 93.184.216.34
6. Routing decision: forward to next hop

Step 16 — MAC address transformation: the router builds a new frame for the next link. The old MAC information is discarded; the IP packet is unchanged.

Old Frame (removed):  AA:AA:AA:AA:AA:AA → BB:BB:BB:BB:BB:BB
New Frame (created):  CC:CC:CC:CC:CC:CC → DD:DD:DD:DD:DD:DD

IP Packet (unchanged): 192.168.1.20 → 93.184.216.34

Step 17 — Forwarded to the next hop: the packet travels through several routers — home router, ISP router, backbone router, destination router — and each hop repeats steps 15–16.

Key point

MAC addresses change at every hop, but the destination IP stays the same end-to-end. That is what makes global routing possible.

Phase 11: Server reception and processing

Step 18 — Server receives the packet: the web server demultiplexes the incoming data.

1. Receive frame from network
2. Check destination MAC
3. Extract IP packet
4. Check destination IP matches
5. Extract TCP segment
6. TCP reassembly

Step 19 — Decryption and decompression: TLS decryption turns ciphertext back into the original request, and decompression expands any compressed payload.

GET /index.html HTTP/1.1
Host: www.example.com

Step 20 — Web server processing: the server parses the request, determines the resource path, checks that the file exists, reads it, and builds a response.

1. Parse HTTP request
2. Determine resource path (/index.html)
3. Check the file exists
4. Read file content
5. Build HTTP response

Phase 12–13: Response preparation and return path

Step 21 — HTTP response creation: the server builds the response message.

HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 1256
Connection: keep-alive

<html>
  <head><title>Example</title></head>
  <body><h1>Hello World!</h1></body>
</html>

Step 22 — Response encoding and encryption: the same processes run in reverse: UTF-8 encoding, optional GZIP compression, TLS encryption, TCP segmentation, and IP packet creation.

Source IP: 93.184.216.34
Dest IP:   192.168.1.20

Step 23 — Response transmission: the packet travels back through the routers to the browser, and each hop transforms the MAC addresses again.

Server → Routers → Browser

HH:HH:HH:HH:HH:HH → GG:GG:GG:GG:GG:GG
GG:GG:GG:GG:GG:GG → FF:FF:FF:FF:FF:FF
...               → AA:AA:AA:AA:AA:AA

Phase 14: Browser reception and rendering

Step 24 — Browser receives the response: the browser reverses the entire stack.

1. Physical → Bits
2. Bits → MAC frame
3. Extract IP packet
4. TCP reassembly
5. TLS decryption
6. Decompression
7. UTF-8 decoding

Step 25 — Browser rendering: the browser parses the HTML, builds the DOM, applies CSS, executes JavaScript, loads images, and paints the page. The user sees the finished web page, typically in roughly 100–500 ms for a simple request.

1. Parse HTML
2. Build DOM
3. Apply CSS styling
4. Execute JavaScript
5. Load images
6. Display the page

Quick recap

  • URL parsing and DNS turn a name into an IP address.
  • A TCP three-way handshake establishes a reliable connection.
  • HTTP builds the request; TLS encrypts it; UTF-8 and GZIP prepare the bytes.
  • IP adds logical addressing; ARP/MAC add local-link addressing.
  • Bits become physical signals and travel hop by hop through routers.
  • Each hop rewrites MAC addresses but keeps the destination IP.
  • The server decrypts, decompresses, processes, and builds a response.
  • The response travels the reverse path, and the browser decodes and renders it.
  • Encapsulation happens going down; decapsulation happens going up.
